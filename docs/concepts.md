# Concepts

Mockingbird turns an API contract into a running mock whose answers come from an LLM, are checked against the contract, and stay consistent for the length of a session. This page names the parts; the other pages go into each one.

## Mocks and contracts

A **mock** is one API you stand in for. It has a name, a route prefix on the data plane (`/` by default when you serve one contract), optional `hosts:` (the real host names it answers for through the [proxy](proxy.md)), a persona, scenarios, chaos, limits and webhooks.

A mock serves the active version of its **contract**: OpenAPI 3.x, Swagger 2.0, GraphQL SDL or introspection JSON, protobuf (`.proto` or a descriptor set), WSDL 1.1 or AsyncAPI 2.x/3.0. The format is detected from the bytes, and each protocol family has its own adapter ([Protocols](protocols.md), [Events](events.md)). Uploading a contract adds a version; activating one swaps the mock's runtime in place, without a restart. When you have no contract, [smart import](import.md) drafts one from documentation, a HAR recording or a Postman collection, for you to review and approve.

Mocks come from the config file (`source = file`, read-only through the API) or from the [Admin API](admin-api.md), the [CLI](cli.md), the [console](console.md) or an agent through [MCP](agents.md) (`source = api`).

## How an answer is made

For each request, the adapter decodes it and validates it against the operation (a request that fails validation gets an error in the contract's declared error shape, and an `X-Mockingbird-Validation` header saying why). Then the engine answers from the first source that can:

| `X-Mockingbird-Source` | Where the answer came from |
| --- | --- |
| `state` | The session already holds the resource (a read after a create, or an item seeded from an earlier list), the stored value matches the response schema and no [earlier write](#sessions-and-state) is waiting to show on it. No LLM call. |
| `cache` | The session asked exactly this before and nothing of that resource type was written since. No LLM call. |
| `llm` | The LLM generated it, prompted with the operation, its response schema, the request, the session's relevant state, the mock's persona and the scenario's instructions, and the answer validated. |
| `patched` | The LLM's first answer had small errors (a pattern, a length, a null where none is allowed, a runaway string, a value breaking a `uuid`, `date-time`, `date`, `time`, `email`, `uri`, `ipv4`, `ipv6` or `hostname` format) that were fixed locally, without a second LLM call. A value the request sent (a path id or query value) is never patched over a format; other formats are annotations. A patch keeps what fits of the LLM's value, and a replaced identifier also changes where the answer repeats it as a whole token. |
| `repaired` | The LLM's answer was invalid and was fixed by one repair call: the validation errors went back to the LLM, and its second answer validated (perhaps after a local patch). |
| `fallback` | The built-in faker generated the answer, because there is no LLM (`--offline`), or the LLM timed out, failed or never produced a valid answer. `X-Mockingbird-Fallback-Reason` says which. An offline answer without a body (a `204`) is `fallback` too. |
| `rejected` | The request failed validation and was answered with the contract's error shape (or problem+json), without the LLM. `X-Mockingbird-Validation` says why. A client error, so `verify --no-fallbacks` does not count it. |

Every answer, whatever its source, matches the contract, with one known gap: the faker does not generate for `not` or `if`/`then`/`else` and relies on retries for them, and when no retry validates, the fallback reason ends with `faker output does not validate against the schema` (counted by `mb_faker_invalid_total`). `--offline` serves faker answers only, which needs no key and no network: the usual choice for CI.

## Sessions and state

State is kept per **session**, named by the `X-Mockingbird-Session` header (or `default`). Writes (creates, updates, deletes) change the session's state, so a `POST /orders` followed by `GET /orders/{id}` returns the order you created, and a deleted resource is gone. An action route such as `POST /payment_intents/{intent}/confirm` acts on the resource its path names: an answer shaped like that resource's `GET` replaces it, unless the LLM gave it an identity of its own, when it is [a new record](import.md#an-update-that-answers-another-record); any other answer leaves it stored as it was. Whether a `POST` is an action comes from the contract's structure, and an operation can correct it ([how it is read](import.md#how-a-post-under-a-resource-is-read)). A write's LLM answer may also list what it changes in the other stored resources it was shown, so a cancellation shows on the booking and a refund on its charge: Mockingbird merges each change into the resource it names in that session, after checking that the resource exists, that the change leaves its `id`, `number` and identity field alone and that the result still matches the schema of the resource's read (a type with no read has none, and takes no change). A change that fails a check is dropped and counted (`mb_effects_total{mock,outcome}`) and the answer is served anyway; a change can never create or delete a resource. An applied change sends `<resource>.updated` to matching [webhook](webhooks.md) targets. Lists seed the session too: the items of a list answer can be read back by id. Answers seed what they mention as well: an object in a 2xx answer with an `id` or `number` is stored when its `$ref` or member name gives it a resource type (`customer` for `customers`) and it would be valid as that type's `GET` answer or list item, or is a shorter form that `GET`'s schema is composed of with `allOf` (a search's `FlightOffer`, of an `Offer`: the `GET` is generated knowing it, keeps what it holds, and its answer takes its place), down to depth 6 and at most 100 per answer, so an order's `customer` reads back from `GET /customers/{id}` and a search's repository from `GET /repos/{owner}/{repo}`, found by its `name`, `login`, `slug` or `key` when the route's last parameter names no field (a stored `full_name` must end with `{owner}/{repo}`); a generated call on a route below it, such as `POST /repos/{owner}/{repo}/issues`, is shown that resource too, so its answer can change it. A generated read by id is stored too, so its first answer stands however later answers mention it. What the session already holds is never overwritten this way, and neither a faker answer standing in for a failed LLM call nor a delete's answer seeds anything. Reads are `GET`s, and `POST`s whose last path segment is a read verb in RPC style (`/accounts/get`, `/transactions/sync`, `/institutions/get_by_id`, `users.list`, `_search`), so Plaid's reads are cached and seeded too, and a read's answer is generated knowing the lists other reads stored under its list members' names (`/auth/get` knows the `accounts` `/accounts/get` answered). GraphQL answers store every object with an `id` under its type (`Cart` as `cart`): a mutation's are merged into what the session holds, a query's added when new, so `cartCreate` → `cart(id:)` → `cartLinesAdd` → `cart(id:)` reads and updates one cart, and a mutation is generated knowing what its `<x>Id` arguments and `gid://…/<Type>/…` ids name. `unknown_ids: 404` makes reads of ids the session never saw answer 404, as the real API would.

A write's request is kept for what its answer did not say. After a 2xx write on an HTTP route, with an LLM and consistency on, an update answering nothing merges the members its read's schema declares (those of an `additionalProperties` map too) into the stored copy, when the result still validates, so `PUT /pets/p1 {"name":"new"}` (204) reads back at once from `state`, and an unheld `PUT` with a whole valid body is stored as it came. A merge leaves the members that identify the resource and `readOnly` members as they are, does not reach into an object under a `oneOf` or `anyOf`, and takes no member saying the resource is another owner's than its path names, which is not remembered either. What could not be applied is remembered, as the route template, the operation and the scrubbed body, including a `null` the schema does not allow, unless all that is left was redacted, which a catch-up could not show. So is a create whose answer is shorter than its read and does not show what the request said (Jira's `id`, `key`, `self`), and an action that does not show on its target (a transition's 204). A member counts as shown only when the stored copy has the same value at the same path. A create, or an action answering nothing, also tells the nearest parent its path names and the session holds: `POST /captures/{id}/refund` makes a refund and tells the capture nothing. Updating or deleting a child does not tell its parent. A remembered action publishes a change of its target, for replicas, feeds and triggers; telling a parent changes nothing it holds, so it publishes nothing.

The next generation for that resource is shown those requests, oldest first, in an `<earlier_requests>` block, and a read that could otherwise answer `state`, with or without a query, generates instead. Its validated answer replaces the stored copy and the requests are done, so the next read is `state` again, and one extra LLM call catches up however many writes are waiting. In that answer the stored copy fills what it left out at any depth, but not across a `oneOf` or `anyOf`, where the branch it took stands, and what the latest write said of the resource itself stands over what it wrote, when that write was an update or a create. Last write wins: a later update puts its own in place, an action or a child's create ends it, and older bodies, like a child's or an action's, are only told, as their members may share names with the resource's and mean something else or be out of date. An own body over 4 KiB is not kept at all. Identity and path fields are kept. Anything else it may rewrite. A catch-up that changes nothing publishes nothing. Nothing is remembered when the resource already shows the write: a create answering its read's own schema or showing what the request said, an update answering its read's schema (which also settles what was waiting), a change an answer's effect applied. A shorter update answer is taken as a create's and settles nothing. A delete drops its target's requests.

When a catch-up fails (the LLM is down, it never answers validly, or its answer stops showing the resource's owner), a stored copy that can be served answers (`state`), else the faker does (`fallback`) as ever; the faker never invents the change. After 2 failed attempts, each up to two LLM calls, reads stop trying until a later write adds a request, and the requests stay; the request record says so under `request.effects`, and it is logged. Two reads at once can each generate, and two writes to one resource at once can lose a request: the memory is read and written back without a lock, as an effect's merge is. A list or a read through a scenario or a named seed forces nothing and settles nothing; a generation of the resource itself is shown the requests. A read whose whole answer is a top-level `oneOf` has no identity, so it is never told; what is kept for it stays within the caps until the session ends.

A resource keeps its newest 5 requests, at most 16 KiB (a body over 4 KiB is cut). Before anything is kept, what the request or read schema marks `writeOnly` or `format: password` and the mock's own credential names are redacted. In a record's own body, a member the read schema otherwise declares is one the API returns, so a credential word in its name hides it (`client_secret`, `password_hash`), while `session`, `auth` and `pin` do so only as its last word (`session_title` stays). Everything else, an action's body and what a child tells its parent included, goes by any name holding one, as the last resort since no list of names is complete (also `{"name": "Authorization", "value": ...}` pairs). Then come the request log's `redact_fields` and the [PII scrubber](configuration.md); a path's values are not kept, as a path may hold the secret. It lives in the session's state store under a type a contract cannot name, and goes with the session (TTL, reset, seed), but it is no resource: not exported, counted or listed, and on no change feed. GraphQL, gRPC and SOAP are not remembered for, and an `--offline` mock has nothing to tell, so both answer as they did.

Sessions can be exported as fixtures, seeded from fixtures and reset ([CLI](cli.md), [Admin API](admin-api.md)), which is how tests start from a known state. State lives in memory, in the storage database, or in Redis (`storage.state_url`), so several replicas share it.

## Personas, overrides and chaos

- A **persona** is free text added to every prompt of a mock: locale, realism, style ("Terse, realistic retail data in en-GB").
- **Override headers** change one request: `X-Mockingbird-Status`, `X-Mockingbird-Latency`, `X-Mockingbird-Scenario`, `X-Mockingbird-Session`, `X-Mockingbird-Seed` (an integer seeding this request's faker values, see [`faker_seed`](configuration.md)) and `X-Mockingbird-Chaos: off`. The [protocols](protocols.md#override-mapping-per-protocol) page shows how each maps onto GraphQL, gRPC and SOAP.
- **Chaos** injects errors in the contract's own error shape, latency jitter and dropped streams, per mock or per scenario ([configuration](configuration.md#mocksnamechaos)).
- **Webhooks** POST signed events after writes, the way Stripe or GitHub would ([Webhooks](webhooks.md)).

## Scenarios

A scenario is a named set of overrides for a mock: extra LLM instructions, a forced status, added latency, fields forced into the body (`set`), the item count and pacing of streamed responses (`stream_items`, `stream_item_interval`), optionally limited to some operation ids. Select one per request:

```sh
curl -i localhost:8080/orders/orders/o1 -H 'X-Mockingbird-Scenario: out-of-stock'
```

A scenario's status applies only to operations whose contract declares that status (or a `default` response), where its `set` fields are forced into that response's body too; a 5xx also applies to operations that do not declare it and is answered natively, as with `X-Mockingbird-Status`. Other operations are served normally, with the scenario's other overrides. The Admin API rejects (`422 Scenario status not declared`), and a config file may not declare, a non-5xx status that none of the scenario's operations declares in the mock's active contract, since it could never take effect. An unknown scenario name is a 400. Scenarios come from the config file or from `PUT /api/v1/mocks/{mock}/scenarios/{name}`.

A mock's `default_scenario` applies when a request names none, so clients that cannot send headers still get it. A scenario's `operations` entries may be `{id, instructions}` to give one operation its own instructions in place of the scenario's.
