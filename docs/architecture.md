# Architecture

Mockingbird turns an API contract into a running mock. Each call is decoded against the contract, answered by an LLM within the contract's response schema, validated, repaired once if needed, and replaced by a schema faker when generation fails or is refused. This page describes how the pieces fit together and how a multi-node deployment stays consistent.

## Crates and boundaries

The library crates live in `crates/mb-*` and are named `mb_*` in code; on crates.io they are published as `mockingbird-<name>` (`mb-engine` → `mockingbird-engine`) for `mockingbird-cli`, with no API stability guarantee. `mb-ext` is the exception: the public extension API, published under its own name and semver.

| Crate | Role |
| --- | --- |
| `mb-mcm` | The Mockingbird Contract Model: operations, channels, per-operation JSON Schemas. No internal dependencies; every other crate exchanges MCM types. |
| `mb-import` | Deterministic compilers (OpenAPI 3, Swagger 2, GraphQL, protobuf, AsyncAPI, WSDL) and the LLM-assisted draft importers (documentation, HAR, Postman). Runs on the control plane only. |
| `mb-llm` | The provider trait and the OpenAI-compatible client (structured output, streaming, outbound CA/proxy). |
| `mb-engine` | Prompt building, generation, validate → repair → fallback, the schema faker, the PII scrubber and the engine guards. No protocol or transport knowledge, and no `axum`. |
| `mb-state` | Session state stores (memory, SQLite, Postgres, Redis), the cross-node bus and leader election. No `axum`. |
| `mb-store` | The control-plane store (SQLite, Postgres) and its migrations. No `axum`. |
| `mb-protocols` | Protocol adapters behind Cargo features: REST, GraphQL, gRPC, SOAP, SSE, WebSocket, Kafka, AMQP, MQTT. Admission limits and chaos. Depends on neither `mb-store` nor `mb-auth`. |
| `mb-ext` | The extension contract (tenancy, quota, usage, secrets, provider policy, admin hooks) with self-hosted defaults. Semver-stable from 1.0; see [its README](../crates/mb-ext/README.md). |
| `mb-auth` | OIDC relying party, RBAC and API keys. |
| `mb-admin` | The Admin REST API (OpenAPI-described) and the audit log. |
| `mb-console` | The embedded React console. |
| `mb-evals` | Weekly LLM evals and the offline throughput bench (not published). |
| `mockingbird` | The binary: CLI, configuration, role wiring, HA bridge, budget, TLS. |

Protocol adapters contain no generation logic: they decode traffic into an operation call and encode the generated response (or stream items) back onto the wire. Data-plane processes load compiled MCM bundles from the control-plane store and never parse source contracts on the request path.

## Roles

A node runs one role (`server.role`, `MB_ROLE` or `--role`):

| | `all` | `control` | `data` |
| --- | --- | --- | --- |
| Data listener and gRPC listener | yes | not bound | yes |
| Admin port | Admin API, console, ops | Admin API, console, ops | ops only (`/healthz`, `/readyz`, `/metrics`) |
| Reconcile, `--watch` | leader only | leader only | never; `--watch` is a usage error |
| Maintenance (session expiry, audit and token-usage retention) | leader only | leader only | no |
| Smart import workers | yes | yes | no |
| Mock runtimes | full | built for manual publish only; channel runtimes start no consumers, triggers or WebSocket routes | full |

`all` is the default and needs nothing shared: SQLite and in-memory state work. `control` and `data` share their stores with other nodes, so they need a Postgres control store and a Postgres or Redis state store; startup refuses SQLite or `memory`.

A data node's Admin port authenticates with API keys only (it needs no OIDC discovery). Manual publish on a WebSocket channel from a control node answers 409, since WebSocket channels are served by data nodes.

A typical HA layout is two `control` replicas (one leader at a time) and an autoscaled set of `data` replicas behind a load balancer, sharing Postgres and, optionally, Redis.

## Request flow

1. **Decode.** The adapter matches the call to an operation and validates its input. Invalid input gets the contract's declared 4xx or error shape, naming the violated field and the reasons; an open code member in it is written once per operation and status by the LLM, else by the faker.
2. **Admission** (`mb.admission` span): the request size cap (`limits.max_request_bytes`, or the mock's own; 413, recorded), data-plane auth, the `mb-ext` tenant resolver and quota guard, then the mock's rate limit (429 with `Retry-After`, `mb_rate_limited_total`).
3. **Plan and chaos.** Override headers and the active scenario are applied. When the mock (or the active scenario) has chaos and the call does not carry `X-Mockingbird-Chaos: off` with header overrides enabled: latency jitter is added, and with probability `error_rate` the call is answered with an injected error in the contract's error shape (or the protocol's native error), marked `X-Mockingbird-Chaos: error`. Counted in `mb_chaos_injected_total{mock,kind}`.
4. **State lookup** (`mb.state`). The session (`X-Mockingbird-Session`, cookie or gRPC metadata; `default` otherwise) and related resources. When the state store fails, the mock serves statelessly and `/readyz` reports `degraded`. Then the **executor** (`crates/mb-protocols/src/call/exec.rs`) takes the operations the effective [world description](world.md) classifies (with `consistency` on, no scenario, forced status or seed, a type with an identity and, but for a create or a list, a target the request names): the store decides the answer and the stored record is rendered into the response schema, tagged `state`, with no LLM call but a create's or a replace's fill. A read of one record by its path (its type's read by id) is that record whatever its query: the first such read stores its answer under the path's id, and later ones are answered from it. Its query only selects how the record is shown, each parameter by what the contract says of it: one selecting a language (its name, `format`, language-tag `enum` or description says so) answers that language's variant of the record, generated once from it with its facts kept; one embedding sub-resources (`append_to_response`, `expand`: an `enum` or description naming optional object members of the answer, or a name or description saying it appends, expands or embeds) has them generated once over the record and kept with it, and leaves them out of reads that do not ask (`embed_missing` while the record lacks them), as it leaves out a part the contract returns only when asked for (a description saying it is not included by default, or an optional paged list its record schema names in `x-expandableFields`, Stripe's Checkout `line_items`). A reference member it names (a choice of an id string and an object of a type, Stripe's `customer`, or a string member named `<t>` or `<t>_id` whose value names a held record) is answered as the record the session holds under that id, shaped to its type's schema, dotted paths (`latest_invoice.payment_intent`) expanding each step, while the stored record keeps the id; one naming a record the session does not hold (nor deleted) is generated once (`reference_unheld`), else drawn by the faker, and stored under that id, and an object the record holds in a reference the read does not ask for is answered as its id (`crates/mb-protocols/src/call/expansions.rs`); any other is applied as a projection where one is described (a fields parameter) and is otherwise ignored. Each such call is logged at `info` with `exec` (its kind), and with `exec_fallback` (`not_held`, `behind`, `render_failed`, `record_invalid`, `consistency_off`, `never_written`, `scope_unresolved`, `undescribed_param`, `embed_missing`, `reference_unheld`...) when it goes on to generation, and with `exec_fallback_on`, the query parameter or body member that caused it, where one did (`undescribed_param`, `undeclared_member`, `read_only_member`); a read's `render_failed` also carries `render_error`, why the record did not render (the rendered answer's first schema violation, `<pointer> <keyword>` such as `/taxes required`, or `envelope member unfilled`), and so do a create's `render_failed` and `record_invalid`, on the log line and the request record: a created record one of its type's reads would not render is never stored, and the create generates. A read renders its record in the envelope the operation answers it in, the envelope's other required members taken from what the session's answers said, else what their schema fixes, else `true` for a boolean (the answer is a success) and a seeded faker value for any other. A held record lacking members the read's record schema requires (one another mock of its `shares` group stored in its own shape: a GraphQL-created pull request read over REST) is completed rather than generated whole (`crates/mb-protocols/src/call/exec/held_gaps.rs`): a member that may be `null` is `null`, any other is written as a create's fill writes it (the model asked for missing free text alone), its stored values kept, and the completed record is stored by a compare and set when the session holds it under the read's own type and key; another mock's record is left as its writer stored it, its completion kept beside it (reserved type) with the record as read, so later reads answer alike until the writer changes it, when only what it still lacks is filled anew. It is tried only when what keeps the record from rendering is members it lacks (`required`), not a stored value of another type. An executor answer is final: a write it decides is stored with only a write's side effects (the store and its change feed, webhooks, the idempotency replay, the response cache), never reconciled as a generated answer is. An acknowledgement a create, update, replace, delete or action renders from its record, whose stored members break the answer's schema, has only those members re-drawn from the schema (`crates/mb-protocols/src/call/exec/redraw.rs`), what names the record and the other values kept; when what names the record breaks it, or no repair validates, it falls back to the faker's answer with the record's identity, else the faker's own, with a fallback reason. Each is noted as `answer_repair` on the request record and counted by `mb_answer_repairs_total{mock,operation,outcome}`. Creates, reads, lists, deletes, updates, replaces and described actions are executed today (a create stores the request's record under the id the request asks for or one it mints, in its lifecycle's initial state, and answers the record or an acknowledgement rendered from it; a delete removes the record, or moves it to its soft-deleted state, and answers its declared delete answer; an update merges the record its request holds into the held one, a replace stores it whole, both keeping its identity and read-only members and minting its described or `If-Match` token; an action whose description has a `transition` or `changes` sets them on the record and answers it, or its own acknowledgement schema with the record's values, else `exec_fallback=undescribed`). Their one LLM call is `Engine::fill` (`crates/mb-engine/src/fill.rs`), at a create or a replace: values for what the type's reads require that the request does not give (a member, or what an object member it sent lacks), so that every later read renders from state, and at a create every other member the reads declare that nothing set, optional ones too, but the server's own members (id, lifecycle state, derived members, the concurrency token, which is minted), `writeOnly` members and references to other records the request could have sent; reads (but one completing a held record, above), lists, updates, deletes and actions make none. Before fill, a create's request reference where the reads hold the record (Buildkite's `pipeline` slug) is replaced by the record the session holds under it, projected to the member's schema, else left for fill; schema defaults are set; and array items declaring the type's id get minted ids. Any other call generates as below.
5. **Prompt** (`mb.prompt`) and **generate** (`mb.llm`), inside the engine guards:
   - the global generation semaphore (`limits.max_concurrent_generations`, `mb_generation_in_flight`); a call that waits longer than its LLM timeout falls back (`mb_generation_queue_timeouts_total`);
   - the mock's daily token budget (`mb_token_budget_used`, `mb_token_budget_exhausted_total`), shared across replicas through the `token_usage` table and flushed every 5 s (the leader deletes rows older than 90 days, daily);
   - the response size cap (`limits.max_response_bytes`).
   A refused guard never errors: the faker answers.
   A 2xx answer to a command with a stored target or related resources is asked for as `{"effects": [{"type", "id", "set"}], "response": <the answer>}`, effects first and both required, in the prompt and, under `output_mode: json_schema`, in the response format (this replaces the `{"items": [...]}` wrapping of an array answer, and is left out when the answer itself has a `response` or `effects` member). A plain answer is accepted as it is. Only the answer is validated, patched and repaired; the effects, at most 10, get the PII scrubber and count towards the size cap, where one that does not fit is dropped and the answer kept. Malformed, surplus and oversized effects, and all those of an answer the provider cut at `max_tokens`, count as `rejected`.
6. **Validate → repair → fallback** (`mb.validate`, `mb.repair`). Values breaking a format the faker produces are refilled locally (never sent for repair), and errors a local fix can solve are patched, also inside an `anyOf` or `oneOf` branch whose `const` and `enum` members already hold. One repair call with the validation errors; then the faker, whose answer is flagged in its fallback reason (and `mb_faker_invalid_total`) when no draw validates. The response carries `X-Mockingbird-Source: llm | patched | repaired | fallback`.
7. **Scrub.** With `pii.enabled`, personal-data look-alikes are replaced with synthetic values of the same shape (`mb_pii_replacements_total{pattern}`). Scrubbed output still validates.
8. **State write and encode** (`mb.encode`). Commands upsert or delete the resource and publish a state change, then apply the answer's effects (`mb_effects_total{mock,outcome}`; each is checked and upserted like a write, sends `<resource>.updated` to matching webhook targets, and is kept in the request record's `request.effects` with its outcome; none under `consistency: off`). An HTTP update answering nothing merges its declared members into the stored copy. A write whose answer did not show its request remembers what is left for its resource, and a create or a body-less action for the parent its path names (which is told only, and publishes nothing; an executed delete tells nothing); an action publishes a change of its target; the resource's next generation is shown it and a read generates to catch up, replaces the stored copy and forgets it, giving up after 2 failed attempts until a later write ([write memory](concepts.md#sessions-and-state); `crates/mb-protocols/src/call/write_memory.rs`). The memory is read and written back without a lock, so two writes at once can lose a request. The adapter encodes the response. Streams (`drop_stream_rate`) may be cut short by chaos.

A request failing validation never reaches the LLM: it is answered with the contract's 400, 422 or `default` error shape (else problem+json), with source `rejected`, whose message-like field, the `X-Mockingbird-Validation` header and the request record's `request.validation` carry the reasons. A member the schema does not declare, in the body or nested in a query parameter, is not a failure unless the mock sets `strict_requests` ([configuration](configuration.md)). Form and multipart bodies and query strings are decoded with bracket notation (`a[b][c]=1`, `a[0]=x`, `a[]=y`) and coerced through the schema before validation.

Every call is recorded in the request log (redacted) and counted in `mb_requests_total{mock,operation,status,source}`. Its `source` is `llm`, `patched`, `repaired`, `fallback`, `state`, `cache`, `example` (the declared example of a non-JSON response, or the value its schema fixes) or `rejected` (a request that failed validation; as in `X-Mockingbird-Source`), or `not_generated` for a call answered without generating a body: refused before generation (auth, quota, rate limit, an invalid override, an unknown scenario) or answered with a native error (a forced or injected error status the contract declares no response for).

## High availability

### The bus

Nodes tell each other what changed over a bus (`bus.url`): Postgres `LISTEN/NOTIFY` on channel `mockingbird_bus`, Redis pub/sub on channel `mockingbird:bus`, or in-process for one node. Payloads are a JSON `BusEnvelope { origin, event }` that carries ids only; receivers reload from the stores. Events:

| Event | Sent when | Receivers |
| --- | --- | --- |
| `Mock { workspace, name }` | a mock, its contract, scenarios, chaos or limits change | rebuild that mock's runtime |
| `Profile { workspace, name }` | an LLM profile changes | rebuild the mocks that use it |
| `Workspace { name }` | a workspace changes | reload its mocks |
| `State { workspace, mock, session, resource_type, id, deleted }` | a session resource changes | fire `on_state_change` triggers and SSE/subscription updates |
| `RequestLogged { id }` | a call is recorded | the live tail looks the entry up by id |
| `Resync` | locally after a reconnect and every 5 minutes (±25 %) as a safety net; to the other nodes once the bus works again after a failed publish; instead of an event larger than 7900 bytes | reload every mock |

A connection that goes half-open (a partition, or conntrack or a load balancer dropping an idle flow) never reports an error by itself, so each node heartbeats its subscriber connection every 10 s (`SELECT 1` on the Postgres listener, `PING` on the Redis pub/sub connection) and treats a heartbeat that fails or takes over 5 s as a lost connection. A disconnected bus reconnects with a backoff from 1 s doubling to 30 s, and `/readyz` reports `degraded` with `bus: <error>` meanwhile. Because every reconnect emits `Resync`, a node never keeps serving a deleted mock for longer than one heartbeat timeout plus one reconnect cycle. `mb_bus_connected` and `mb_bus_events_total{direction,type}` expose the bus.

### Leader election

Work that must run once per cluster is leader-gated: the startup reconcile of `mockingbird.yaml`, `--watch`, and maintenance (session expiry, audit and token-usage retention). The leader holds the lock `control`:

- with Postgres, a session advisory lock whose key is the first 8 bytes (big-endian `i64`) of sha256(`"mockingbird:control"`);
- with Redis, the key `mockingbird:leader:control`, a lease of 15 s renewed every 5 s;
- with an in-process bus, the node always leads.

A node that loses its connection stops leader work within 5 s, and another takes over within 15 s. `mb_leader` is 1 on the leader, and `/readyz` shows `"role"`, `"leader"`, the `"config"` file and working `"dir"` the node was started with (which a project's MCP server checks to act only on its own project's server, see [agents.md](agents.md)), its `"proxy"` address (`null` without one; `run` and `proxy env` check it to hand out only the project's own proxy, see [proxy.md](proxy.md#whose-proxy)) and, on a node that serves mocks, its `"data_plane"` (`port`, `tls`), which the MCP server's `call_mock` uses to find the data plane of the Admin API it talks to.

With Postgres, leadership can briefly overlap. The lock is released the moment the holder's session ends on the server (a terminated backend, a server restart, a dropped connection), so another node may acquire it at once, while the old holder only notices at its next renew (a `SELECT 1` every 5 s, itself timing out after 5 s). For up to one renew interval, and up to 10 s when the connection hangs rather than fails, both nodes may run leader work. Reconcile writes the same desired state from either node and the retention jobs are idempotent deletes, so an overlap costs duplicate work and, at worst, a logged conflict.

The bus and the leader lock need a session-level Postgres connection: a pooler in transaction mode (PgBouncer `pool_mode = transaction`, and statement mode) is unsupported for them, because `LISTEN/NOTIFY` and session advisory locks do not survive a connection being handed to another client between transactions. Point `bus.url` (or, without one, `storage.url`) at Postgres directly or through a session-mode pooler, or use Redis for the bus.

### Bus capacity and resync

Each node fans bus traffic out through in-process broadcast channels of 1024 events. Besides the control events (a mock, profile or workspace changed), the same channels carry the per-request traffic: state changes for subscriptions and change feeds, and request-log notices for the console's live view. A busy data plane can therefore fill them; a receiver that falls behind skips the missed events and, rather than guess what it lost, triggers a full local `Resync`.

Every `Resync`, whether from lag, a reconnect, the networked bus's safety resync (about every 5 minutes) or another node's request, rebuilds every mounted mock from the control store. Rebuilding a mock resets its in-memory rate-limit buckets (callers briefly get a full burst again) and restarts its event channels: their triggers and consumers start over, and WebSocket channel subscribers are disconnected and must reconnect. GraphQL subscriptions and SSE streams already open stay on the previous build of the mock (its contract and settings at the time) until the client reconnects. `mb_bus_events_total{type="resync"}` counts them; a steady rate means the node is lagging and should be scaled out.

### Per-mock scheduler lease

Channel triggers (`every`, `cron`, `on_state_change`) run on data-plane nodes, so each mock's scheduler is guarded by its own lease in the `scheduler_leases` table (30 s): only the holder fires, and another node takes over when it expires. Consumers share the work through broker features instead: one Kafka consumer group and one AMQP queue per mock, and MQTT shared subscriptions (`$share/<client_id_prefix>/<topic>`) when the bus is shared.

## State backends

| Profile | Control store | Session state | Bus |
| --- | --- | --- | --- |
| Local | SQLite (file or memory) | SQLite or memory | In-process |
| HA | Postgres | Postgres or Redis | Postgres `LISTEN/NOTIFY` or Redis pub/sub |

Session state is keyed by workspace, mock, session, resource type and id, and expires `storage.session_ttl` after its last write. A record whose routes address it only under parent path parameters, by a key the contract does not mark unique on its own (GitHub's issue `number` under `/repos/{owner}/{repo}`, a secret's name), is kept under its parent too: its id is stored as the parent's values and its own id joined by U+001F (`a␟x␟2847391056` in an export, shown here with ␟), so two repositories' issue `#5` are two records, lists and reads under a parent see that parent's, and a minted number counts within the parent (`mb-protocols` `call::scopes`). Records stored under their own id alone (seeded, or written before) still answer under any parent whose path their own links do not contradict; a write under a parent moves such a record there, and a delete there removes it. A list under a parent reads only the ids under its prefix (`StateStore::list_prefix`: an ordered id range in memory and SQL, a server-side prefix match in Redis) once a per-session marker says the type holds no record stored under no parent. A state-change trigger of such a record keeps its own `id` and names its `parent`, and an SSE feed under a parent sends that parent's records; a GraphQL delete by `id` removes the shared REST record a GraphQL read of that id finds, and leaves the deleted markers a REST delete under its parent would, so neither mock generates it back. The write memory and the earlier answers use the same table or keys under a reserved type (`mb_state::INTERNAL_TYPE`), so it needs no migration and shares the session's lifetime; every backend leaves that type out of exports, counts, seeds and change events. `mb_state_sessions{mock}` counts live sessions on every data-serving node.

Each node also keeps a per-session response cache in memory (500 answers per session, least recently used first out), so a session repeating a read gets the same answer (`X-Mockingbird-Source: cache`). A write of a resource type, from this node or relayed over the bus, drops that type's answers; a session reset or seed drops the session's, and a mock reset every session's of that mock, on every node (the node that made it announces it on the bus); an idle session's answers expire with `storage.session_ttl`. Mocks with `consistency: off` bypass the cache.

The Redis state store needs `maxmemory-policy noeviction`: evicting a key would silently lose a session's resources. It uses multi-key transactions without hash tags, so Redis Cluster is not supported; use a single primary.

Migrations run at startup under an advisory lock, for SQLite and Postgres alike. See [upgrading](upgrading.md) for the migration history.
