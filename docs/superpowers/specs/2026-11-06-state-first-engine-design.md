# State-first engine

**Status:** approved direction (2026-11-06). This spec fixes the shape; the plan is at the end.

## Problem

Today every call is generated by the LLM, and the engine then reconciles the answer with the store. That means:
- effects are inferred from the answer;
- write memory re-asks the model until it catches up with earlier writes;
- forced ids, list repairs and repeat detection patch the result.

`complete()` alone is ~780 lines of this. The model decides ids, list contents, filter matches and error cases, so correctness depends on the model. Weak models fail and every fix is a special case.

On blind13, 91% of failed checks were engine bugs or missing engine features, and 1% were model misses.

## Design

For a resource operation, the **store decides the answer**:
- the engine executes the operation against the store;
- it renders the stored record into the response schema;
- the LLM only supplies **values** for record members nobody else determines.

Everything the executor can't classify takes today's path unchanged.

### 1. When the executor runs

In `call::prepare`, before generation, the effective world gives the operation's `kind`, `type`, `target` and the type's `identity`. The executor handles a call when all of these hold:
- the kind is `create`, `read`, `list`, `update`, `replace`, `delete`, or an `action` with described `transition`/`changes`;
- the type has an identity;
- a target-taking op resolves its target;
- `consistency` is on;
- no forced status, scenario or chaos applies to the call (those keep today's path).

Otherwise it returns `None` and the call is generated as today.

No new config key, no flag. The world description already says enough. Where it doesn't, the call falls back.

### 2. Executors (one function per kind, in a new `call/exec.rs`)

| Kind | Store action | Answer |
|---|---|---|
| read | Get the target. Missing: the `unknown_ids` rule (not_found → declared 404 via `nothing_held`; generate → fall back). | The record rendered. |
| create | The record is the request body's record (via `request.record`, else the body). The id is minted by the identity rule (existing minted/pattern code). The lifecycle `initial` is set. Unique and concurrency checks are the existing ones. Missing members come from **fill** (§3). Store. | The record rendered, with the identity header/Location as today. |
| update | Merge the body into the held record (JSON merge semantics; `request.format` patch kinds when described). Check against the record schema; a change that adds a violation is refused (#349 rule). Store. | The record rendered, or the declared bodiless status. |
| replace | The body replaces the record, keeping its id and server-owned members. Missing required members come from fill. | Same as update. |
| delete | Remove (or soft-delete per the world). | The declared delete answer (bodiless, `{}`, or the record). |
| list | Records of the type in the session, then scope (`parent` / `where`), described `filters`, `sort`, then page with the existing `pages` tokens/links. An undescribed non-paging query param falls back to generation, marked `undescribed_param`. | The items rendered into the list envelope. |
| action | Apply `transition`/`changes` to the held target; preconditions are the existing refusals. | The target rendered (or `answer.record` location). |

Refusals (404, 409 unique/stale, 422 precondition) use the existing `refuse_held` / `nothing_held` path. Error bodies stay as they are.

### 3. Fill: the only LLM call on the executor path

`Engine::fill(type schema, known: Map, missing: [members], context) -> Map`. It is one structured-output call whose schema is the record schema restricted to the missing members, with the known members in the prompt for coherence. Rules:
- The output is validated, and an invalid or refused member falls back to the faker (existing).
- It is only for creates and replaces. Reads, lists, updates, deletes and actions make **no** LLM call.
- Server-owned members are deterministic, not filled:
  - the id;
  - lifecycle state;
  - `stamps` (if and when they exist);
  - members whose value the world derives.
- Members the request sent are never filled.

With `fake_llm` or the faker the executor still produces correct state behaviour. That's the point, and it makes the fake-LLM bench a faithful free preview.

### 4. Rendering

Reuse `Engine::held_answer` / `serve_stored`: the record goes to the answer, using `identity.record` (`RecordAt`) for envelopes, and the list item array via the existing envelope code. Answer members outside the record (envelope metadata such as `request_id`) come from the faker, deterministically per `faker_seed`. They're not checked by journeys, and no LLM is needed.

If the rendered answer doesn't validate against the response schema, the call falls back to generation, marked `render_failed`. Each such mark is a renderer bug to fix, never a reason to patch the answer.

### 5. What happens to the reconciliation code

Nothing is deleted up front. Once every executor has landed and the fake-LLM bench shows which fallback paths are still taken, a final cleanup PR deletes code that's only reachable for calls the executor now handles. Expect most of `write_memory`, effects for described actions, and the `complete()` repairs for creates and lists to go. Each deletion is justified by a fallback-rate count, not by guesswork.

### 6. Measuring (free)

Run `server_suites.py` against `fake_llm.py` with the committed world cache. Per suite, report:
- the pass rate;
- the executor coverage (the share of calls with source `state`/`exec` vs generated);
- the fallback reasons.

Checks that only a real model can pass, like realistic text, are listed separately as `model-dependent`.

Every PR reports its delta against the baseline taken before step 1. The single paid run happens only when the fake-LLM pass rate, plus the model-dependent checks known to pass, projects ≥92% on every suite.

### Non-goals

- No new crate.
- No new public config.
- No metrics, dashboards or tracing work.
- No protocol-specific executors: the executor sits in the shared `call` module, so GraphQL, gRPC and SOAP get it through the same operation model.
- No world-format v2 work until the executor shows what's missing.

## Plan

Each step is one PR under the AGENTS.md shipping rules, with fail-first tests.

0. **Baseline (bench only, no PR).** A fake-LLM run of all suites, world agent where cached and tier-0 elsewhere. Record the pass rate, coverage and fallback reasons per suite in bench-results.
1. **The executor seam plus read.** It handles held-record reads (most already go through `serve_held`) and adds the `exec` source mark plus a fallback-reason log line. Tests: read of a held record, missing id under both `unknown_ids` settings, render failure falls back.
2. **Create plus fill.** Request body → record; id; initial state; unique checks; `Engine::fill`; store; render.
3. **Update, replace and delete.**
4. **List.** Scope, filters, sort, paging, and the `undescribed_param` fallback.
5. **Action.** Transitions and changes, plus preconditions.
6. **Cleanup.** Delete the code paths the bench shows are now dead.

Steps 2–5 depend only on step 1 and touch separate executor functions, so they run in parallel worktrees once step 1 merges.
