# Mockingbird P1 Core Loop Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** `mockingbird serve orders.yaml` serves a stateful REST mock whose responses are LLM-generated per request, schema-valid, and backed by a deterministic faker when the LLM fails.

**Architecture:** A Cargo workspace of focused crates. `mb-import` compiles OpenAPI 3 and Swagger 2 into the Mockingbird Contract Model (`mb-mcm`). `mb-engine` turns an `OperationCall` into a validated response via `mb-llm` (OpenAI-compatible) with validate → repair → fallback. `mb-state` holds session-scoped resources. `mb-protocols` (feature `http-rest`) is an axum adapter. The `mockingbird` binary wires them behind a `serve` CLI.

**Tech Stack:** Rust 1.97 (edition 2024), tokio 1, axum 0.8, matchit 0.9, reqwest 0.13 (rustls), serde/serde_json, serde_yaml_ng 0.10, jsonschema 0.58, rand 0.10, async-trait, thiserror 2, clap 4, tracing + tracing-subscriber, dashmap 6, humantime 2, serde_urlencoded, sha2, chrono, uuid, anyhow (binary only); dev: wiremock 0.6, proptest 1, insta 1 (yaml, redactions), tower (util), assert_cmd, tempfile.

**Spec:** `docs/superpowers/specs/2026-10-14-mockingbird-platform-design.md` (P1 row of §16; §§4–7, 9, 10, 13 as they apply to REST).

## Global Constraints

- License: every crate `license = "MIT OR Apache-2.0"`, with `LICENSE-MIT` and `LICENSE-APACHE` at the repo root.
- Crate names exactly: `mb-mcm`, `mb-import`, `mb-llm`, `mb-engine`, `mb-state`, `mb-protocols`, `mockingbird` (binary). Do not create `mb-ext`, `mb-auth`, `mb-admin`, or `mb-console` in P1.
- `mb-mcm` has no internal dependencies. `mb-engine` must not depend on axum, http, or `mb-protocols`.
- All schemas inside MCM are JSON Schema 2020-12. Component refs are rewritten to `#/$defs/<Name>`.
- Response source tag header: `X-Mockingbird-Source: llm | repaired | fallback`.
- Override headers in P1: `X-Mockingbird-Status`, `X-Mockingbird-Latency`, `X-Mockingbird-Session`. Default session id: `default`. Scenarios are P2.
- LLM env: `MB_LLM_BASE_URL` (default `https://api.deepseek.com`), `MB_LLM_MODEL` (default `deepseek-chat`), `MB_LLM_API_KEY`, `MB_LLM_JSON_SCHEMA` (`true|false`, default `false`; DeepSeek supports JSON mode, not JSON Schema mode).
- Default LLM timeout 3 s. Exactly one repair attempt.
- Default bind `127.0.0.1:8080`. A non-loopback `--host` requires `--insecure-no-auth` (P1 has no auth).
- Session TTL default 24 h.
- No `unwrap()`/`expect()` on request-path code. `cargo clippy --all-targets -- -D warnings` and `cargo fmt --check` must pass at every commit.

## Review Focus

1. **LLM output wrapped in Markdown fences or prose** (```` ```json … ``` ````, "Here is the response: {…}"). This is common with cheap models. The engine must extract the JSON object and still validate it. Test: Task 8 `extracts_json_from_fenced_output`.
2. **Recursive schemas** (`Category.parent: $ref Category`, tree nodes). The importer must not loop, and the faker must terminate with valid output. Tests: Task 3 `compiles_recursive_schema`, Task 5 `fakes_recursive_schema_within_depth`.
3. **Operations with no response body** (`204`, a `DELETE` with no content). These need no LLM call, an empty body, and a correct status. Tests: Task 8 `no_content_skips_llm`, Task 9 `delete_returns_204_and_removes_state`.
4. **Path variants**: a trailing slash, a query string, percent-encoded parameters, an unknown path. These must match the intended operation, and an unknown path must return a problem+json 404 rather than panic. Test: Task 9 `routes_trailing_slash_query_and_unknown`.
5. **Malformed or non-JSON request body on a JSON operation.** Return the contract's 400 (or a problem+json 400) without calling the LLM. Test: Task 9 `invalid_body_returns_400_without_llm`.

**Fixture `orders-3.0.yaml`.** The 3.1 file is the same contract written with 3.1 syntax (`type: [string, "null"]`). Required content:
- `info: {title: Orders API, version: 1.0.0}`
- `GET /orders`: `operationId: listOrders`, query `status` enum `[pending, shipped]`, 200 → array of `Order`.
- `POST /orders`: `operationId: createOrder`, body `NewOrder`, 201 → `Order`, 400 → `Error`.
- `GET /orders/{orderId}`: `operationId: getOrder`, 200 → `Order`, 404 → `Error`.
- `PUT /orders/{orderId}`: `operationId: updateOrder`, body `NewOrder`, 200 → `Order`.
- `DELETE /orders/{orderId}`: `operationId: deleteOrder`, 204 with no content.
- `components.schemas`:
  - `Order {id: string uuid, customerId: string, status: enum [pending, shipped], total: number ≥ 0, note: string nullable, category: $ref Category}`, required `[id, customerId, status, total]`
  - `NewOrder {customerId, total}` (both required)
  - `Category {name: string, parent: $ref Category}`, required `[name]`
  - `Error {code: integer, message: string}`, both required

Rules:
- `#/components/schemas/X` → `#/$defs/X`.
- For 3.0: `nullable: true` → `type: [T, "null"]`; strip `example`, `xml`, `discriminator`, `externalDocs`; `exclusiveMinimum: true` + `minimum: n` → `exclusiveMinimum: n`.
- Path-level and operation-level parameters merge, with the operation-level parameter winning on the same name+in.
- Path, query, and header params become an object schema each, with `required` taken from the params.
- Only `application/json` (or `*/*+json`) request and response bodies get schemas. Others keep `content_type` with `schema: None`.
- Kinds: GET/HEAD/OPTIONS → `Query`. POST → `Command(Create)` when the path ends in a static segment, else `Command(Other)`. PUT/PATCH → `Command(Update)`. DELETE → `Command(Delete)`.
- `resource_type`: the last static segment before any trailing `{param}`.
- `identity`: `path_param` = the trailing `{param}` if present; `field` = `"id"` if the success schema (resolved through `$defs`) has an `id` property, else the property whose name equals the path param, else `None`.
- Unresolvable `$ref` → `ImportError::Invalid` with that JSON pointer. Recursive refs are fine, because refs are rewritten, never inlined.

**Files:**

**Interfaces:**

```rust
// validate.rs
pub struct SchemaValidator { /* jsonschema::Validator, draft 2020-12 */ }
impl SchemaValidator {
    pub fn new(schema_with_defs: &Value) -> Result<Self, EngineError>;
    pub fn validate(&self, instance: &Value) -> Result<(), Vec<String>>; // "<instance path>: <message>", max 10
}
// faker.rs
pub struct Faker { max_depth: usize }               // default 6
impl Faker {
    pub fn new(max_depth: usize) -> Self;
    pub fn fake(&self, schema_with_defs: &Value, rng: &mut impl rand::Rng) -> Value;
}
// lib.rs
#[derive(thiserror::Error)] pub enum EngineError { #[error("invalid schema: {0}")] Schema(String), /* more in Task 8 */ }
```

Faker rules:
- Resolve `$ref` against the root's `$defs`.
- Honour `const`, then `enum`, then `type` (for a type array, prefer non-null).
- `allOf`: merge `properties` and `required`. `oneOf`/`anyOf`: pick the first branch.
- Strings: `format` `uuid`, `date-time`, `date`, `email`, `uri`; otherwise a word, padded or truncated to `minLength`/`maxLength`; `pattern` is ignored unless it is a fixed literal.
- Numbers: within `minimum`/`maximum`/`exclusive*`, rounded to a multiple of `multipleOf` when it is set.
- Arrays: length `max(minItems, 1)` capped by `maxItems`, honouring `uniqueItems`.
- Objects: all required properties, plus optional properties only while `depth < max_depth`.
- At `depth >= max_depth`: only required properties; arrays get `minItems` items; a schema whose type allows null yields `null`.
- `additionalProperties` is ignored (nothing extra is generated).

Handler flow (one `fallback` handler on the router):
1. **Route.** Strip one trailing `/` (except at root) and percent-decode params, then `find`.
   - No path match → 404 `problem("Not Found")`.
   - Path matches under another method → 405 with an `Allow` header.
2. **Decode** the query (`serde_urlencoded` → strings; coerce to number/boolean when the query schema property type says so) and the JSON body (a body is required when the op has an `input.body` schema and the method is POST/PUT/PATCH).
   - Validate the path/query/body against their schemas.
   - On failure: if the op has an error variant for 400 or 422 (`error_output(&[400, 422])`) with a schema, return `engine.fallback` for it. Otherwise return `problem(400, "Invalid request", errors joined)`.
   - Never call the LLM here.
3. **Overrides** (when `header_overrides`):
   - `X-Mockingbird-Session` (default `default`).
   - `X-Mockingbird-Status` (a u16; a bad value → 400 problem).
   - `X-Mockingbird-Latency`: `humantime` duration, capped at 30 s, applied with `tokio::time::sleep` before responding.
4. **State read.**
   - `SessionKey{workspace:"default", mock: rt.name, session}`.
   - `target`: if `identity.path_param` is set, `state.get(resource_type, path_params[param])`.
   - `related`: for a list Query (no path param), `state.list(resource_type, 20)`. Also, for every body or query field named `<x>Id` or `<x>_id` with a string value, look up resource types `<x>s` then `<x>` and add any hit.
5. **Generate** via `engine.generate`. `UndeclaredStatus` → `problem(400, "Undeclared status override", …)`.
6. **State write** (2xx only):
   - `Create`: take the id from `body[identity.field]` as a string (number → string) and upsert.
   - `Update`: upsert under the path param id; data = the response body if present, else the request body.
   - `Delete`: `state.delete`.
7. **Respond** with the status, `Content-Type: application/json` when there's a body, and `X-Mockingbird-Source: <source>`.
