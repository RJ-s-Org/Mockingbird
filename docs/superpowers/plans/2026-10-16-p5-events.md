# Mockingbird P5 Events Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Compile AsyncAPI 2.x/3.0 contracts into MCM channels and serve them: generated messages published to Kafka, AMQP, MQTT and WebSocket on schedule, cron, state-change and manual triggers, and consumed messages validated, recorded and optionally answered.

**Architecture:**
- **`mb-mcm`** gains `Bundle.channels: Vec<Channel>`, with broker bindings, a direction (from the mock's point of view), message, key and header schemas, address parameters, triggers, replies and an optional state effect.
- **`mb-import`** gains an AsyncAPI compiler (`asyncapi/{mod,v2,v3,avro}.rs`). It handles 2.0–2.6 and 3.0, converts Avro payloads to JSON Schema, maps kafka/amqp/mqtt/ws bindings and parses `x-mockingbird-*` extensions. It also exports `validate_triggers`, which the Admin API and reconcile reuse.
- **`mb-engine`** gains `Engine::generate_message`, `Engine::validate_message` and `Engine::fake`, which follow the unary validate → repair → fallback path with a message prompt.
- **`mb-store`** gains migration `0100_events`, which adds:
  - a `kind` column on `request_log`;
  - the tables `channel_settings`, `mock_event_settings` and `scheduler_leases`.
- **`mb-protocols`** gains an `events` module (feature `events`, on by default):
  - a `BrokerClient` trait with an in-memory `MemoryBroker`, and the `Brokers` registry of configured connections;
  - a per-mock `ChannelRuntime`: producers with retry, consumers with validation, recording, replies and a hop guard, schedule/cron/state-change triggers behind a store-backed lease, and WebSocket channel routes;
  - broker clients behind the features `mqtt` (rumqttc, MQTT 5), `amqp` (lapin) and `kafka` (rdkafka).
- **`mb-admin`** gains `channels.rs`: list, inspect and configure channels, publish on demand, per-mock broker selection and the broker list. Runtime actions go through a `ChannelControl` trait object passed as an axum `Extension`.
- **`mockingbird`** adds:
  - the `brokers:` config section, plus per-mock `broker` and `channels`;
  - mounting of a `ChannelRuntime` next to each mock that has channels;
  - `/readyz` broker reasons, producer flush on shutdown, and the `channels`/`brokers` CLI commands.

**Tech Stack:** P4 stack, plus these exact pins (all `[workspace.dependencies]`):
- `cron = "0.17.0"`
- `rumqttc = "0.25.1"` (default features: rustls)
- `lapin = "4.12.2"` (default features: rustls, tokio runtime)
- `rdkafka = { version = "0.39.0", default-features = false, features = ["cmake-build", "tokio", "libz", "ssl"] }`
  - librdkafka is built from source with cmake and linked statically. OpenSSL is dynamic, from `libssl-dev` at build time and `libssl3` at run time, which distroless `cc` has.
  - The `sasl` feature is not used: librdkafka's built-in PLAIN and SCRAM need no Cyrus SASL. GSSAPI is unsupported.
- dev: `rumqttd = { version = "0.20.0", default-features = false }` (an embedded MQTT 5 broker for tests)
- Avro uses no crate. Avro schemas are JSON, so the in-repo converter needs only serde_json (`apache-avro` is not added).

**Spec:** `docs/superpowers/specs/2026-10-14-mockingbird-platform-design.md`. This plan covers the P5 row of §16 and implements:
- §5 (Channel), §6.1 (AsyncAPI) and §7.3;
- the broker parts of §§12–14.

The controller's decisions brief (`p5-decisions.md`) is folded into the tasks below, and the plan is self-contained. The console Channels tab is out of scope (P6 builds it on the merged P3 console). Everything is exposed through the Admin API and the CLI.

- Limits:

| Limit | Value |
|---|---|
| Message payload, produced or consumed (`MAX_MESSAGE_BYTES`) | 1 MiB (1 048 576 bytes) |
| Shortest schedule interval (`MIN_SCHEDULE_INTERVAL`) | 100 ms |
| Reply hop limit (`MAX_HOPS`) | 3 (no reply to a message whose hop ≥ 3) |
| Publish retries | 3, after 200 ms, 400 ms and 800 ms |
| Broker connect / per-attempt publish timeout | 10 s each |
| Consumer resubscribe backoff | 1 s doubling to 30 s |
| Manual publish `count` | 1–100 (default 1), generated 4 at a time, in order |
| Scheduler lease | TTL 30 s, renewed every 10 s |
| Related resources in a message prompt | the changed resource plus up to 5 more of its type |
| Producer flush on shutdown | 5 s |

- **Broker work and task ownership:**
  - Every broker call runs under a `tokio::time::timeout`.
  - No task spawned by a `ChannelRuntime` outlives it: tasks live in a `JoinSet` owned by the runtime handle and are aborted on drop. Tasks and routers hold only `Arc<ChannelInner>`, so there is no reference cycle.
- **TLS providers:** if `cargo tree -i ring` and `cargo tree -i aws-lc-rs` both show up after adding the broker crates, every rustls config Mockingbird builds uses `ClientConfig::builder_with_provider(…)`. Mockingbird never relies on a process-default provider.
- **Every produced or consumed message is reported** to `MockRuntime.recorder` as one `RequestRecord` with `kind: RequestKind::Event`:
  - `operation_id` = the channel id;
  - `method` = `PUBLISH` or `RECEIVE`;
  - `path` = the resolved address;
  - the message counts in `mb_broker_messages_total{mock, channel, direction, outcome}`.

## Review Focus

1. **The broker is unreachable at startup, or goes down later.**
   - Expected: the mock still mounts and serves HTTP/WS. `/readyz` reports `degraded` with `mock <m>: broker <b>: <error>`. Producers retry 3 times and then record a `503`. Consumers resubscribe with backoff. Nothing panics or exits.
   - Tests: Task 13 `unreachable_broker_degrades_readyz_but_mounts`, Task 7 `publish_failure_retries_then_records_503`, Task 10 `broker_down_reports_error`.
2. **A consumed poison message** (not JSON, wrong schema, over 1 MiB).
   - Expected: it is recorded with `400`/`422`/`413`, the consumer keeps running, and the next good message is still processed. No reply is sent for an invalid message.
   - Tests: Task 7 `poison_message_recorded_not_crash`, `oversized_consumed_message_recorded_413`; Task 9 `ws_invalid_frame_recorded_and_socket_stays_open`.
3. **Reply loops.**
   - Expected: a reply channel that the same mock also consumes stops after exactly 3 replies (hop 1, 2, 3).
   - Test: Task 7 `reply_hop_limit_stops_loop`.
4. **Bad trigger configuration.**
   - Expected: an invalid cron expression, or `every` < 100 ms, is a 422 from the Admin API, a config error naming the mock and channel, and an `ImportError::Invalid` naming the pointer in an AsyncAPI extension. It never becomes a running hot loop.
   - Tests: Task 2 `trigger_validation_rules`, `runaway_schedule_extension_invalid`; Task 12 `put_invalid_cron_422`, `put_runaway_schedule_422`; Task 14 `file_channel_invalid_cron_rejected`.
5. **A generated message that is too large, or a schema the LLM cannot satisfy.**
   - Expected: a payload over 1 MiB is not published. It is recorded as `413`, and manual publish returns 502 `Generated message too large`. LLM output that stays invalid after one repair falls back to faker output that validates.
   - Tests: Task 7 `oversized_generated_message_not_published`; Task 5 `unrepairable_message_falls_back_to_faker`.

Rules:
- **`detect_format`** checks `asyncapi` first: `"2.0.0"` through `"2.6.x"` → `AsyncApi2`; `"3.0.x"` → `AsyncApi3`; anything else → `Unsupported("asyncapi <v>")`. Both JSON and YAML reach it through `sniff`.
- **`validate_triggers`** (shared with Tasks 12 and 14):
  - any trigger on a `Subscribe` channel → `Err("triggers apply only to channels this mock publishes")`;
  - `Schedule.every < MIN_SCHEDULE_INTERVAL` → `Err("schedule interval must be at least 100ms")`;
  - a `Cron` whose `cron::Schedule::from_str(&Trigger::normalized_cron(expr))` fails → `Err("invalid cron expression \"<expr>\": <error>")`;
  - an empty `OnStateChange.resource_type` → `Err("on_state_change needs a resource_type")`.
- **2.x mapping:**
  - Each `channels.<address>` item yields one `Channel` per present operation:
    - `subscribe` (the application sends) → `Direction::Publish`;
    - `publish` (the application receives) → `Direction::Subscribe`.
  - `id`:
    - is the operation's `operationId`;
    - else `"<publish|subscribe>-<slug(address)>"`, using the Mockingbird direction;
    - a duplicate → `Invalid{pointer: "/channels/<escaped>/<op>/operationId"}`.
  - `title` = the operation's `summary`, else the address. `address` = the channel key.
  - `semantic_hints` = the channel `description`, then the operation `description`, then tag names, then each message's `summary` and `description` (non-empty, in that order).
  - `operation.traits` are merged into the operation, and `message.traits` into the message. Both use JSON Merge Patch in declared order, with the trait's values winning (2.x semantics).
  - `message` may be one message, `{oneOf: [...]}`, or a `$ref` to either. `#/components/...` refs resolve through `deref`. A non-local `$ref` → `Invalid{…, "external $ref is not supported"}`.
- **Message names and schemas:**
  - `message_names`: `name`, else `messageId`, else the `$ref`'s last segment, else `<channel id>-message-<n>` (1-based).
  - `message_schema`: the single payload, else `{"oneOf": [payloads…]}` in declared order. A message without a payload → `{}`.
  - `headers_schema`: the first message's normalized `headers`, or `oneOf` when the messages differ.
  - `content_type`: the message `contentType`, else the document `defaultContentType`, else `application/json`.
- **Payload schema formats:**
  - none, `application/vnd.aai.asyncapi[+json|+yaml];version=…` or `application/schema+(json|yaml);version=draft-07` → `normalize_schema(payload, "#/components/schemas/", false)`;
  - `application/vnd.apache.avro[+json|+yaml];version=1.x` → `avro_to_json_schema`;
  - any other format → `Unsupported("schemaFormat <f> at <pointer>")`.
  - `components.schemas` become `defs`.
- **Avro to JSON Schema:**
  - `null`→`{"type":"null"}`, `boolean`, `int`→`{"type":"integer","format":"int32"}`, `long`→`{"type":"integer","format":"int64"}`, `float`/`double`→`number`, `bytes`/`fixed`→`string`, `string`.
  - `record` → an object with `properties` and `required` (fields whose type is not a union containing `null` and that have no `default`), plus `additionalProperties: false`. Its full name (`namespace.name`) goes into `defs`, and repeat uses are `$ref: "#/$defs/<fullname>"`.
  - `enum` → `{"type":"string","enum":[symbols]}`, also in defs.
  - `array` → `items`; `map` → `additionalProperties`; a union → `anyOf`.
  - Logical types: `date`→`format: date`; `timestamp-millis`/`timestamp-micros`/`local-timestamp-*`→`{"type":"string","format":"date-time"}`; `uuid`→`format: uuid`; `decimal`→`number`; `time-*`→`format: time`.
  - `doc` → `description`.
  - An unknown named type → `Invalid`. A defs name colliding with a component schema → `Invalid`.
- **Binding protocol:**
  - the channel's `bindings` key among `kafka|amqp|mqtt|ws`, when it has exactly one;
  - else `server_protocol`: the protocol of the channel's first `servers` entry, else of the first server in sorted name order. `kafka|kafka-secure` → kafka; `amqp|amqps` → amqp; `mqtt|mqtts|secure-mqtt` → mqtt; `ws|wss` → ws;
  - none → `Invalid{pointer: "/channels/<escaped>", message: "cannot determine the broker protocol: add channel bindings or servers"}`.
- **Bindings** (`servers` URLs are never used for connections):
  - **kafka:** `topic` = channel binding `topic`, else the address; `partitions_hint` = `partitions`. The message binding `kafka.key` schema → `key_schema` (normalized).
  - **amqp:** `is: routingKey` (default) → `exchange` = `exchange.name` (default `""`), `exchange_type` = `exchange.type` (default `"topic"`), `routing_key` = the address. `is: queue` → `exchange ""`, `exchange_type "direct"`, `routing_key ""`, `queue` = `queue.name`, else the address.
  - **mqtt:** `topic` = the address; `qos` = the operation binding `mqtt.qos` (default 0; above 2 → `Invalid`); `retain` = `mqtt.retain` (default false).
