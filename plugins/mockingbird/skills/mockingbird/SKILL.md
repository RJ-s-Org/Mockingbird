# Mockingbird

Mockingbird imports an API contract and serves a running mock that answers with schema-valid responses generated by an LLM (or by a built-in faker when offline). One binary, `mockingbird`, does everything: serve mocks, the Admin API, a web console, and an MCP server for agents.

## What to reach for

| The user wants to… | Do this | Details |
| --- | --- | --- |
| Install Mockingbird, pick an LLM (OpenRouter, Google AI Studio, Cloudflare AI Gateway, OpenAI, Anthropic, local, any OpenAI-compatible endpoint) | `mockingbird-setup` skill | `install.sh`, `mockingbird init`, `mockingbird llm configure/test` |

## Fast path (no questions needed)

```sh
command -v mockingbird || curl -fsSL https://raw.githubusercontent.com/rj-s-org/mockingbird/main/install.sh | sh
mockingbird init --offline --contract ./openapi.yaml          # or --provider openrouter (see mockingbird-setup)
mockingbird server start -c mockingbird.yaml                  # background; prints URLs as JSON
curl -s localhost:8080/<mock>/<path>                           # the mock, mounted at /<file stem>
mockingbird server stop
```

Every response carries `X-Mockingbird-Source: llm | repaired | fallback` (`fallback` = faker). Ports: data plane `:8080`, Admin API + console `:9090` (console at http://127.0.0.1:9090/), gRPC `:50051`.

## MCP tools

When the `mockingbird` MCP server is connected, prefer its tools over shell commands; they return JSON. All of them work against the Admin API at `MB_ADMIN_URL` (default `http://127.0.0.1:9090`) in workspace `MB_WORKSPACE` (default `default`).

- Setup and lifecycle: `doctor`, `list_llm_providers`, `init_config`, `configure_llm`, `test_llm`, `validate_contract`, `start_server`, `server_status`, `server_logs`, `stop_server`, `proxy_env`
- Mocks: `list_mocks`, `get_mock`, `create_mock`, `update_mock`, `delete_mock`, `import_contract`, `list_contract_versions`, `activate_contract_version`
- Drafts (imported documentation, HAR, Postman): `get_draft`, `edit_draft`, `approve_draft`
- Behaviour: `list_scenarios`, `put_scenario`, `delete_scenario`, `list_llm_profiles`, `put_llm_profile`, `delete_llm_profile`
- State and traffic: `call_mock`, `list_requests`, `get_request`, `list_sessions`, `export_session`, `seed_session`, `reset_session`
- Events: `list_channels`, `publish_event`
- Anything else in the Admin API (API keys, workspaces, audit): `admin_api`

Without MCP, the same operations are CLI subcommands (`mockingbird --help`); each prints JSON.

## Rules

- Start with `doctor` (or `mockingbird doctor`) when the state is unknown: it reports the binary, config, provider keys and whether a server is running.
- Never write an API key into a file, a command line or a tool argument. Profiles hold references (`env:OPENROUTER_API_KEY`); ask the user to export the variable, then restart or re-test.
- Without an LLM key, use `--offline` (faker only): mocks still answer schema-valid data.
- Changes through the Admin API take effect immediately; a config file served with `--watch` (the default for `server start`) is reloaded on save.
- Mocks, profiles and scenarios declared in `mockingbird.yaml` are read-only through the API (409): edit the file instead.
