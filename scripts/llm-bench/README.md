# LLM model benchmark harness

This harness runs OpenRouter models through Mockingbird's real LLM code paths: the engine workload through `mb-evals` and the `mockingbird serve` suites. It records latency, tokens and cost for every call and keeps spend under a hard budget. It uses only the Python 3.9+ standard library.

| file | role |
|---|---|
| `proxy.py` | Recording proxy in front of OpenRouter. It enforces the budget and measures latency and cost. |
| `providers.json` | Per-model OpenRouter provider pins, which the proxy sends (see [Provider pins](#provider-pins)). |
| `run.py` | Orchestrator with three subcommands: `preflight`, `pilot` and `full`. |
| `server_suites.py` | The `mockingbird serve` workloads: consistency, SSE, smart import, the multi-step journeys and the held-out journeys. |
| `grade.py` | Deterministic schema conformance grading of the samples. |
| `aggregate.py` | Joins all outputs into `results.json`, `results.csv` and `tables.md`. |
| `world_author.py` | World descriptions for `--world`: blind authoring by a coding agent, the cache per contract hash, and applying a description to a suite's mocks. |
| `stub_author.py` | A free, deterministic stand-in author for dry runs and tests. |
| `replay.py` | Recordings of the journeys suites' LLM answers, and the replay gate that runs on them (see [Replay gate](#replay-gate)). |
| `recordings/` | The committed recordings, one `<model slug>~<suite>.json.gz` per (model, suite). |

## The key

`OPENROUTER_API_KEY` must be in the environment (`source ~/.zshenv >/dev/null 2>&1`). Never print it or write it to a file. Only `proxy.py` and the `preflight` metadata calls read it. Child processes get dummy keys: `MB_EVAL_LLM_API_KEY=bench-dummy` for mb-evals and `OPENROUTER_API_KEY=bench-dummy` for the server suites. The proxy replaces the client's Authorization header with the real key.

## Re-running

```sh
source ~/.zshenv >/dev/null 2>&1
cargo build --release -p mb-evals -p mockingbird-cli

# 1. Model metadata and prices -> roster.json; key credit numbers -> key-before.json
python3 scripts/llm-bench/run.py preflight

# 2. Pilot: ~10 engine calls per model, then a printed cost projection
python3 scripts/llm-bench/run.py pilot --calls 10 --repeat 3
#    (--models a,b,c to limit it; results in <out>/pilot/pilot.json)

# 3. Full run: cheapest first, 3 models at a time, Inkling models last and alone
python3 scripts/llm-bench/run.py full --repeat 3 --parallel 3 --concurrency 4

# 4. Grade and aggregate (see grade.py / aggregate.py --help)
```

mb-evals runs with a default LLM profile's settings, as the server does: a 60 s timeout, `max_tokens` 16,384, temperature 0.7 and the default output budget (1,500 tokens). `--llm-timeout-secs`, `--max-tokens` and `--output-budget` override them. GraphQL targets are called with the selection set their manifest entry gives (`selections` in `docs/benchmarks/workloads.json`, see `crates/mb-evals/src/selection.rs`), as a real client's query would. `--prior-ledger <earlier calls.jsonl(.gz)>` (repeatable) counts an earlier run's spend toward `--budget-usd`. `--output-mode none|json_object|json_schema` sets the engine's `output_mode` (default `json_schema`, the server default). A model listed as `<id>@nojson` always runs with `none`, and the proxy also strips `response_format`.

The 2026-10-29 run predates these settings: it ran at 2,048 tokens and 30 s, with no GraphQL selections.

All results go to `--out`, which defaults to `docs/benchmarks/2026-10-29`. Relative paths resolve against the repository root, and children run with the root as their working directory.

| path under `--out` | contents |
|---|---|
| `roster.json` | The requested models with per-token `pricing`, `supported_parameters`, `response_format` and `structured_outputs`. Models OpenRouter does not list have `found: false`. |
| `key-before.json`, `key-after.json` | Only `usage`, `usage_daily` and `limit_remaining`. |
| `calls.jsonl` | The proxy ledger for the full run, one line per client call. The spec lists the fields. |
| `engine/<slug>/` | Per model: `samples.jsonl`, `report.json`, `report.md` and `mb-evals.log`. |
| `server/<slug>/` | Per model: `server.jsonl` and `server_suites.log`. |
| `samples.jsonl`, `server.jsonl` | Every model's samples and server checks merged into one file each. `run.py` adds `model` and `model_slug` to each sample line. |
| `run.json` | Run state: order, projections, each model's status (`done`/`partial`/`failed`/`skipped`), why models were skipped, and spend. |
| `pilot/` | The pilot's own ledger (`calls.jsonl`), slice manifest, `pilot.json` and per-model mb-evals output. |
| `proxy.log` | The proxy's log, which never contains the key. |
| `BUDGET_TRIPPED` | Exists once the budget has been hit. |
| `invalid.jsonl` | Written by `server_suites.py` (in its `--out`, so `server/<slug>/` under `run.py`): one line per suite run that the bench's own budget stopped. See [Budget](#budget). |

The model slug is the model id with `/` replaced by `__`. Proxy labels have the form `<slug>~<workload>`. The workload is `engine` for the full run, `pilot` for the pilot, and the suite name for the server suites.

## Running the server suites fast

By default `server_suites.py` runs every suite, rep and journey in order, so a model has about one LLM call in flight. Two flags change that without changing the rows (case names, rep numbers and `ok` are the same; only row order and latencies differ):

- `--jobs N` runs the independent units of each suite on N threads against the suite's one server: every (rep, journey) pair of the journeys suites, and every rep of `consistency` and `sse`. Each unit has its own `x-mockingbird-session`. A consistency rep's three checks share their session, so they stay in order inside the rep. `import` always runs in order, because the server queues import jobs on two workers and the wait would count toward `--import-timeout` and the measured time.
- `--suites-parallel` runs the suites given with `--suite` at the same time, each on its own server. Running one process per (model, suite) does the same thing, and so does `run.py full --parallel`. Each server gets its own temp directory, its own log (`server-logs/<slug>~<suite>.log`) and its own proxy label. Its three ports are picked under a lock file (`$TMPDIR/mb-bench-ports.lock`) that is held until the server answers `/readyz`, so two servers starting at the same moment never get the same port. Processes coordinate only through that file, so they must share one `TMPDIR`: a process started with a different `TMPDIR` (another user, a sandbox, a container) does not see the lock. A server waits for the lock for at most `--ready-timeout` + 30 s, so a stopped holder cannot block the others forever; after that it goes on without the lock, and a server that then loses a port exits and is retried on new ports (3 starts). All of them can share one `--out`, since `server.jsonl` is appended under `flock`.
- Ctrl-C stops a parallel run: queued units are cancelled, units already running stop at their next call and write no more rows (a journey cut short is not padded with failed checks), and each server is shut down.

```sh
python3 scripts/llm-bench/server_suites.py --model <id> --proxy-base http://127.0.0.1:<port> --out <dir> \
  --repeat 3 --suite journeys_blind6 --suite journeys_blind7 --suites-parallel --jobs 4
```

`run.py full --server-jobs N` passes `--jobs N` on. The number of calls in flight per model is about (number of suites running) × `--jobs`, and the proxy reserves a budget estimate for each call in flight, so leave `--budget-usd` some headroom (`server_suites.py` warns at start when it is short; see [Budget](#budget)). A journeys suite of 5 journeys × 3 reps has 15 units, so `--jobs 4` makes it about 3–4× faster, and `--jobs 15` makes it as fast as its slowest journey. The server allows 64 LLM generations at once (`limits.max_concurrent_generations`); a call that waits past its LLM timeout is answered by the faker, so keep the total well under that.

## Comparing two commits (A/B)

To tell a regression from model variance, run the same suites on two builds with the same bench scripts and model. Build the binaries one after another into one persistent target dir. The second build then recompiles only the crates that changed, where two cold builds in their own target dirs each take minutes. Copy each binary out as soon as it is built, since the next build overwrites it:

```sh
T=/private/tmp/claude-502/bis-target   # shared by every A/B run on this machine
for c in <sha-a> <sha-b>; do
  git worktree add -q --detach /private/tmp/claude-502/bis-$c $c
  (cd /private/tmp/claude-502/bis-$c && CARGO_TARGET_DIR=$T cargo build -q --release -p mockingbird-cli) \
    && mkdir -p <out>/bin && cp $T/release/mockingbird <out>/bin/mb-$c
  git worktree remove --force /private/tmp/claude-502/bis-$c
done
```

Then run `server_suites.py ... --binary <out>/bin/mb-<sha>` for each build, with the scripts from one checkout, so only the binary differs. Use `--repeat 4` or more: at repeat 2, a check that passes half the time moves by a whole rep.

### The free gate (`fakegate.py`)

`python3 scripts/llm-bench/fakegate.py <branch|sha|binary> [--base origin/main]` runs every journeys suite and `consistency` (not the undiagnosed blind sets) on `fake_llm.py` for a candidate and a base. It runs them at the `agent` tier, with the committed world-cache's descriptions and cache only, and at tier 0. It costs no spend. Before an engine pull request is marked ready, run it on the branch. It lists every check that went from pass to fail (LOST) or the other way (gained), tier by tier, and exits 1 when a tier lost more than `--noise` checks net. The default noise is 1, because the engine is not entirely deterministic. A check that passes on the fake LLM is one the engine decides, so a loss here is a regression whatever model runs later. Checks that need a real model's answers are not judged. Worktrees, binaries and both sides' results stay under `--work` (default `$TMPDIR/mb-fakegate`). A side's results are kept in a directory named by a hash of its binary, checkout, suites, contracts and descriptions, and reused only from there, so a gate with other inputs never replaces results another gate is reading; a side with no rows for a suite it should have run stops the gate (exit 2) instead of being compared, so gating several branches against one main builds and runs main once; locks let gates share `--work`. A check the base passed that the candidate did not run counts as lost. Each tier also reports its executor-decided failures apart from the net (`executor-decided: N -> M fail (+x/-y)`, with each new one listed as EXEC-FAIL): failing checks whose deciding call the engine answered itself (`source` state or rejected), which fail the same way on a real model, so a junk-LLM gain elsewhere cannot hide an executor regression. They are reported, not part of the verdict. A branch candidate runs with its own scripts and contracts, so a pull request that changes checks moves its own yardstick; to compare engines only, pass a binary, which runs with the base's. A branch name resolves to `origin/<branch>` first, and the gate prints the commit it took. `test_fakegate.py` tests the comparison and the choice of descriptions, and checks that the committed cache covers every suite the gate runs: Sonnet-authored descriptions (`claude-code~claude-sonnet-5-5~p1`) for blind1-10, held-out, journeys and consistency, and Opus ones for blind11-13.

### The end-to-end eval (`e2e.py`)

The product as a user meets it: a coding agent gets one prompt and an API's contract, builds a mock with Mockingbird's plugin, and the app's hidden journeys then run against what it built.

**Stage 1: `e2e.py build --binary B --cache DIR`.** It makes one task per contract of the dev suites (every journeys suite and `consistency`, minus blind14 and blind15). The task directory holds:
- `contract.<ext>`;
- `docs/`, when doc excerpts sit next to the contract as `<stem>.docs/`;
- `PROMPT.md`, one fixed line: "My app integrates with the <Vendor> API. The contract is in ./contract.<ext>. Set up a Mockingbird mock so I can develop and test the app against it."

There are no journeys, checks or hints. `e2e.py tasks --out DIR` writes the task directories on their own.

The agent is a headless Claude Code (`claude -p`, Sonnet by default), set up as follows:
- **Plugin:** the Mockingbird plugin built from the binary under test, its skills loaded through the Skill tool.
- **MCP:** that binary's `mockingbird mcp` is its only MCP server.
- **Files:** Read, Grep and Glob, confined by `--restricted` to the task directory and the plugin.
- **Server:** an empty `mockingbird serve` with no LLM profile, already running for it.
- **Tools:** every MCP tool, except those that start, stop or reconfigure servers, open a browser or test a provider.
- **Caps:** `--budget` (default $1) and `--max-turns` (default 60) per task, and `--cap` dollars for the whole run.

When the agent stops, the product's `mockingbird snapshot export --include scenarios,chaos,limits,world` saves what it built. Each task's `result.json` records:
- every tool's calls and errors, and the retries;
- the skill pages read and the refused world entries;
- turns, cost and wall time;
- the mocks it built.

Results are cached in `<cache>/<key>/<task>/`. The key hashes the skills, the MCP tool schemas, the prompt version, the model and the caps. The binary's hash is recorded with each result, and joins the key only with `--key-binary`, so an engine change reuses the snapshots. The transcripts in the cache are never committed.

**Stage 2: `server_suites.py --world e2e --e2e-cache <cache>/<key>`.** Each suite's server starts with no mocks. Each mock its journeys call is loaded from the stage-1 snapshot of its contract with `mockingbird snapshot import`, renamed to the mock name and route prefix the journeys use. A contract whose agent built nothing stays unmocked, so its journeys fail.

`fakegate.py --e2e-cache <cache>/<key>` adds this as the `e2e` tier. Both sides load the same snapshots, so the tier gates the engine on fixed builds.

**The report: `e2e.py report RUN --stage1 <cache>/<key> [--paid DIR ...] [--curated RUN] [--attribution FILE ...]`.** For each suite and tier it prints the fake pass rate, the projected rate, and the failures split into floor, missed and model. Each failed check is in exactly one class, so floor + missed + model is the failure count. The projected rate is (passed + model) / total: missed and floor failures do not count toward it.

The class of a failed check is the first of these that applies:
1. An attribution names it `missed`: **missed**. An attribution names it `engine`, `inexpressible` or `journey`: **floor**.
2. The curated tier (`agent`, the run's own or `--curated`, on the same binary) passes it: **missed**.
3. Its deciding call never reached the model, so `source` is not llm, llm-repaired, repaired, patched or fallback: **floor**. That covers the engine-decided sources (state, rejected) and calls that never ran (error, `?`).
4. `--paid` runs are given and none of them passed it: **floor**.
5. Otherwise: **model**.

An attribution only demotes a check out of model. Naming it `model` keeps whatever class the other rules give, so it can never promote a floor or missed check into model. A curated row that fails, or is missing, changes nothing. The curated tier and the attributions judge only the `e2e` tier; the `agent`, `none` and derived tiers use rules 3 to 5. The `--paid` rule applies to every tier.

`--attribution` takes classifier output, `[{suite, check, reclass|cls}]`, where the class is one of `model`, `missed`, `engine`, `inexpressible` or `journey`. Any other class stops the report with an error. With `--attribution` given, model failures that no attribution names are shown as unattributed: the projection is an upper bound by that many. A baseline's attribution comes from classifier agents reading each model-reached failure's deciding call: its executor fallback and the curated diff.

## Budget

The proxy stops spending. Before each call it reserves an estimate of the call's cost and holds it while the call is in flight. It refuses the call with 402 (`bench budget exhausted`) when the following would reach `--budget-usd` (default 9.0):

    ledger spend + prior-ledger spend + in-flight reservations + this call's estimate

The estimate starts as the worst case: prompt characters / 3 × input price, plus `max_tokens` (default 4096; Mockingbird's server profiles send 16,384) × output price. Real calls cost far less than that, so with many calls in flight the reservations alone can reach the cap while real spend is well under it. Once the ledger (`--ledger`, including rows from an earlier start) has 20 successful calls of a model (any `@variant`), that model's calls reserve the 90th-percentile measured cost per call × 1.5 instead, at least the call's prompt part and never more than the worst case. `GET /reserve?model=<id>&max_tokens=<n>` reports what such a call reserves now, and whether it is the measured or worst-case figure. With measured reservations a burst of unusually long answers can end slightly over the cap: the in-flight calls are charged what they cost.

A refusal records `error_kind: budget` and creates `BUDGET_TRIPPED`. After that the proxy refuses every call, including after a restart. To reset, delete the file and raise the budget on purpose.

The budget covers the pilot and the full run together. `run.py` passes the other phase's ledger to the proxy as `--prior-ledger`, and a `BUDGET_TRIPPED` next to a prior ledger counts as a trip too.

Mockingbird answers a refused call with its faker, which says nothing about the model. So as soon as `server_suites.py` sees an answer whose fallback reason is the proxy's 402 (`x-mockingbird-fallback-reason` matching `proxy.budget_exhausted`, or an import job failing on it), it stops the run: every unit stops at its next call, the refused answer and any later check write no row, each suite prints `<suite>: INVALID: bench budget exhausted (spent $X of $Y cap)`, and the process exits 3. Each stopped suite run appends a line to `<out>/invalid.jsonl` with its `run_id`, model, suite, world, rows written, spend, cap and the first refusal. Every `server.jsonl` row carries the `run_id` of the process that wrote it; `aggregate.py` leaves the rows of every run in `invalid.jsonl` out of all scores, lists the runs in `results.json` (`invalid_runs`) and at the top of `tables.md`, and prints them on stderr. A record names one suite of one process (`run_id`, suite, world): a suite that finished before the budget ran out keeps its rows, while every suite still running when it ran out is stopped and recorded. Re-run the stopped suites with more budget; the new run's rows have a new `run_id`.

Some answers carry no fallback reason: Mockingbird's SSE handler sends its headers before it generates, so a refused SSE call looks like any other stream. As a backstop that works on every protocol, `server_suites.py` reads the proxy's `/stats` when a suite starts and again when it ends: each label's entry in `per_label` counts its calls the proxy refused on its budget (`budget_refused`), and a suite whose label gained a refusal while it ran is stopped and recorded the same way (its rows written before the check are left out by the record); a proxy that does not answer `/stats`, or does not count refusals, gives no verdict). It also checks the fallback reason a request-log entry reports (the SSE suite reads its source there). When `/reserve` at start says the proxy has already tripped, `server_suites.py` prints an error and exits 3 before running anything. `run.py` records a model whose server suites exited 3 as `invalid` (with `invalid_reason`) in `run.json`, not `failed`.

A call the proxy itself fails on (a proxy bug, `error_kind: stream_error` with `proxy error:` in the excerpt) is charged the call's worst case, not its reservation: the upstream may have generated the whole `max_tokens`, and a measured reservation would undercount the ledger.

At start `server_suites.py` asks the proxy what one of its calls reserves and warns when the budget left (cap − spend − other calls' reservations) is under 2 × (calls in flight × that reservation). Calls in flight are `--jobs`, times the number of suites with `--suites-parallel`. Other bench processes sharing the proxy (several tiers at once) also reserve, so leave room for them too.

On SIGTERM or Ctrl-C the proxy stops accepting calls and waits (up to its 120 s upstream timeout) for in-flight calls to reach the ledger, so a restart counts their cost. `run.py` starts it in its own session and stops it after the children. A kill -9 still loses the in-flight calls' records.

`full` also checks the budget before it starts each model. Projections come from `pilot/pilot.json` when it exists and from roster prices otherwise. If spend so far, plus the unspent projections of the models still running, plus the next model's projection would cross the budget, `full` skips that model and every model after it.

## Stopping

Press Ctrl-C or create `<out>/ABORT`. No new model starts, and the running mb-evals and server-suite processes get SIGTERM. Remove `ABORT` before the next run.

Children never see the key: `run.py` drops `OPENROUTER_API_KEY`, any variable with the same value and every `MB_LLM_*` / `MB_EVAL_LLM_*` variable (mockingbird's zero-config profile defaults to openrouter.ai, which would bypass the proxy). `server_suites.py` drops every `MB_*` variable from the server's environment. The proxy redacts the key from anything it echoes (error excerpts and error bodies).

## Proxy details

- `GET /stats` returns spend, call count, the trip flag and per-label totals. `GET /healthz` returns 200.
- `--record <raw.jsonl>` appends each call's journey tag (from `x-bench-journey` and the `POST /bench/mark` marks) and answer, never a header; `--replay <recordings>` answers every call from recordings with no upstream, no key and no ledger needed, and `--replay-log` records each call's match. Both are for `replay.py` (see [Replay gate](#replay-gate)).
- `--dump <exchanges.jsonl>` appends each forwarded call's messages and answer, never a header, with its status and the same journey tag `--record` writes (`journey`, `rep`, `op`, `n`, `hash`, `now`). `server_suites.py` tags journeys by default, so the dump of any run (`run.py` keeps one next to the ledger) can be packed into a recording: `replay.py pack-dump` (see [Seeding from a run's dump](#seeding-from-a-runs-dump)).
- When the client did not ask for streaming, the proxy upgrades the call to streaming (turn this off with `--no-stream-upgrade`). This lets it measure TTFT, the time to the first non-empty `delta.content`. TTFR is the time to the first reasoning delta. Both are measured from when the attempt that succeeded had its upstream connection up (TCP and TLS are excluded: a real client reuses pooled connections). `total_ms` is measured from when the client's request arrived.
- OpenRouter's keep-alive comments (`: OPENROUTER PROCESSING`) are skipped. The proxy reads usage, including `usage.cost`, from the final chunk. A mid-stream `error` object, or `finish_reason: "error"`, becomes a 502 carrying the error body. If the client asked for a stream, the 200 header has already gone out, so the error passes through inside the stream.
- If the upstream rejects `reasoning: {"enabled": false}` (400/404/422 with "reasoning" in the body), the proxy retries once without it and remembers that for the model. It does the same for `response_format` (400/422 that mentions response_format or JSON mode).
- When there is no usage chunk (cut stream or timeout), cost is estimated from the prompt plus the output seen so far, with `cost_source: "estimate"`. A model the roster does not price is reserved at deliberately high fallback prices.
- `error_kind: empty` means both content and reasoning were empty. `refusal` means `finish_reason == "content_filter"` or a non-null `refusal`.
- **A streaming client that hangs up.** The proxy notices when a relay write to a streaming client fails (any socket error: broken pipe, reset, macOS `EPROTOTYPE`). Mockingbird does this when it aborts a looping answer. What happens next depends on whether the answer had ended.
  - **Mid-generation.** No `finish_reason`, no in-band error and no `[DONE]` yet. The proxy stops reading from the provider at once and closes that connection. The call is recorded with what was received so far: `status: 499`, `error_kind: client_closed`, `client_closed: true`, `received_chars`, and the `generation_id`, which can be used to look the generation up. Cost follows the rule above: usage if it had arrived, else the prompt plus the output seen. The reservation is released.
  - **Billing after a drop.** OpenRouter stops billing on a dropped stream only for providers that support cancellation. Others keep generating and bill the full answer, so a 499's cost is a lower bound.
  - **After the answer ended.** This is the usual case: Mockingbird drops the stream right after a `finish_reason: length` chunk or an in-band error. The proxy stops relaying but keeps reading the remaining lines without forwarding them, so the usage that comes last still arrives. The call is recorded as usual, plus `client_gone_after_end: true`.
  - **How a 499 counts.** It is neither a success nor an error, everywhere calls are counted. `aggregate.py` (its reliability block has an explicit `client_closed` count), `run.py`'s summaries (`client_closed`), `live.py` and the proxy's `/stats` per label (`client_closed`) all leave it out of errors.
  - **Hang-ups noticed late.** Nothing is relayed before the first chunk (keep-alives are held until then, for the pin check), so a hang-up before the first content chunk is noticed only when chunks arrive. The provider generates, and bills, until then. A client that drops a non-streamed call is only noticed when the answer is sent, after the provider has finished.

## Provider pins

OpenRouter can send one model to different upstream providers from one run to the next. Between full6 and full7, Nemotron went from Fireworks (2089 of 2114 calls) to a mix of CoreWeave, DeepInfra, Fireworks, Io Net and Darkbloom. Its timeouts and truncations went up with the change, and about 80 Nemotron checks moved with them. To stop this, the proxy pins each model to one provider, or to a short ordered list of endpoints held equivalent for comparability.

- **Where pins live.** [`providers.json`](providers.json) maps a model id to an OpenRouter `provider` object: `{"order": [...], "only": [...], "allow_fallbacks": false}`, plus `quantizations` (OpenRouter's precision filter) where the pin states one. Each pin's `basis` field records why it was picked. Change a pin there, not in code. `proxy.py --provider-pins <file>` and `run.py --provider-pins <file>` read another file, and `''` turns pins off. `run.py preflight` copies each model's pin into `roster.json` as `provider_pin`, and it honours `--provider-pins` too.
- **Current pins.** Each model is pinned to the one provider that served most of its full6 calls:

  | model | pin | full6 share |
  |---|---|---|
  | `nvidia/nemotron-3.5-lightning` | `fireworks` | 2089 of 2114 calls (98.8%). Fireworks lists one endpoint for this model. In full8 it looped: 271 of its 2708 calls stopped at max_tokens (`finish_reason: length`), against 8 of 2245 in full6. |
  | `openai/gpt-6-luna` | `openai` | 1913 of 2108 calls (90.7%) |
  | `deepseek/deepseek-v4.1-flash-1017` | `wafer/us`, `quantizations: ["mxfp4"]` | 378 of 2090 calls (18.1%). About 25 providers served the rest, so this pin changes DeepSeek's conditions the most. In full8, 94 of 2648 calls got a 429 (`temporarily rate-limited upstream`); those fallbacks are labelled `detail.infra`. No second endpoint qualified (see `basis`). |

- **Endpoint variants.** A pin names the endpoint variant (a `tag` from `GET /api/v1/models/<id>/endpoints`). In OpenRouter's routing, a full tag such as `wafer/us` matches only that endpoint, so OpenRouter does not route DeepSeek to `wafer/mxfp4`. On 2026-11-04 the endpoint list reports `mxfp4` for both. A base slug matches every endpoint of that provider except the service tiers, so `openai` leaves out `openai/flex` and `openai/fast`. full6 recorded only the provider's display name, not which variant served a call, so the variants were chosen from the endpoint list. The answer still carries only that display name (`Wafer`, not `wafer/us`). The ledger cannot record the variant either: the pin in `provider_pin` is the record. The proxy's own check (`pin_allows`) matches that display name against each pin entry's base slug, so it confirms the provider (Wafer) but cannot tell Wafer's endpoints apart. Keeping to `wafer/us` and to `mxfp4` rests on OpenRouter honouring `only` and `quantizations`; the bench cannot verify it per call.

- **What a pin guarantees.** With `only` repeating `order` and `allow_fallbacks: false`, OpenRouter serves the call from a listed endpoint or fails it; it never goes to another provider. A pin may list up to three endpoints, which OpenRouter tries in `order`. Every endpoint must serve the same model and report a known precision that is at least the first's. `quantizations` names exactly the values the endpoints report, so OpenRouter refuses an endpoint whose reported precision changes. The OpenRouter values are `int4`, `int8`, `fp4`, `mxfp4`, `nvfp4`, `fp6`, `fp8`, `mxfp8`, `fp16`, `bf16`, `fp32` and `unknown`. `fp4` covers `mxfp4` and `nvfp4`, and `fp8` covers `mxfp8`, so a pin never names those umbrella values or `unknown`. An endpoint that reports `unknown` or an umbrella value is not added. OpenRouter defines no order between the values, so whether one precision is at least another is judged when a pin is chosen, and recorded in `basis`. A test checks how each pin is built (documented values, no `unknown`, no umbrella value, `only` equal to `order`, no fallbacks). A later endpoint also needs no bad call (non-200, error or `length`) in full-run ledgers with enough calls to show it, and a latency close to the first's. Today every pin is a single endpoint.
- **Before a run: is the pinned endpoint healthy?** A pin has no fallback, so when its endpoint is degraded the run scores the provider's timeouts and 502s as the model's failures. One Nemotron run got 180 timeouts (HTTP 499) and 209 502s while OpenRouter listed Fireworks at status -2 with 90% uptime over 30 minutes; every other endpoint was at status 0 and 100%. So before a run starts, `server_suites.py` (before any suite) and `run.py full` (just before each model, and again when that model's server suites start) read the model's public endpoint list, `GET https://openrouter.ai/api/v1/models/<id>/endpoints`. It needs no key, and the key is never sent to it. The pin's entries are matched to endpoints as above: a full tag matches that tag only, a base slug matches the provider's endpoints except service tiers (`service_tier` set), and a pin's `quantizations` leaves out endpoints reporting another precision.
  - **Healthy** means `status` 0 and `uptime_last_30m` at least 99% (`HEALTHY_STATUS` and `MIN_UPTIME_30M` in [`provider_health.py`](provider_health.py)). A pin entry that matches no listed endpoint counts as degraded.
  - **A degraded pinned endpoint refuses the run.** The message names the model, the endpoint, its status and its uptime. `server_suites.py` exits 4 before starting a server. `run.py full` marks that model `refused` in `run.json` (with `refuse_reason`), goes on with the other models, and exits 4 at the end. `--allow-degraded-provider` (both scripts) runs anyway with a warning, and the record says `allowed_degraded: true`.
  - **The list cannot be fetched** (network, HTTP error, unexpected answer): a warning, and the run goes on with the verdict `unknown`.
  - **What is recorded.** `<out>/providers-status.json` keeps one record per model, from its latest check: `verdict` (`healthy`, `degraded`, `unknown`, or `unpinned` for a model with no pin), `problems`, `fetch_error`, `checked_at`, and each listed endpoint's `tag`, `provider_name`, `status`, `uptime_last_30m`, `uptime_last_5m`, `quantization`, `service_tier`, `pinned` and `healthy`. An unpinned model's endpoints are recorded for information and never refuse a run. A one-line summary goes to stderr. Under `run.py full` the file is `<out>/providers-status.json` for the checks before each model and `<out>/server/<model>/providers-status.json` for the server suites' own check.
  - **Turning it off.** `--no-provider-check` skips the check (offline runs). `replay.py` always passes it, since recorded answers do not depend on the live endpoints, and `run.py` skips it with a fake `--upstream`.
- **How a pin is added.** The proxy adds the pin as the call's `provider` field. If the client already sent a `provider` field, the proxy passes it on as sent and does not enforce it. A model with no pin is forwarded unchanged. A bench variant (`<id>@nojson`) uses its base model's pin.
- **When the pinned provider is unavailable.** OpenRouter documents this failure as a 503 ("no available model provider that meets your routing requirements"). A 503 passes through as `http_5xx`, which the journeys label as `detail.infra` (see the blind7 notes below). When OpenRouter answers a 400 or 404 with its no-allowed-provider message instead ("No allowed providers are available ..."), the proxy turns it into a 503 with `error_kind: provider_unavailable`. Mockingbird reports that as `LLM returned HTTP 503: pinned provider ... unavailable`, which is labelled infra too. Only those exact phrases count. A 4xx that merely mentions a provider or an endpoint passes through as `http_4xx`, because mb-llm steps down from those itself (schema, reasoning). Examples: `Provider returned error`, `This endpoint's maximum context length ...`, `No endpoints found that can handle the requested parameters`. The call is never sent to another provider.
- **An answer from a provider the pin does not allow.** The proxy refuses it the same way (503 `provider_unavailable`) and sets `provider_pin_mismatch: true` in the ledger. It checks the provider on the first streamed chunk. Nothing is relayed to a streaming client before that check, not even the 200 head; keep-alives wait. If the first chunk names no provider and a later chunk names a provider the pin does not allow, the stream has already gone out, so the call is only flagged.
- **One unavailable call can show as two rows.** mb-llm retries a 503 once, so one mock call that the pinned provider could not serve usually appears as two `provider_unavailable` ledger rows. Those rows count in `aggregate.py`'s errors and error rate.
- **What the ledger records.** Every ledger line has `provider` (who served the call), `provider_pin` (the `provider.order` it was sent with) and `provider_pin_by` (`proxy`, `client` or null).
- **Where the provider mix is reported.**
  - `/stats` counts providers per label, for calls made since that proxy started. Rows already in a resumed ledger count toward spend but not toward the mix, so the mix covers the current run.
  - `server_suites.py` prints each suite's provider mix under its ok count.
  - `run.py full` logs each model's mix when the model finishes and stores it as `providers` in `run.json`.
  - `aggregate.py` shows the pin and the pin-unavailable count next to the served-provider shares in section 6 of `tables.md`. It reads the whole ledger it is given.

  Read a score together with its model's provider mix.

## World descriptions (`--world`)

`server_suites.py --world none|derived|agent` sets the world description every mock of a run serves with (see [`docs/world.md`](../../docs/world.md)). The flag is per run, so measuring the three tiers takes three runs into the same `--out`:

| tier | what the mocks get |
|---|---|
| `none` (default) | No revision. The runtime reads the heuristic description implicitly, as every run did before the flag. |
| `derived` | Mockingbird's own heuristic (tier-0) description, read with `get_world` and written back as an explicit revision (author `user`). The runtime is meant to answer exactly as with `none` (the step 3 plan's "tier 0 must change nothing"), so a gap between the two is a runtime bug, not a description effect. |
| `agent` | A description a coding agent wrote from the contract alone, before any suite ran, written as a revision with author `agent`. `agent` minus `derived` is what the agent's understanding adds. |

**How the agent writes it.** For each contract of the selected suites, `world_author.py` starts a private `mockingbird serve` with that contract alone (fresh SQLite, free ports, no LLM profile, so nothing reaches OpenRouter) and a working directory holding only a copy of the contract and the Mockingbird skills (`mockingbird agent skills .claude/skills`). In that directory it runs a headless Claude Code, the way a user's coding agent works with the Mockingbird plugin:

```sh
claude -p "<prompt>" --model claude-opus-5-5 --output-format stream-json --verbose \
  --restricted --strict-mcp-config \
  --mcp-config '{"mcpServers":{"mockingbird":{"command":"<binary>","args":["--admin-url","<admin>","mcp"],"env":{"MB_DATA_URL":"<data plane>"}}}}' \
  --tools Read,Grep,Glob --allowedTools Read,Grep,Glob,mcp__mockingbird__get_world,... \
  --disallowedTools mcp__mockingbird__import_contract,... \
  --permission-prompts none --no-session-persistence --max-budget-usd 5 [--bare]
```

The prompt names the contract file and the mock and asks for the `mockingbird-world` skill's loop: read `get_world` and its gaps, write with `patch_world`/`put_world` and `author: "agent"`, read `refused` and fix it, optionally try entries with `call_mock`. It names no suite, journey or check. `--restricted` confines Read, Grep and Glob to the working directory and ignores user and project settings. Bash, web and agent tools are not available. The Mockingbird MCP server is the only MCP server, and only its read, world and `call_mock`/request-log tools are allowed (no imports, deletes, servers, LLM profiles or key setup). Every other Mockingbird tool is in `--disallowedTools`, read from `mockingbird mcp`'s own tool list. `MB_DATA_URL` points `call_mock` at the authoring server's data plane. Without it, `call_mock` would go to a server on the default port. So the agent writes only through Mockingbird's authoring interface, and it sees the contract and the skill, never the journeys, the checks, the engine or a past result. The agent's environment has no OpenRouter key: not `OPENROUTER_API_KEY`, no variable holding its value, and no other `*_API_KEY` but `ANTHROPIC_API_KEY`.

The bench checks isolation from the session's `system/init` event. When the session offers a built-in tool beyond Read, Grep and Glob, an MCP server other than `mockingbird`, or a plugin other than Claude Code's own built-in ones (source `<name>@builtin`), the authoring fails. Built-in plugins add no tools, as the tool check shows; their names are kept in the entry under `builtin_plugins`. The event's tools, MCP servers, skills and plugins are kept in the entry under `session`.

Two limits remain:
- `--restricted` still loads the user's own `~/.claude/CLAUDE.md`. `--author-isolation bare` adds `--bare`, which skips CLAUDE.md, auto-memory and hooks, but needs `ANTHROPIC_API_KEY` authentication.
- `call_mock` takes an optional `base_url`, so the agent could call another URL on the machine. Its prompt and the skill never point it anywhere but the mock. `--author stub` runs `stub_author.py` instead. It writes through the CLI (`mockingbird world show|patch --author agent`), restates the heuristic identities and sends one unknown operation to exercise a refusal. It costs nothing, carries no knowledge of the API, and is for dry runs only.

**What is recorded.** Each contract's result is cached as `--world-cache` (default `docs/benchmarks/world-cache`)`/<author id>/<contract sha256>.json`, next to the agent's stream-json transcript (`.transcript.jsonl`; both are scanned for `sk-or-` before they are written). A successful entry keeps none of the agent's text: its closing summary is the transcript's result event, and its stderr is kept only in a failed entry. The author id is `claude-code~<model>~p<prompt version>`. `--author-model` defaults to a full id (`claude-opus-5-5`), not an alias, so a new model release is never mistaken for a cache hit. Each entry also records the sha256 of the skills Mockingbird installs and of the world schema (`inputs`). A different contract, model, prompt, skill text or schema is therefore authored again, while a rerun reads the cache and pays nothing. Concurrent runs that need the same contract (`run.py --parallel` models, two terminals) take a lock per contract: the first authors it, and the others wait and read the cache. A failed authoring is kept as `<sha>.failed.json` and is never read back, so the next run tries again. Failure means a non-zero exit, an error result, a timeout, or an isolation problem. In the run that hit the failure, applying it fails the suite (`suite_error`) rather than silently running the heuristics. The entry holds:

- the cost (`total_cost_usd` from Claude Code), duration, turns and token usage;
- every world write's answer from the transcript: `revision` and `refused` entries (`path`, `code`, `message`), or the problem of a whole-document refusal, which stores nothing (an answer that is not JSON is `ok: null`, unknown rather than failed);
- every revision the agent stored;
- the accepted description: `document`, the newest revision's overlay;
- the gaps before and after authoring, the refused entries left at the end, each entry's author, and the effective description.

`--refresh` authors again. The stored transcript drops session ids and machine paths.

**The committed cache.** `docs/benchmarks/world-cache` is committed with the authored descriptions of blind11, blind12 and blind13 (the replay gate's agent tier runs on them). Only the `<author id>/<contract sha256>.json` entries are committed: the directory's `.gitignore` keeps out the transcripts, the failed attempts and the locks, and `test_replay.py` fails when the tracked files hold anything else, an entry that keeps the agent's text, or a finding of the scan. Commit new entries with the run that authored them, after scanning exactly the files you add:

```sh
python3 scripts/llm-bench/world_author.py --scan $(git diff --cached --name-only -- docs/benchmarks/world-cache)
```

The scan flags `sk-` keys, an Authorization or Bearer token other than an obvious placeholder (`Bearer test`, `bench-placeholder`), well-known vendor key shapes and private keys, a long value of a field named like a key or password, and any email address outside the reserved domains (`example.*`, `.test`, `.invalid`, `.localhost`) and the bench's own. `--world-cache-only` (on `server_suites.py`, and what `replay.py --world agent` passes) never authors: each description is read from the cache whatever its recorded `inputs`, nothing is locked or written there, and a contract with no entry stops the run.

During a run, `<out>/world-authoring.jsonl` gets one summary row per contract (`cached` true on a hit, with the first authoring's cost and time). `<out>/world-applied.jsonl` gets one row per (model, suite, mock) with the revision the write made on the suite's mock and the entries the server refused then (the runtime's validator may differ from the one at authoring time). A write counts only once the server says the running mock serves it (`runtime: mounted` in the answer of the world write): a `pending` write is sent again, up to `WORLD_WRITE_ATTEMPTS` (3) times, and a mock that never serves it fails the suite, so no call is measured on the previous description. The row keeps `runtime`. A description the server refuses as a whole fails the suite (`suite_error`). Rows of a run with a world carry `"world": "<tier>"` in `server.jsonl` (rows with no `world` are `none`). The proxy label and the server log are `<slug>~<suite>@<tier>`, so the ledger keeps the tiers' LLM spend apart.

**Aggregate.** `aggregate.py` keys the journeys table by `<suite>@<tier>`. The scored blocks read `none` rows only: consistency, SSE, import, and the ledger's reliability, latency and cost (so Q, the gates and Value too). A `--world` run in the same directory therefore changes no score. Its LLM calls are reported per tier under `world.ledger`. `server.worlds` in `results.json`, and a table in section 8 of `tables.md`, put each suite's ok rate under `none`, `derived` and `agent` side by side for each model. `world` in `results.json` and the table after it list each contract's latest authoring: cost, minutes, turns, writes, failed writes, entries refused in writes, refused at the end, gaps before and after, and the error if it failed. The totals count every authoring that ran in the directory, including a `--refresh`, but not cache hits. A tier that failed to apply shows its suite errors.

**Running it.** Author ahead of the suites (optional; `--world agent` authors whatever is not cached), then run the three tiers. Use the same model, suites, repeat and jobs for each:

```sh
python3 scripts/llm-bench/world_author.py --suite journeys_blind11 --out $OUT          # authoring only
for w in none derived agent; do
  python3 scripts/llm-bench/server_suites.py --model $MODEL --proxy-base $PROXY --out $OUT \
    --suite journeys_blind11 --repeat 3 --jobs 5 --world $w
done
python3 scripts/llm-bench/aggregate.py --out $OUT
```

`run.py full --world agent` passes the flag on to every model's server suites, with `--author`, `--author-model`, `--author-isolation`, `--world-cache` and `--refresh-world` (sent as `--refresh`). Under `--journey`, only the named journeys' contracts are authored and applied. The default suites (`consistency`, `sse`) would author the full Stripe, TMDB and Square specs, so name the suites you want measured. The headline is the `agent` tier on a blind set that was never diagnosed, judged against `derived` on the same model and providers. A dry run needs no spend: `fake_llm.py` stands in for the proxy (`--proxy-base http://127.0.0.1:<its port>`) and `--author stub --world-cache <scratch dir>` stands in for the agent.

## Replay gate

A regression that is deterministic given the model's answers (a check answered from stored state going from pass to fail after an engine change) does not need a paid run to be found. `replay.py gate` runs the journeys suites against recorded LLM answers, offline and with no key, and compares each check with the recording's result. The `Replay gate` workflow runs it on every pull request that touches `crates/mb-protocols`, `crates/mb-engine`, `crates/mb-import`, `crates/mb-state`, `crates/mb-store`, `crates/mb-llm`, `scripts/llm-bench` or `docs/benchmarks/world-cache`, on both world tiers (`--world none --world agent`), and `scripts/gate.sh` runs it locally for the same paths (on the release binary it builds first, which the bench's Python tests also get as `MB_BENCH_BINARY`).

```sh
cargo build --release -p mockingbird-cli
python3 scripts/llm-bench/replay.py gate [--world none] [--world agent] [--suite journeys_blind6] [--keep] [--report verdict.json]
```

**World tiers.** A recording is made on one world tier (`record --world none|agent`, default `none`). The `agent` tier runs every mock with its committed description from `docs/benchmarks/world-cache` (`server_suites.py --world agent --world-cache-only`): the description comes from the cache, is never authored during `record` or `gate`, and a contract with no cached description fails its suite. Its recordings are a set of their own, `recordings/<model slug>~<suite>@agent.json.gz` (the proxy label carries `@agent`), with `"world": "agent"`, and their results are the `server.jsonl` rows of that world. `gate` replays the tiers named by `--world` (default `none`, so the `none` recordings and their verdicts are unchanged); the workflow and `scripts/gate.sh` name both. A suite that reports no result at all (a server that did not start, a world cache miss) fails the gate rather than masking its checks as dirt.

**Recordings.** `recordings/<model slug>~<suite>.json.gz` holds, for rep 0 of one (model, suite) run: every LLM call's journey, operation, order and prompt hash with the answer the model gave (`content`, `finish_reason`, or the error status), and the run's per-check results (`case` -> `ok`). It holds no prompt, no header and no key: `test_replay.py` scans every committed recording for an Authorization header and for any `sk-or-` string, and `replay.py scan` does the same on demand. The recorder drops anything shaped like an OpenRouter key from what it writes.

**How a call is answered.** The gate starts `proxy.py --replay recordings/`, which never opens an upstream connection and never reads the key, and runs `server_suites.py --repeat 1` against it, which tags journeys (`--tag-journeys`, the default since it makes every run seedable; `--no-tag-journeys` turns it off). Tagging gives each mock its own copy of the LLM profile that sends `x-bench-journey: <mock>`, posts a mark (`POST /bench/mark`) before each journey rep so the proxy knows the rep, runs a journey's reps one after another, and seeds the faker (`faker_seed: 1`) so a fallback answers the same each run. An engine change can change the prompt, so a call is matched in this order:

| match | rule |
|---|---|
| `exact` | the same prompt hash (messages and `response_format`, timestamps blanked) in the same label, on a recorded call not yet used |
| `key` | the same (journey, rep, operation, n-th call of that operation in the journey) |
| `reused` | the same prompt hash as a recorded call already used: the journey asks it more often than when recorded, so that answer is given again |
| `nearest` | the recorded call of the same operation closest in order, in the same journey if it has one |
| `none` | no call of that operation: a 503 whose message starts `REPLAY_UNMATCHED`, which the engine answers with its fallback |

The operation is the prompt's `Operation:` line (else `HTTP:`, else the `response_format` schema name). A replayed answer's timestamps (ISO strings, and Unix times in fields named like `created` or `*_at`) move by the time between the recording's clock and the replay's, fixed per journey at its first call, so a check of "created recently" holds a week later and a timestamp two answers share stays equal. Exact matches are fewer than you might expect: the engine makes up the part of an id the model's answer leaves out of its pattern, so later prompts differ; key matches carry those journeys.

**The verdict.** Per check of the recording:

- **regressed**: passed in the recording, fails (or is missing) now, and its journey is clean: every LLM call of it matched `exact` or `key`, each operation was called as many times as when recorded, and every recorded call of it was used. The gate fails. A suite with one is replayed again (`--confirm`, default 2 re-runs) and a check counts only when it regressed every time, since the engine's own randomness can flip a check once.
- **drift-masked**: the same in a dirty journey: some call matched only `reused`, `nearest` or `none`, an operation was called more or fewer times than when recorded, or a recorded call went unused. The model may have been asked something new, and once a journey makes one extra call of an operation every later key match of it is off by one (the n-th call gets the answer recorded for another), so nothing in it can be pinned on the engine. Reported with the reasons, never a failure.
- **improved**: failed in the recording, passes now. Reported.
- **unstable**: listed in the recording's `unstable`, never compared. When a recording is made, it is replayed `--calibrate` times (default 4) on the binary that made it, and every check whose result differs from the recorded one in any replay is marked unstable. Calibration also lists the journeys that are dirty on that same binary (`baseline_dirty` in the recording, printed by `record`): the gate can never hold their checks, so a journey there wants a look (nondeterminism in the journey or in its tagging) before the recording is committed.
- **expected to change**: listed in the recording's `expected_change` (`replay.py expect <recording> '<journey>.<check>'`), never compared, until the recording is made again.

A journey can be dirty on an unchanged binary when the engine itself is not deterministic. `fake_llm.py` answers a string with a simple `pattern` (digits only, fixed prefixes, character classes with quantifiers, anchors, alternation, taking a later branch when the first cannot meet the length bounds) with a value that matches it, at most 4096 characters and within a fixed amount of work per pattern (a pattern it cannot meet in that keeps the plain `valN`), so the engine does not patch in an id of its own. Before that (and before the engine's repairs were seeded, in #275), it drew the patched id at random, not from `faker_seed`: `journeys_blind6` zohobooks got `invoice_id` `val11` against `^[0-9]+$`, and whether the patched id was short decided how many `getInvoice` calls went to the LLM (5 recorded, 7 in most replays). Two cases remain in the free seed, both from ids the engine makes up when the fake's answer repeats one (the fake answers the same id for every create in a journey, since its values depend only on the schema). `journeys_blind4` digitalocean sometimes answers `POST /v2/tags/{tag}/resources` from state instead of asking the LLM (about 1 gate run in 5), so it is listed in that recording's `baseline_dirty` and its checks are masked when it happens. `journeys_blind10` `pagerduty.a resolved incident frees its key` passes only when the engine gives the re-triggered incident a new id instead of the fake's repeated one; it flipped in about 1 gate run in 4 and is marked `unstable` (record with `--calibrate 30` so calibration sees it flip).

A server that does not start, or a suite that breaks, fails the gate too. The table lists, per suite, the checks, recorded and replayed passes, the four counts, the dirty journeys and the calls per match kind; each dirty journey is then listed with why.

**When the gate is red on purpose.** A change that is meant to alter what a recorded check returns re-records in the same pull request: `replay.py record --fake` for the free seed. A paid recording is re-recorded on the next paid run; until then, mark each check that legitimately changes with `replay.py expect <recording> '<journey>.<check>'`, commit the recording and name the checks in the pull request (or delete that recording, and say so).

**Recording.** Re-recording happens only on a recording run, never in the gate.

```sh
# The free seed: fake_llm.py answers every call, recorded as model bench/fake-llm.
# --calibrate 30 is what the committed seed was calibrated with (see above): 30 free replays, so it runs far longer than one gate.
python3 scripts/llm-bench/replay.py record --fake --calibrate 30
# The agent tier's free seed: every journeys suite with cached descriptions (blind11-13)
python3 scripts/llm-bench/replay.py record --fake --world agent --calibrate 30

# A paid recording: one rep of every journeys suite through the budget-guarded proxy
source ~/.zshenv >/dev/null 2>&1   # OPENROUTER_API_KEY, never printed
python3 scripts/llm-bench/replay.py record --model deepseek/deepseek-v4.1-flash-1017 \
  --budget-usd 1.5 --prices docs/benchmarks/<latest run>/roster.json [--suite journeys_blind6 ...]
```

**Budget for a paid recording.** One rep of all 14 journeys suites on one model costs about $0.2: the last full run of the default model on all 14 suites at `--repeat 4` cost $0.75. `--budget-usd` defaults to 1.5, about 7× that, because the proxy also reserves an estimate for every call in flight (the 14 suites run at once, `--jobs` journeys each) and a pricier model costs more. Pass `--prices`: without roster prices the proxy reserves each call at its high fallback rates (4096 × $40 per M output tokens, about $0.16 a call), and ten calls in flight trip a $1.5 budget at once. Raise `--budget-usd` for a pricier model, from its pilot projection.

**What `record` refuses to pack.** `pack` (and `record`, which runs it) exits 1 and writes no recording when the run is not one the model answered in full:

- the proxy wrote `BUDGET_TRIPPED` (next to the raw file or the ledger);
- a call in the raw recording or the ledger has a status other than 200, a 402 (`error_kind: budget`, which reaches only the ledger), or any other error kind, such as an in-stream `stream_error` behind a 200 head, `timeout`, `provider_unavailable` or a client hang-up (499). Only `refusal` and `empty`, the model's own answers, are kept;
- a check in `server.jsonl` is labelled `detail.infra` or `detail.infra_cascade` (judged on a provider failure).

Such a recording would hold faker fallbacks as the model's answers, and the gate would then protect the wrong results. Re-run with a larger budget, or later for a provider outage. `replay.py pack --ledger <calls.jsonl>` applies the same checks to a hand-packed run.

**The scan fails closed.** `replay.py scan` (and `record`'s last step) flags an Authorization header shape anywhere in a recording, answers included. A model answer that legitimately carries an authorization field with a scheme (`"Authorization": "Bearer ..."`, also `Basic` or `Token`, in any quoting) therefore fails the scan, and `record` exits 1: do not commit that recording; drop that suite from the run, or re-record. An API's own `authorizations` field, or an `authorization` field without a scheme, does not match.

`record` starts `proxy.py --record`, which forwards each call as usual (budget, pins, ledger) and also appends the call's journey tag and answer to a raw file; it runs the suites once with `--tag-journeys`, then `replay.py pack` joins the raw file with `server.jsonl` into `recordings/` (or refuses, as above, and `record` stops there), calibrates, prints the journeys dirty at baseline, and scans the result. Only the proxy gets the key; `server_suites.py` and the server get a placeholder. The paid run's cost is about one rep of each suite (see the budget above): check the pilot projection for the model first. Commit the new `recordings/*.json.gz` with the run.

The recordings committed now are the free seed (`source: "fake_llm.py"`, model `bench/fake-llm`). Its answers are schema-shaped values, so its passing checks are mostly the ones the engine answers from state: reads of what a write stored, lists that hold a created item, deletes that leave a 404. That is what the gate protects first. The 2026-10-30 dumps under `docs/benchmarks` (`exchanges.jsonl.gz`) predate the journey tags and many engine changes, so they cannot seed it. A paid recording adds the checks that pass only with a real model's answers.

### Seeding from a run's dump

Every paid run can seed the gate without a second, recording run. `server_suites.py` tags journeys by default and the proxy's `--dump` keeps each call's tag, so the dump and the run's `server.jsonl` pack into recordings:

```sh
# run.py full: the dump and the ledger sit in $OUT, each model's server.jsonl under $OUT/server/<model slug>
python3 scripts/llm-bench/replay.py pack-dump $OUT/exchanges.jsonl $OUT/server/<model slug>/server.jsonl \
  --rep 0 [--source "paid run 2026-11-06 via OpenRouter"]
```

It writes one recording per journeys suite (`JOURNEY_SUITES`, and world tier) of that model with results in `server.jsonl`, for the rep given; the calls of the run's other suites are in the dump too, and it skips them and names them on stderr. It refuses as `pack` does (the ledger defaults to `calls.jsonl` next to the dump, where `run.py` puts it), and also when a dumped call has no tag (a dump from before tagging, or a run with `--no-tag-journeys`). Calibrate before committing: the recording has none of `record`'s calibration, so replay it with `gate` a few times on the run's binary, then `expect` or drop what flips.

## Testing without spend

Both scripts accept a hidden `--upstream URL` flag that points the proxy at a fake chat endpoint. With it, `run.py` skips the key calls. `fake_llm.py` can stand in for OpenRouter:

```sh
python3 scripts/llm-bench/fake_llm.py --port 18999 &
env -u OPENROUTER_API_KEY python3 scripts/llm-bench/run.py pilot --out /tmp/bench-test \
  --models a/x,b/y --upstream http://127.0.0.1:18999/api/v1/chat/completions
```

`test_replay.py` tests the matching (`reused` included), the shift of timestamps, the comparison and what makes a journey dirty, the baseline report of calibration, `expect`, packing and its refusals, the world tiers, `pack-dump` from a tagged proxy dump, default tagging, the security scan, the committed world cache (entries only, scanned clean, a cache hit for blind11-13) and the proxy's replay mode (with every upstream connection patched to fail). Its end-to-end tests record the `journeys` suite against `fake_llm.py`, replay it green, then claim a failing check passed and expect the gate to fail, and record `journeys_blind11` on the agent tier, replay it green with `--world agent` and expect a gate on an empty world cache to fail; it runs when the release binary is built (`target/release/mockingbird`, `$CARGO_TARGET_DIR/release/mockingbird` or `MB_BENCH_BINARY`).

`python3 -m unittest scripts/llm-bench/test_world.py` tests the `--world` mode with fakes only: transcript parsing, the agent's blind tool set and environment, the cache, applying each tier, the row and label changes, and the aggregate split. One end-to-end test runs `stub_author.py` against a real `mockingbird serve` when `target/release/mockingbird` is built.
