# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Added

- World description revisions in the control store: `ControlStore::add_world_revision`, `list_world_revisions`, `get_world_revision` and `latest_world_revision` keep numbered revisions (from 1) of each contract version's authored world overlay, with its author. A write can name the revision it expects as the newest and gets a `Conflict` otherwise. Revisions go with their contract version and with the mock. Store migration `1300_world_revisions` adds the table. Nothing reads them yet; no mock answers differently.
- World description types (`mb_mcm::world`): a `World` of type and operation descriptions (identity, parent, lifecycle and soft delete, unique members, concurrency, derived counts and sums; operation kind, target, request and answer pointers, transition, changes, scope, filters, order, paging, idempotency, not-found status), `overlay` for entry-by-entry overriding, RFC 6901 `Pointer` parsing, the `Author` tiers (`heuristic`, `agent`, `llm`, `user`), and the published JSON Schema `world.v1.json` (`mb_mcm::world::SCHEMA`). Unknown keys are kept so they can be refused by name. Nothing reads it yet; no mock answers differently.
- World description validation (`mb_mcm::world::validate`): each entry of a description is checked against the compiled contract (operations and types exist; members are properties of the type's record schema, found through answer pointers and `$ref`s; parameters, headers and statuses are declared; request and answer pointers land inside their schemas, and `records` on an array). Entries that resolve apply; the rest are refused by JSON pointer as `unknown_key`, `unresolved`, `not_applicable` (e.g. a header on a GraphQL operation) or `invalid`. `check_size` refuses documents over 256 KiB or nested deeper than 32. `Bundle::resolve` follows `$ref`s into the bundle's definitions. Nothing reads it yet; no mock answers differently.
- Tier-0 world descriptions (`mb_import::world::tier0`): what the import heuristics already put in a bundle, restated as a world description: each operation's kind and resource type, its target (the identity's path parameter, or the request body field non-HTTP operations name the record by), where its answer holds the record, and each type's identity member (of the id fields its operations name, its reads' first, the first that is a member of its record). It validates cleanly on every contract in `examples/apis` and `scripts/llm-bench/contracts`. The gap report (`mb_protocols::world_gaps::gaps`) lists what a description leaves open: written types with no identity, reads, updates, deletes and actions with no target, create and update answers whose record could not be found, HTTP routes that are not served (with the router's message), and entries refused at validation. `OpKind::of` gives the kind the contract gives an operation. Nothing reads them yet; no mock answers differently.
- World description validation takes a type's record schema from its first operation with an identity when it has no read, before its first operation (often a list envelope), and, when composed branches both declare a member, from the branch that says what it is rather than one that allows anything (an envelope's `result: {}`).
- World description validation visits each schema once per lookup, so a contract whose composition refers back to itself (`A = {anyOf: [{$ref: A}, {$ref: A}, {$ref: A}]}`) no longer takes seconds to minutes per member. A `unique` set whose `scope` is not a member of the record is refused; a `transition` on a type with no lifecycle is refused; `conflict` and `not_found` statuses on non-HTTP operations are `not_applicable`; a `target`, `request`, `answer` or `concurrency` whose every entry was refused is dropped instead of kept empty. That includes one whose only keys are unknown (a typo such as `target: {path_parm: ...}`), which was kept as an empty object. A description over 256 KiB is refused as `too_large` (no longer `invalid`, which stays for one nested too deep). Path and query parameters and request headers are found through `allOf`, `anyOf` and `oneOf` in the operation's inputs, as body members already were. A `records` answer pointer refused as not landing on an array no longer stands in for the record, so valid members of that type are not refused with it. `Bundle::resolve` follows refs into a definition's interior (`#/$defs/Folder/properties/meta`, as imports write them), so members, parameters and pointers behind such refs resolve.
- A looping LLM reply is stopped early and retried once (`limits.repetition_guard`, on by default; `llm.profiles.<name>.repetition_guard` turns it off per profile). Some models fall into a loop and write it until `max_tokens`: `0_0_0_…`, one line repeated hundreds of times, or a few short pieces shuffled, each costing ~16k tokens and tens of seconds before the faker answered anyway. The client now streams every call and watches the answer and the reasoning; once the text has been of low variety (at most 256 distinct 8-byte sequences per 8 KiB) throughout `limits.repetition_guard_span` bytes (32 KiB by default) it closes the stream and sends the same request once more. A retry that loops too falls back with `LLM output repeated itself: provider …, aborted after about N tokens`, without salvaging or repairing the looped text. It knows nothing of JSON, the API or the model, and leaves shorter low-variety answers (seat maps, enum arrays, bitmaps, placeholder items) alone. Streamed calls without a usage chunk are charged an estimate; a stream that just stops is a retried transport error; an endpoint refusing `stream` gets plain requests; a profile whose `extra_body` sets `stream` or `n` is not streamed. New metric `mb_llm_cut_replies_total{reason}` counts replies cut at `max_tokens` and replies stopped for looping. Store migration `1200_profile_repetition_guard` adds the profile column ([configuration](docs/configuration.md#limits)).
- Concurrency tokens are tied by evidence, not only by the contract's wording, and are read from request headers. With an LLM and `consistency: on`, on HTTP routes, a write declaring a `409` or `412` now also treats as a token a top-level member of the stored record that: `If-Match` holds (an RFC 9110 entity-tag list, quoted tags kept whole and compared by opaque value, so `W/"3"` matches `"3"`), for a string member the server manages (`readOnly`, or set by no create or update); another declared header holds whole, for a member the server manages, once the client is seen to track it as it moves (a header that stays the same while the member moves never pairs); or its body or query requires as the only member of the record the write declares (the `{version, actions}` shape) or that the client is seen to track (it sent back the value the member moved to; `readOnly` alone ties nothing), that no create sets and the request echoes. Once an update was seen to change it, a stale value is refused with the declared `412`/`409` before the LLM, its error body filled from the contract; an integer body token is stale only when lower. A successful update advances it: the model's new value stands over the stored copy's, and an `If-Match` token the model left as it was is minted anew in the same format (no other token is). That token is served in a declared `ETag` response header, and any delete of the record forgets its tokens. `If-Match: *`, requests with no token, first writes, records nothing stores, untracked headers, and members the client sets are left to the LLM ([concepts](docs/concepts.md#sessions-and-state)).
- A create that repeats a value the contract says is unique is refused, whatever the LLM answered, when the evidence is structural. With an LLM and `consistency: on`, on HTTP routes, a create answered `2xx` although its prompt listed a stored record of its type holding the same value under the same member (`<same_values>`) is answered with its declared `409` instead, storing nothing and dropping its effects, when that `409`'s own response description names the member in code position and nothing else there ("A widget with this `sku` exists."), and the record, read back, still holds the value and is in the create's collection. A `400`, `412` or `422` (validation as often as uniqueness, "The `sku` is malformed."), a `409` naming the member in prose or beside another code, sentences of the operation's or the API's description, another collection, another value and a record gone since leave the LLM's answer: the refusal stays an offer, and the mock's own refusals of those statuses still get the contract's code.
- A `409` whose description names a member in code position is treated as that member's uniqueness conflict, whatever else it says: "The `email` must be verified before a widget is made." refuses a create repeating a stored record's email. Structure cannot tell such a conflict from a duplicate.
- An answer to a create under a stored record's id that holds the value the create repeats is never refused and stores nothing: it is served as answered when every member it shares with the stored record agrees (an "it exists" answer, `existing: true` beside it), else as the stored record, unchanged. A create asking for a taken id is answered the same way, where an agreeing answer used to be replaced by the offered refusal.
- Refusal bodies carry the error code the contract gives them. A refusal offered to the LLM whose declared statuses share one JSON error schema asks for its body too, as `"refusal_body"` beside `"refusal"`; a body valid against the response's schema is served, keeping what it chose (only members it left empty take the contract's values), else the faker's as before. A refusal body Mockingbird builds takes the values the contract names: besides a member named in code position, a member named as a plain word (`the code `product_invalid_sku``, `code 1001` for a number, never the status itself), a value belonging to the member named nearest before it in its sentence; a member with no `enum` whose own schema description lists codes in code position ("Such as `ConcurrentModification`, `ResourceNotFound`…") taking the one of them the status's description names alone, as an enum's; and for the mock's own refusal of a repeat (never an LLM's), a sentence of the API description (`info.description`) holding that status as its only status number and naming the repeated member, no other request member, and the type created (`refused with 400 and `api_error_code` `duplicate_entry``). Where the prose names the repeated request member, an error-body member of that name takes nothing from it.
- Writes on a parent's other routes reach its lists, and writes answering no body get effects. With an LLM and `consistency: on`, on HTTP routes: a 2xx write is also kept for the list reads one level under its path's parent (the path through its last parameter, then literal segments only) and told to them as `<earlier_writes>`, as a write to a list's own route is. Only lists one segment under the parent: one whose segment the write's route ends in (`POST /lists/{id}/relationships/profiles` and `GET /lists/{id}/profiles`, not `/lists/{id}/archived/profiles`) is told what the request's schema and the list's items declare of the body; for a write on the parent itself, one whose segment a body member holding an object or a list names by stem, at most two deep (`PUT /tickets/{id}` with `ticket.comment`, to `/tickets/{id}/comments`), is told only that member. Only told, never forced. A 2xx write whose declared answer has no body, shown records besides its target, is now asked in one call for its effects alone (`{"effects": [...], "response": null}`), with no repair round, and they apply under the guards every answer's effects pass (counted by `mb_bodyless_effects_calls_total{outcome}`); a delete, a write shown nothing, and a client's retry (a `PUT` or `DELETE`, or a `POST` with an `Idempotency-Key` header, repeating the session's latest 2xx write within 30 seconds, kept with the session's internal state) still make no call, and such a retry is remembered once. A delete of a record the session held is now told to the parent its path names, naming that record, so that parent's next read catches up (counts, membership).
- Stale versions are refused before the LLM, where the contract says writes are checked. With an LLM and `consistency: on`, on HTTP routes, an update or a delete sending a body member with another value than the record's current one is answered with its declared `409` (else `412`), changing nothing and with no LLM call, when that `409` or `412` names the member in code position in its description, the server manages it (`readOnly` in the record's read, or settable by no create or update of the type, in its body or query), it is an integer or a string with no `enum` or `const` and no identity or path member, and an update was seen to change it. Such a member the request's body or query sets no new value for advances with the model's answer, even when `readOnly`; nothing else of a request is replaced, and identity and owner stay. Counters, timestamps, states, members an error schema merely declares (a problem's `title`), members the write sets (a duplicate `name`), first writes, requests with no token, other sessions and operations declaring neither status are left to the LLM ([concepts](docs/concepts.md#sessions-and-state)).
- Error bodies Mockingbird builds itself take the values the contract names. A refusal (an LLM's, a repeated create's, a stale write's) and the `404` of a missing or deleted record are still faker-filled, but each scalar member then takes its schema's `const` or one `enum` value, else a value this status's description names in backticks or `<code>` (when the member's `enum` holds it alone, or the description names the member, such as `error.code`, followed in the same sentence by one value only that is no member name), else its example where no other status's response shares that schema. The HTTP status reflected in a problem's `status` stays, a value that breaks the schema is not taken, and other members keep the faker's value.
- A list whose next page is a URL in the answer reaches it. With an LLM and `consistency: on`, on HTTP routes, a page cut short (or full, while the session holds more records it asks for) of a list not paged by number or offset, whose contract has no text member pairing a query parameter for its token but one URL member for the next page (a string with `format: uri`, `uri-reference`, `url`, `iri` or `iri-reference`, or described as a URL or URI, beside the list or in objects beside it, at most three names deep, with a name on its path that is `next` or starts with the word `next`: HAL's `_links.next.href`, Bitbucket's `next`, JSON:API's `links.next`, `next_page_url`, `@odata.nextLink`), gets the URL of its next page there. The cursor is a free-text query parameter the request does not carry, that is no page size, names no member of the items and has no `format` or `pattern`, found in this order: the one a link of this very request the LLM wrote outside the list (its `self`, showing every value of the request's query) carries empty, as a first page's cursor; the one of several words sharing its first word with a page size of several words (`page[cursor]` beside `page[size]`); the one whose description names the `next` member in backticks, or that the `next` member's own description (not a shared link schema's) names in backticks or as a query key (`from=`). Prose never ties one, nor does a filter the `self` link carries with a value. None, two, or two URL members write nothing. The URL is the mock's own, as the request reached it (scheme and host as the WSDL addresses take them, with `X-Forwarded-*` when trusted, the mount prefix and the request's path as sent), never the host the LLM wrote, with the request's query and the token under the cursor. A `null` link object is written as a copy of a link beside it (HAL's `self`, for its `type`). Following the URL serves the next page from the kept items as a token does; the last page's link is `null`, or left out, where the answer allows. A URL the LLM gave to another page of the route (`?page=2`), or carrying the cursor, stays as it is.
- Lists paged by a page number or an offset reach their later pages. With an LLM and `consistency: on`, on HTTP routes, a list whose query declares an integer parameter beside its page size with `default` and `minimum` both `1` (a page number) or both `0` (an offset), confirmed by the contract (the answer declares one integer member named as it beside the list or in an object beside it, such as Zoho's `page_context.page` or Box's `offset`, or the parameter is named `page` or `offset`), keeps its first page when that page leaves items out: items the page size cut, or the session's records a full page does not show, under the same rules a cursor token's rest follows (the type's sole unscoped list, the path's collection, filters, projections, number parameters). Every first page answered replaces the kept one. A later page (`page=2`, `offset=1`) on the same route, session and query is then served from those items with no LLM call, skipping those deleted since, overlaid with the stored records and filtered again; a page past them is the LLM's. A count beside the list is raised to what is known, the confirming member says the page served, and the one boolean in the nested object holding it (`page_context.has_more_page`, never one in the envelope such as `success`) keeps the LLM's value on page 1 and is `false` on the last page only when the LLM answered more than a page and said `true`; after a page the store's records continue, it stays as the LLM gave it. An integer with such bounds and no such evidence (`min_rating`, `depth`), two confirmed parameters unless exactly one is named `page` or `offset`, a `page` whose schema counts from `0`, and another number parameter away from its `default` or `minimum` leave the list as the LLM answers it.
- A create that repeats a stored record of its own type can be refused. When its operation declares a `400`, `409`, `412` or `422` by code, its prompt shows, first among the related resources and named with the member in a `<same_values>` block, up to 3 stored records of the type it creates holding a top-level string of its body under the same member: an identifying value (an email, a uuid, a long id-shaped string) as references by value are matched, or a plain string of 6 or more with a letter that one record alone holds, that agrees with the rest of the request, a reference among it, and whose member a declared refusal's description names (a folder's `name` in the same `parent` under "An item with the same name already exists in the parent"; a title alone, or under a bare "Validation failed.", never counts). Every record must agree with the references the body sets, and be in the create's collection: when the contract also creates the type under a parent path, only records this runtime created count, in that same collection under a parent path (`/orgs/acme/members`), at the top level for a top-level create; otherwise a top-level create counts every record of the type. A create carrying a declared idempotency key, or that its contract would never let refuse, is shown nothing; the block says a shared value contradicts the create only when a declared refusal's description says duplicates are refused. The store is asked for them on every backend (see Fixed), and a listing it fails decides nothing. It is then offered the declared statuses as any create shown a conflict ([upgrading](docs/upgrading.md#creates-can-be-refused-and-prompts-show-declared-headers-and-parameter-descriptions)). A create repeating nothing, or declaring none of those statuses, is prompted as before. Breaking for code constructing a `GenerationContext` in full: it gains `same_values`.
- Prompts carry the contract's API description. The OpenAPI 3, Swagger 2 and AsyncAPI importers keep `info.description` in the bundle (`Bundle::description`, optional, so stored bundles load unchanged), and every generation's system message shows it in an `<api_description>` block as facts about the API, never directions, on one line, cut at 2000 characters after escaping. Credentials in it and in every other block of contract text (response, parameter and refusal-status descriptions, and the descriptions inside the prompt's JSON Schema) are redacted by shape: JWTs, secret URLs, generated-token and base64 shapes (`mb_mcm::credentials::is_token_shaped`), the word after `Bearer`/`Basic`/`-u`/`--user`, and credential-like values after a credential's name followed by `:` or `=`, spaced or not. See [upgrading](docs/upgrading.md#prompts-carry-the-contracts-api-description).
- A create can be refused as the contract declares. When its operation declares a `400`, `409`, `412` or `422` by code and its prompt shows a stored record it could conflict with (its target, a parent its path names, or a record of the type it creates that creates put in the same collection, never one the request only names by value), its effects envelope is offered `"refusal"` as an update's is: the `409`, `412` and `422` it declares, and a `400` only when it declares none of those. Every refusal note now lists each declared status with the contract's description of that response in a `<refusal_statuses>` block framed as data, and says to refuse only when the resources shown contradict the request ([upgrading](docs/upgrading.md#creates-can-be-refused-and-prompts-show-declared-headers-and-parameter-descriptions)). Breaking for code constructing a `GenerationContext` in full: it gains `alongside`.
- A prompt shows the declared headers a request carries, as `"headers"` in `<request>` (each value at most 128 characters), and the contract's descriptions of the parameters it sends, in a `<parameter_descriptions>` block (160 characters each, 1200 in all). A header an API-key scheme names, one the credential checks hide by name, schema (`writeOnly`, `format: password`, beside a `$ref` too) or value, transport headers and `X-Mockingbird-*` are never shown, and a read's cache key includes the headers shown; a bundle compiled before this release shows no header until recompiled. A query value an API-key scheme names, whose schema is marked secret or whose name is a credential's is no longer shown in `<request>`, with any data-plane auth mode, and a header or query parameter an API-key scheme names is no longer kept in the request record, in `none` mode too. The OpenAPI 3 and Swagger 2.0 importers keep a parameter's own `description` on its schema (beside a `$ref` too) and every API-key name the security schemes declare as `Bundle::api_key_names`. A request with none of these gets the prompt it did. A member whose schema has `writeOnly` or `format: password` beside a `$ref` is now kept out of write memory as well. Breaking for code constructing a `Bundle` in full: it gains `api_key_names: Option<Vec<ApiKeyName>>`.

- Records stay consistent after related writes. On an HTTP route, with an LLM and `consistency: on`, a 2xx create now also tells the held records its request refers to by value: a value of its body, or of its path beyond the parent, that holds a digit or a separator (or is a whole number of at least 100000) and is a held record's stored id or a path field known to hold it, by the same matching that shows a request's references to its generation. What the generated answer says names nothing. A reply naming the message it answers, or a refund at `/refunds` naming its payment, makes that record's next read generate once, as a create under a parent's path already did for the parent. Such a record is never rewritten wholesale: that read is offered the effects envelope, only the effects its answer lists on that record apply, validated as any effect, and it answers the stored copy as it then stands. A parent under the path keeps its catch-up. At most 4 records per create, found within 8 store reads; none an applied effect of the answer changed. The read catching up with a create, parent or referenced, is shown the records the waiting creates made, in a `<new_resources>` block after the rest (taken out of `<related_resources>`, which tells a list answer to keep them unchanged), so a count, a total or a status can move ([upgrading](docs/upgrading.md#related-writes-bring-their-records-up-to-date)).
- An update whose LLM answer settles on its stored target is told, in one sentence, that what the answer changes beyond what the request names is kept only when listed as effects.

- A prompt shows where a value the mock minted came from. On an HTTP route, with an LLM and `consistency: on`, a generated 2xx create or action whose answer holds a string under a member named as a credential (`access_token`, `public_token`, `link_token`, not `key` or `sid`), or shaped like one, that its request did not send, in its body, query, path or `Authorization: Bearer` header, is remembered by a hash of that value, with the answer and its request as context may show them: what their schemas declare, past the wider name and shape checks, so the value itself and a client's secret are left out, as is any string holding one of them. A later request carrying the value, or sending it as a bearer token, is shown that answer and request in an `<earlier_origins>` block, as what may have changed, so a Plaid `access_token` brings the `item_id` it was exchanged for. At most 8 answers per session are kept and 3 shown, each up to 4 KiB, under the reserved state type: not exported or counted, and cleared by a session reset ([upgrading](docs/upgrading.md#prompts-show-where-a-minted-value-came-from-and-a-write-can-be-refused)).
- A write on the target record the model was shown, not a create, can be refused as the contract declares. When the operation declares a `400`, `409`, `412` or `422` response, the effects envelope may carry `"refusal": <status>`, one of those, and the engine answers that declared error, faker-filled, with no effects and no second LLM call; a body the faker could not make valid is served as `fallback`, with its reason. A status the operation does not declare is ignored, and an operation declaring none of them is asked for exactly what it was. Not offered with a forced status or a scenario.
- `StateStore::touch_live` refreshes a live session and says whether it was live, never creating one. Its default, for test doubles, touches and answers `true`; the memory, SQL, Redis and caching stores implement it.
- `mb_state::UNLISTED_ID`: a session holding that internal document and no resource is left out of `StateStore::sessions` and `session_count` on every backend.
- Lists and lookups agree with the session, from the contract alone. With an LLM and `consistency: on`, on HTTP routes: a generated list answer keeps only the items whose member a query parameter names (by its name, in any case, or by stem: `To` for `to`, `generations` for `generation`) and holds another value, when the parameter and the member declare the same one type (text, integer or boolean, not a real number or a `const`), the value is one the member's `enum` and asserted `format` allow (`status=all` beside an `enum` without `all` filters nothing), the parameter's own `enum`, if it has one, has a member `enum` beside it, and the parameter is not a bare `id`. A comma-separated value is a set only when every part is in the `enum`. A text member with no `enum`, `format` or `pattern` keeps the items whose value contains the requested one, ignoring case, so `name=Ann` keeps `Anna`; a value holding a digit (an id, a phone number, a code) matches whole, ignoring case, so `owner_id=u1` does not keep `u10`. A value is trimmed first, one left empty filters nothing, and one that came with a leading space and a digit also matches with a `+`, as an unencoded `+` decodes to a space. A search's `q`, ranges and items missing the member are left alone. The list's main array is then cut to the page size the request asks for, by the signal the output budget reads. Each step is kept only when the answer still validates and keeps its `minItems`; a count that clearly belongs to the list goes down by what the filter took out, as for a deleted id, and a page size leaves it. Of the 77 list routes of `examples/apis`, 16 get a filter and 38 a page size, 40 in all. The page size a name gives, without a `maximum` tying it to an array, is now the whole normalized name only (`limit`, `per_page`, `page_size`, `max_results`, `size`, `first`, `top`), never a part of one, so `topic_id`, `desktop`, `first_seen` and `image_size` set neither the output budget's page nor a cap. A delete of a stored record also marks, by hash, the text of its identity and of the members a lookup of its type keys on, those a list read's required query parameter names (Auth0's `email`; never an optional filter such as `state`), under a bound of 1024 of their own, so a lookup naming that value (`/users-by-email?email=`) drops an item the session does not hold that carries it, where the model made up a new user with the deleted one's email; storing a record with that value again clears the mark. And a create or a read under a parent path (`/captures/{id}/refund`) is shown, as related resources and scrubbed as they are, the newest 4 records creates put under that same path, so a second refund sees the first; a generated read of one record by its path (`/captures/{id}`, a catch-up too) is shown the same of what creates put under it, so a capture's read sees its refunds. Nothing is added to an answer, there are as many LLM calls as before, and `consistency: off`, offline mocks and GraphQL are unchanged ([upgrading](docs/upgrading.md#lists-and-lookups-agree-with-the-session)). `mockingbird-engine` gains `budget::requested_page` and `consistency::list_member`, and `consistency::item_schema` is public.
- A prompt shows what a request refers to and who the caller is, from the contract and what the session holds, with no per-API rule. On an HTTP route, with an LLM and `consistency: on`: a body or query value that could be an id (6 to 128 bytes with no space and a digit or a separator, or a whole number of at least 100000) is looked up as the stored id of the types an effect can name, or a path field a write was seen to hold, and a hit joins the related resources, following none of its own references, so a write is offered effects on it, which go on the stored copy. An effect cannot write the redaction marker, here or anywhere: a member holding it stays as stored. `reactions.add` with `timestamp` and a reply with `thread_ts` reach their Slack message, where they found nothing. A word-only id such as `closed` is not matched, and a date can be. At most 8 values, 32 store reads and 6 records per generated call. A `GET` route with no path or query parameters answering a single object (`/users/@me`, `auth.test`) has what its read declares of its answer, scrubbed, at most 2 KiB and the newest 3 kept for the session, shown to later generations, its own route's too, in an `<earlier_answers>` block as what the API said and may have changed. A write on that route answering the read's schema replaces its answer, any other forgets it, and so does deleting the record it is the identity of. A write that stored no record of a list's type (`POST /users/{id}/roles` answering 204) is kept for its path and told to that path's list read in an `<earlier_writes>` block, as what may have changed, the newest 5: its route and the members of its body that its request schema or the list's items declare, past the name and shape checks, never its query. Deleting the path's parent forgets them, and deleting a child forgets the writes naming it. These three leave out what wider checks than a request record's find: credential names (`pass`, `pwd`, `passphrase`, `jwt`, `otp`, `hmac`, `signature`, `license_key`, `card_number`, `credit_card`, `ssn`, `salt`, `mfa`, `recovery_code`, `connection_string`, `dsn`, and as a last word `key` and `sid`, unless they are a type's identity and the type is not itself a credential), URLs with a password or a credential-named parameter, JWTs, `Bearer ` values, and a pair labelled as a credential, whole. All of this only adds to a prompt: there are as many LLM calls as before, and with nothing to show a prompt is the same to the byte. `consistency: off`, offline mocks, GraphQL, gRPC, SOAP and SSE are unchanged.
- Mocks remember a write's request when its answer did not show it. After a 2xx write on an HTTP route, with an LLM and `consistency: on`, a 204 update's members that the read's schema declares (not identity, path or `readOnly` members, and not into an object under a `oneOf` or `anyOf`) are merged into the stored copy when the result validates, and what could not be applied is kept, with the route template, the operation and a scrubbed body, for the resource it targets. So is a create answering less than its read and not holding what the request said, and an action not shown on its target. A create or an action answering nothing also tells the nearest parent its path names and the session holds; an update or a delete of a child does not. A merged update or a remembered action publishes a change of its resource; telling a parent publishes nothing. The resource's next generation is shown the requests in an `<earlier_requests>` block, and a read that could have answered `state`, with or without a query, generates to catch up, replaces the stored copy and forgets them, so the next read is `state`: the stored copy fills what the answer omits at any depth, the latest write's own body stands when that was an update or a create (last write wins; older bodies, and a child's or an action's, are only told), identity and path fields are kept, and an answer that stops showing its owner counts as a failed attempt. An update answering its read's schema, or an effect that applied, needs no such read. Costs: one state read per generation or read by id on an LLM mock, and one LLM call per batch of remembered writes that succeeds. A failing catch-up tries twice, each up to two LLM calls, answering with a servable stored copy or else the faker, then stops until a later write, which the request record notes under `request.effects`. Concurrent reads can each generate; concurrent writes to one resource can lose a request (no lock). Newest 5 requests per resource, 16 KiB, bodies cut at 4 KiB. `writeOnly` and `format: password`, then credential-named members and name/value pairs (one shared predicate, `mb_mcm::credentials`, which also now decides for headers and import redaction), the mock's credential names, the request log's `redact_fields` and the PII scrubber apply; a path's values are not kept. It is stored under a reserved type (no migration, no config key, no Admin API change), cleared with the session and absent from exports, counts, seeds and change feeds; an `x-mockingbird-resource` naming that type gets an `invalid_resource_extension` warning. GraphQL, gRPC, SOAP, streams and offline mocks are unchanged ([state](docs/concepts.md#sessions-and-state), [upgrading](docs/upgrading.md#write-memory)). Breaking for code constructing a `GenerationContext` in full: it gains `earlier_requests` and `earlier_own_body`. `mb_state::INTERNAL_TYPE`, `mb_engine::REDACTED`, `Engine::scrub` and a defaulted `RequestRecorder::redact` are new.

- A write's LLM answer can change related resources: a command with a stored target or related resources is asked for `{"effects": [{"type", "id", "set"}], "response": ...}`, deciding the changes first, with both members required in the schema sent, since a provider enforcing it writes only what it requires (a plain answer, or one with no `effects`, still counts, at no extra cost), and each effect, at most 10, is merged into the resource it names in that session when the resource exists, its `id`, `number` and identity field are left alone and the result matches its schema. An order's `customer` then reads back from `GET /customers/{id}` with source `state`. A route whose last parameter names no field (`/repos/{owner}/{repo}`, `/users/{username}`) also finds a stored resource by its `name`, `login`, `slug` or `key`; a stored `full_name` must end with `{owner}/{repo}` on a route ending in two parameters ([state](docs/concepts.md)). - `mockingbird-auth`, `mockingbird-admin`: every public type implements `Debug`, and none prints a secret: `OidcClient` (and `WebAuth`, `AdminState`) show neither the client secret nor pending logins, `ApiKeys`, `SessionManager` and `Authenticator` show only their settings. `Problem` implements `Display` (`404 Not Found: …`) and `std::error::Error`, and so does `channels::ChannelControlError` (its `Partial` error's source is the failure that stopped the publish). `Role` implements `Display` and `FromStr` (an unknown name is a `ParseRoleError`); `KeyScope` and `PrincipalKind` implement `Display`, and `PrincipalKind::as_str` gives its wire name. ### Changed

- Prompts carry more of the contract. A response's `description` is shown under its status in a `<response_description>` block framed as data, not instructions, on one line, escaped and cut to 160 characters like the schema's descriptions, unless it is only the status's reason phrase (`OK`, `Not Found`); OpenAPI 3 and Swagger 2.0 imports keep it as the new `OutputVariant::description`. A query parameter, or a member of a body that is not an update's, that the request leaves out and whose schema declares a `default` is shown in a `<request_defaults>` block, except a page size as the output budget reads one (a `limit` defaulting to 100 would read as asking for 100 items) and what the credential checks hide by name or shape; and a create's answer reflects a body default as it reflects the body, so a create leaving out `generation` with `default: legacy` answers `legacy`; a scenario's `set` still wins. With neither, nothing is added, though the next entry changes the system message of every call. Stored bundles need a recompile to show descriptions ([upgrading](docs/upgrading.md#prompts-carry-response-descriptions-and-request-defaults)). Breaking for code constructing an `OutputVariant` in full: add `description: None`.
- The system prompt allows an empty list: a list or search that nothing plausibly matches may answer `[]` where the schema allows it, and 3 to 5 items stay the default otherwise.
- The output budget leaves out the deepest required members first, then the heaviest, and keeps an array item's only object member whose schema requires an `id` or `uri` of its own while anything else can go instead: a playlist entry keeps its `track`, and the track's `album` goes instead, where the faker filled a random track. When nothing else fits the budget, that member goes too, as before.
- A create's, or an action's new record's, generated id is redrawn as a taken id is when the request carries it, in its path (other than a create's own path id) or as a string in its body (other than a member named as its identity), and the session holds a record of another type under it (looking in at most 32 types, with `consistency: on`): a new message no longer takes the id of the channel it names. Another type's id the request does not name is kept (user `42` held, a new account `42` stays `42`), and so is a value the request carries that is no held record's (`POST /b {"name": "my-bucket"}` answered `{"id": "my-bucket"}`).
- Prompts no longer tell an action that a status moves, since not every action does and not every resource has one, and an action answering something else is asked for its target's change only if it changes anything. Models told a `validate` succeeded set `status` to `validated`, a value the contract did not allow, every time; now about half keep the status ([results](docs/benchmarks/action-note-2026-10-31/README.md)).
- **Action routes come from the contract's structure, not the spelling of the path.** The rule that a tail ending in `s` is a collection is gone, so `/{id}/process` and `/{id}/address` are no longer collections. A `POST` under `<static>/{param}` whose successes declare no body acts on the parent and stores nothing, even with a `GET` beside it (Jira's `transitions`, Auth0's user `roles`), over a read verb, or under a longer static tail, and sends no webhook unless the contract gives it a payload. A declared `201` is a record of its own, also with no identity (when it stores nothing). An answer of the parent's own schema is an update whatever the status, and the runtime decides: with a stored parent, an LLM answer with another identity is a new record of the parent's type stored under its own id, which a stored record keeps if it holds that id (the answer takes a fresh id and a number past those stored, and is served unstored, with no webhook or effects, if no id can be drawn), with the parent untouched and a `created` webhook (`POST /comments/{id}/replies`), while the target's identity or none updates the parent (PayPal's `POST /orders/{id}/capture`). This depends on the model: a reply got a new id 8 of 8 times on Luna and the default model and at most 2 of 8 on Lightning. An answer another resource's `GET` serves by path is created under that route's type and identity (PayPal's `captures/{id}/refund` now creates `refunds`). A `200` nothing reads acts on the parent. A format suffix no longer hides a detail route. See [upgrading](docs/upgrading.md#action-routes-come-from-the-contracts-structure).
- **Action routes act on their parent resource.** A `POST <static>/{param}/<verb>` the contract shows acting on its parent (`POST /v1/payment_intents/{intent}/confirm`; see the entry above for how that is read) compiled as a create on a type named `confirm`, so it invented a new id and never touched the intent. It now takes its resource type from `<static>` and its identity from `{param}`. When it answers what `GET <static>/{param}` answers it is an update, whose LLM answer wins over the stored resource and is what later reads return (a faker answer leaves the stored values), unless the LLM's answer carries another identity, when it is a new record stored under that id with the resource untouched. Otherwise it is `Effect::Other`: the resource is prompt context, nothing is stored, and the answer keeps its own `id` unless a member is named for the parameter (`bookingId`, `intent`; a bare `{id}` names nothing there, so the answer of a `POST /orders/{id}/ship` that stays an action keeps its own `id`). Webhook event types follow (`confirm.created` becomes `payment_intent.updated`). Stored bundles need a recompile to pick this up ([upgrading](docs/upgrading.md#action-routes-act-on-their-parent-resource)). `mockingbird-mcm` gains `Operation::is_action` and `is_generic_id`.
- **`output_mode` now defaults to `json_schema`.** Answers are generated against the response schema, which raised first-try validity with `deepseek/deepseek-v4.1-flash-1017` from 66% to 99%, with median latency rising from 1.9 s to 2.2 s. Free-text strings in the sent schema carry a 2,000-character limit, because a model could otherwise loop in one until `max_tokens`. A schema the provider rejects is asked for in JSON mode, with a warning, instead of failing the call, and an empty answer is tried once more in JSON mode. An array answer is asked for as `{"items": [...]}` in this mode too, so a snapshot of one replays through its operation key, not its exact prompt; re-record if you need exact matches. The `openrouter` preset uses this mode too. Profiles already stored through the Admin API keep the mode they have. To keep the old behaviour elsewhere, set `output_mode: json_object`.
- Local patching keeps more of the LLM's answer. A value breaking a pattern or length keeps the characters that fit, and a replaced identifier also changes where the answer repeats it as a whole token, such as inside a URL or a secret. Errors inside `anyOf` and `oneOf` are now patched in the branch needing the fewest fixes instead of costing a repair call, unless that would change a `const` or `enum` member.
- The default LLM model is `deepseek/deepseek-v4.1-flash-1017`, on `MB_LLM_MODEL` and the `openrouter` preset, instead of `deepseek/deepseek-v4.1-flash`. A config that names a model keeps it; to keep the old one, set `MB_LLM_MODEL=deepseek/deepseek-v4.1-flash`, or pass `--model deepseek/deepseek-v4.1-flash` with `--provider openrouter`. This model is a dated snapshot: if OpenRouter retires it, calls fail with the provider's error and mocks fall back to the faker (`X-Mockingbird-Fallback-Reason` says why, `mockingbird llm test` exits 1), with no switch to another model unless the profile sets `fallback` ([benchmarks](docs/benchmarks.md)).
- Event channels and webhooks use the per-call provider policy too, instead of always the mock's configured profile. Broker and WebSocket replies and trigger messages (scheduled, cron, state change) ask the policy with their tenancy: a WebSocket client's from its upgrade, otherwise the `TenantResolver`'s for the channel's operation id and, for a broker reply, the consumed message's headers, falling back to tenant `default` for the policy when the resolver refuses. A broker reply's usage event is now attributed to that tenancy (it was resolved without the message's headers). A webhook payload uses the profile chosen for the call that sent it. A policy's refusal skips that one message with a warning, a `PUBLISH` record with its status, a publish error in the channel's activity and metrics, and a `not_generated` usage event; the consumer or trigger carries on. The self-hosted defaults (`SingleTenant`, `ConfiguredProfile`) choose the same tenant and profile as before and build no second engine. Manual publishes still use the configured profile ([event channels](docs/events.md)). No public API changes.

- A changed LLM profile rebuilds only the mocks that use it, on every node, instead of every mock: those naming it, those naming none while it is the default, those whose fallback chain reaches it, those whose calls the provider policy sent to it (their cached engine for it is dropped with the runtime), and those whose last build failed. A change of `llm.default_profile` rebuilds only the mocks naming no profile. Workspace changes and resyncs still rebuild every mock. `MockRegistry` gains `reload_profile` and `reload_default_profile_mocks`.
- The provider policy (`mb-ext` `ProviderPolicy`) is asked for every call with the call's tenancy, as its documentation said, instead of once per mock build as tenant `default`. Data-plane calls ask it after admission; a profile other than the configured one generates with that profile's provider chain, built on first use and kept for the mock (until the mock or a profile changes); a rejection is answered as the call's problem (`application/problem+json`, its status and `Retry-After`), like a quota's, instead of failing the mock's build. Imports and draft previews resolve their tenant through the `TenantResolver` (operation `import` or `draft`, the Admin API request's headers, the request's workspace) instead of always billing tenant `default`; the import worker bills the tenant its job was created for, and a resolver's or policy's refusal is the request's problem. The self-hosted defaults (`SingleTenant`, `ConfiguredProfile`) choose the same tenant and profile as before, so single-tenant servers see no change: no new configuration, and no second provider is ever built. `mb-ext` gains no API. New, additive: `mb_protocols::ProfileEngines`, `MockRuntime::{configured_profile, profile_engines, engine_for}`, `mb_admin::LlmAccessError` with the defaulted `LlmResolver::{import_llm_for, preview_engine_for}`, and `mockingbird::runtime::{import_provider_for, preview_engine_for}`.
- `mockingbird-cli`: `server::binds_for` (a `(bool, bool, bool)` tuple) and `Snapshot::open(dir, replay, record)` are deprecated in favour of `Binds::for_role` and `Snapshot::open_with`. `ServeError::Other`'s `Display` shows the error's own message instead of the whole chain (`{e:#}`); the causes are its `source()`.
- `mockingbird-import`: `validate_triggers` and `FetchPolicy::from_allowlist`, which return `String` errors, are deprecated in favour of `check_triggers` and `FetchPolicy::parse_allowlist`, which return typed errors with the same messages. The `smart` submodules that only this crate's tests use (`chunk`, `complete`, `embedded`, `har`, `infer`, `llm`, `paths`, `postman`, `text`) are hidden from the docs; they become private in 0.2.

- API keys are verified from a short-lived cache instead of a control-store read on every call: data-plane calls to `data_plane_auth: api_key` mocks and Admin API calls with a key read the store once per key every 5 seconds (10,000 checks on SQLite: 36 to 0.9 µs each), and concurrent calls write `last_used_at` once. A revocation through the Admin API applies at once on that node; other nodes of a cluster can accept the key for up to 5 seconds ([API keys](docs/console.md#api-keys)). `mb_auth::ApiKeys::with_cache`, `ApiKeys::invalidate_caches`, `DEFAULT_API_KEY_CACHE_TTL` and `StoreDataPlaneKeys::with_keys` expose it; `ApiKeys::new` and `StoreDataPlaneKeys::new` still read the store every time.
- Generated answers are checked against the `format`s the faker produces (`uuid`, `date-time`, `date`, `time`, `email`, `uri`, `ipv4`, `ipv6`, `hostname`): a value breaking one (an LLM's `"createdAt": "yesterday"`) is refilled locally and the answer is `repaired`, without a repair call. A value equal to a request path or query value is kept, so a path id echoed into a `format: uuid` field survives. Other formats, and request validation, keep `format` as an annotation. `SchemaValidator::for_output`, `is_valid_output` and `patch_keeping` are new.
- `mockingbird-llm`: `OpenAiCompatible::reasoning_off` is deprecated in favour of `with_reasoning_disabled`, which does the same.
- LLM answers are read from the first complete JSON value in the reply (after the whole text and a Markdown fence) instead of the text from the first `{` to the last `}`, so two objects back to back (`{..}{..}`) or trailing prose with braces no longer make the answer unparseable. A value nested in a broken or truncated answer is never taken for the answer (a truncated reply still goes to repair), and an empty `{}` or `[]` in prose loses to a later value.
- The `json_schema` profile key, `MB_LLM_JSON_SCHEMA` and `--json-schema` are deprecated aliases of `output_mode` (`true` is `json_schema`, `false` `json_object`); setting both keys (or both `configure_llm` arguments) is an error, as is an unknown `MB_LLM_OUTPUT_MODE`. The Admin API still reports `json_schema` beside `output_mode`, and a stored `output_mode` that contradicts the `json_schema` flag (written by an older node during a rolling upgrade) reads as the flag. `mockingbird-cli`'s `LlmEnv::from_env` is deprecated in favour of `try_from_env`, which rejects an invalid `MB_LLM_OUTPUT_MODE`.
- A faker answer that matches no schema-valid draw (a schema the faker cannot satisfy, such as one relying on `not`) says so: its `X-Mockingbird-Fallback-Reason` ends with `faker output does not validate against the schema` (`mb_engine::FAKER_INVALID_REASON`). It was served as if valid.
- An offline answer without a body (a `204`) is labelled `X-Mockingbird-Source: fallback` with the offline reason; it was labelled `llm`.
- A scenario's `set` is checked when it is written: with an active contract, `PUT …/scenarios/{name}` answers `422 Invalid scenario` naming the pointer (`set/total fits no response the scenario can select (getOrder 200: …)`) when no response the scenario can select accepts a key present in `set`, and the config file is refused at load the same way. Such a `set` was dropped at request time with only a WARN. Absent keys and `required` are not checked, and `null` is always accepted. `mb_admin::invalid_scenario_set` holds the shared check.
- Audit webhook: a failing event is retried in the background (at most 64 at once) instead of holding up the queue, so one event's 7 s of backoff no longer delays every event behind it (the next event went out after 0.7 s with a 100 ms backoff base, now after about 2 ms). First attempts keep the queue's order, but a retried event can now arrive after later ones; order by the event `id`.
- Admin API reads fetch less from the store: listing mocks reads every active version number in one query instead of one full contract per mock (100 mocks with 256 KiB contracts: 10 to 1.0 ms on SQLite, 23 to 1.1 ms on Postgres); listing contract versions and `requests?fields=summary` no longer read sources and bodies (500 entries with 32 KiB bodies: 365 to 5 ms on SQLite, 481 to 13 ms on Postgres); drafts, channels, scenarios and uploads read the active bundle without its source, and a draft's parse and diff run off the async runtime; scenario validation checks operation names through hash sets (5,000 operations: 86 to 16 ms). `mockingbird-store` gains defaulted `ControlStore` methods for this (`active_versions`, `active_bundle`, `list_contract_version_infos`, `latest_contract_version`, `list_request_log_summaries`) and the `ActiveBundle`, `ContractVersionInfo` and `RequestLogSummary` types.
- The gRPC service conflict check (contract uploads and activation, and config reload against mocks managed through the API) reads the other mocks' active bundles 64 per query instead of one query per mock, and config reload no longer reads their sources (500 mocks on SQLite: 30 to 15 ms). `mockingbird-store` gains a defaulted `ControlStore::active_bundles`.
- `mockingbird` serve and proxy do less per change and per request, with the same results: queued control changes are applied once per mock (a burst of 100 changes to one mock: 26 to 2 ms until the next change is mounted); a reload of every mock builds 8 at a time in name order (40 mocks with 2 ms store reads: 316 to 39 ms); the proxy's claimed-host check is one set lookup (10,000 hosts: 1.5 ms to 86 ns); request-log records are not copied when nobody tails the log, and their redaction and truncation no longer allocate per key or hold the whole serialized body (a 10 MB response: 73 to 61 ms); HA state-change announcements are published from a queue of their own, so a slow bus no longer delays this node's change feed (500 changes with a 1 ms bus: 1.26 s to 1 ms); the request-log relay of another node lists the mocks at most once a second for entries of an unknown mock (200 lookups: 152 to 1.2 ms); and `serve --record` holds each answer once (10,000 answers to one prompt: 796 to 7.6 ms). The proxy now remembers at most 500 unmapped hosts: past them, new hosts are not logged and are counted as `host="other"` in `mb_proxy_unmapped_requests_total` (and `mockingbird report`) instead of adding a series each ([proxy](docs/proxy.md)).
- SQLite request-log pruning deletes by an id range on the `(mock_id, id)` index instead of `NOT IN` the kept rows, so its cost no longer grows with the retention (100 appends with one prune at a retention of 100,000: 46 to 12.5 ms).
- The response engine does less per answer, with the same answers: faker answers reuse each schema's definitions, cost table and compiled patterns (an offline answer 108 to 60 µs), persona templates are matched without compiling a regex per object (a 1,000-item list 26 to 0.4 ms), local patches fake from the validator's schema instead of copying its definitions per error (a 12-error patch 1.1 to 0.28 ms), validity checks stop at the first error, and the budget-shape caches are bounded across contract uploads. `SchemaValidator` gains `is_valid` and `declared_property_names`.
- `vault:` secrets: concurrent cache misses on one reference share a single Vault read (16 concurrent resolves of two references made 16 requests, now 2), and expired values are evicted when a new one is cached instead of staying in memory. Failed reads are still not cached.
- Session state hot paths: the in-memory store keeps each session's resources per type in recency order, so a list reads only the items it returns and reads share the session lock (a 20-item list in a 10,000-resource session, 77 µs to 3.2 µs, flat in the session size); the Redis store lists in one Lua round trip that pages the order set newest first and stops at the limit, instead of fetching every member of every type; and the response cache evicts its least recently used answer from a recency index instead of a scan (a put at capacity 5,000, 30 µs to 0.5 µs).
- Hot-path trims: `PrometheusUsage` shares each label value across its series and reuses status and source label text (about 240 instead of 390 to 500 ns per call without a recorder, 0.88 instead of 1.18 µs with a registry); the console serves embedded files without copying them per request; JSON found in a reasoning-only LLM reply is validated without being built (2.4x faster on 10 KB of reasoning); event channel lookups by id (manual publish, request-reply) use an index instead of a scan (300 channels: 1.6 µs to 0.2 µs).
- Reads by a path field that is not the stored id (GitHub's `GET …/issues/{issue_number}`) find a resource the mock wrote or seeded without scanning the session's resources of that type (500 stored issues, in-memory store: 316 to 1.4 µs per read); resources written elsewhere (the Admin API, another node) are still found by the scan. GraphQL root fields reuse the narrowed schema of a selection they saw before (bounded cache) and hash it for the response cache key without printing it (GitHub `viewer`, 12 fields: 48 to 7 µs per root field). Same answers.
- Imports do less on the async runtime, with the same results: HAR path templating accepts or rejects a group of response shapes from their sizes and shared keys before comparing pairs (2,000 sibling paths with 23-key responses: 463 ms to 6.4 ms); a draft save sizes its schemas once instead of twice, both that and the import worker's sizing run off the runtime, and so does the sniffing of a contract source download (once instead of twice, about 55 ms per MiB of YAML) and of an import upload with no kind. `mockingbird-import` gains `smart::assemble::schema_warnings_from`.

### Deprecated

- `mb_mcm::OperationKind::label` (use `as_str` or `Display`, same text), and `LocalBus::new`, `MemoryBusHub::new` and `GenerationLimiter::new`, which return an `Arc<Self>` (use `new_shared`; in 0.2.0 `new` will return `Self`).

### Fixed

- A route answering `allOf: [Envelope, {result: Record}]` over a base envelope whose `result` is a placeholder (`result: {}`) holds its record in `result`. `allOf` branches were merged last first, so the base's `{}` replaced the record schema and such routes had no identity: a `PUT` or a create was not stored, and a read was never served from state. A member two branches declare now keeps the schema that constrains it (`{}`, `properties: {}` and `additionalProperties: true` or `{}` add nothing); two that both declare members have them all, merged member by member; otherwise the later branch's is kept (a schema's own `properties` after its `allOf`). In the 65 contracts of the examples, fixtures and bench, only Cloudflare's zone and DNS-record routes change.
- With nothing held, an update or a create whose generated answer is an envelope the contract does not describe stores the record it holds: the one member of the answer (one level down) that suits the type, is not declared as another type's schema, and, for an update, carries the target's id (as its key or path member, or as any single value when the route has no identity), or, for a create, holds every single value the request sent that the type's schema declares. A create stores it as a mention: never over a held record or one the session deleted, and not as the record it made. An acknowledgement, a bodyless answer and an envelope with two such members still store nothing.
- The records one write stores read back in its order. A list answer's items, and the records an answer mentions (blocks appended in one call), were listed newest first among themselves too, so a later list's prompt showed them reversed. `StateStore::insert_seeded_all` stores them as one write: newer than anything before, and in their order among themselves, on every backend (its default inserts the last first, so the memory, SQL and Redis stores order them by their recency sequence).
- A write sending its records as a list of objects (`{"Contacts": [{...}]}`) no longer replaces the answer's list. Where the answer holds as many objects and each pair agrees on every single value both name, the request's items go onto the answer's item by item: the ids, statuses and times the answer assigned stay, and a member it lacks or holds as `null` takes the request's value. When a pair disagrees on a value (items listed in another order), an LLM's list stands as answered, and a faker's items take the request's values, keeping the ids they drew. Lists of another length are replaced as before.
- A read by `{ContactID}` answering `{Id, Status, Contacts: [Contact]}` reads the contact by its `ContactID`, the record being the array's one item (`record: {member_item: "Contacts"}`), instead of tying the parameter to the envelope's `Id`. It applies when the collection's own list (`GET /Contacts`, same type) answers that array member with the same item, the item of exactly one array member has a member of the parameter's very name that is the item's own key, and the envelope has no `id` and no member of that name; an order keyed by `id` whose lines refer to it by `order_id` stays the order. Among the 65 contracts above, only Xero's contact and contact-group routes change.
- Requests name a record by a member value on every store. The value index held only identities unless the store was local-only (the in-memory store, or a private in-memory SQLite database), so on a SQLite file, Postgres or Redis a ticket created with its contact's email never showed that contact. Member values are now indexed whatever the backend. On a store other processes may write to, a match the index finds is also checked against the store: the session's complete listing of the holder's type must show that record holding the value and no other, and so must the listing of each type whose read declares the member. A second holder, a listing of 500 records or more (which may be cut short, so a session holding that many of such a type matches nothing by member value there), or a failed read makes it no match. Sessions and workspaces stay apart.
- An owner tie reads a compound path parameter. A parameter whose name joins alternatives with `_or_` (`{organization_id_or_slug}`) names one thing by any of them: a stored record's `organization` member (the stem exactly, or followed by `_` or a capital: `organization_slug`, `organizationId`, not `organizations`), or one of its keys `organization_id` or `organization_slug` that the record's own type does not declare, holding the path's value shows it is that owner's, so a read by slug under its owner is served from state. Such a member holding another value (the owner's id, under a route given its slug) says nothing, as the path used another key. A follower's own `username` is not tied to `{user_id_or_username}`. A compound whose first alternative has no stem (`{id_or_name}`) stands for itself; `_or_` is the one separator read.
- A create's answer keeps the `id` the model got right when the contract keys the record apart. When the type's read schema, its record schema or the operation's own declared success answer declares both `id` and the one scalar member named for the type (`seat_id` of a `seats` record), and the answer holds that member, the answer's `id` may be another record's (the showing booked), as the schema describes; that id naming a held record of another type no longer gets it re-minted. A member only the answer holds keys nothing apart, and an id the session holds for the same type is still re-minted.
- GraphQL deletes leave a delete marker. A root delete by id (`commentDelete(id:)`) now marks the id as a REST delete does, unless its payload contradicts it (a non-empty `userErrors` or `errors` list, or a member naming the deleted record, `id`, a `deleted…Id` or `<type>Id`, that is `null` or another id; a Relay `clientMutationId` or a parent's id says nothing), and a root read of a marked id the session does not hold answers `null` with an error instead of a generated record. With an LLM and `consistency: on`; GraphQL lists and mentions are not checked against markers.
- A read of a missing or deleted record answers a declared `410` when the operation declares no `404` (a `4XX` range declares one) and no `default`. Any other status, a `403` included, keeps the problem+json `404`.
- A full list page whose query carries a value that is no filter no longer keeps the session's stored records off its next page. With an LLM and `consistency: on`, when the create that stored a record in this runtime carried the parameter (a scope such as `organization_id=…`), and the record is unchanged since but for this runtime's own writes of it, that alone decides: the same value lets it follow on the next page, another keeps it off whatever its text holds. Otherwise a record shows a value it holds whole, as before; or a value at the parameter's `default` asks nothing when neither the page nor any record holds the `default` or another of its `enum` values (`type=scheduled` beside an integer `type`, but not `show=open` beside records holding `open` or `done`); or, for a free-text parameter (a string with no `enum`, `const`, `format` or `pattern`) and a value of at least 3 characters holding no digit, a declared plain-text member of the item (no identity, no `format`) holds it, ignoring case (`q=walk`). A value no record holds whole and the mock cannot read, such as an expression (`filter=any(…)`), still keeps the records off, and the next page is the model's as before; a debug event now names the parameters that did. A page whose token or next link the model gave, while stored records the query asks for are left, now gets the mock's token or link for them, and the last of their pages carries the model's token or link on to the model's own pages, whose answer then leaves out the records already served and keeps its own token (or ends the list, when nothing else is left on it); its count is kept. Such a page now reads the store, as one without a token did. Nothing stored is changed. The runtime's in-memory record of where resources were written, when full, now drops its oldest quarter instead of everything.
- Member names a model writes with JSON around them are the declared ones. Models sometimes emit keys such as `"id:"`, `"System.Title:"`, `" .tag"` or `"indexedDocuments\":null},"`; in an object that allows other members these validated, so the declared member was missing (and a required one failed only where it was required). Before an answer is checked (and before any repair call), a key the schema does not declare is renamed to a declared one when, trimmed of ASCII whitespace and cut at its first `"`, `:`, `}` or `,`, it is exactly that one and what was cut off is JSON debris alone (punctuation; and `null`/`true`/`false`, numbers and quoted strings only after a `"` that closes the name); it is dropped when the object holds the declared member as well. A name of its own such as `name:en`, `id:alt`, `xmlns:foo`, `a,b`, `user:1` or `v:2.0` is kept, as is a key a `patternProperties` pattern matches. This goes through nested objects and array items, and through the `set` of an answer's effects, against the record's schema. A key is never renamed to one the schema does not declare, and the keys of a map (an object whose schema declares no members) are never touched.
- An effect setting a member to `null` no longer stores a null its schema does not admit. Such a null removes the member when it is optional, and rejects the whole effect when the member is required. Members of value objects inside the record follow the same rule, and in a `oneOf`/`anyOf` record what is required or nullable is read from the variant the held record matches.
- A record type whose schema requires no members no longer takes any object as one of its records. An object now suits a type only when at least one of its members is declared by the type's schema, or, for an object found in an answer, by the inline schema of the place it was found at (not a `$ref`, whose definition may be another type's). Since an inline object always holds members its own place declares, the check does not apply to objects at inline places named after a type, as before; before, a task acknowledging a settings update was stored, and later served, as the settings record. A type whose schema declares no members (`properties: {}`, a map) takes any object as before. An update's answer that does not suit its type, with no record held, is not stored as the record.
- The OpenAPI 3 and Swagger 2.0 importers read a key inside a path segment as the router serves it. A segment such as `customers({customer_id})` used to be the resource type itself, with no identity, so a record created under `/companies({company_id})/customers` and read at `/companies({company_id})/customers({customer_id})` was stored under two types, a delete left no marker, an update or read by key found nothing and a bound action (`/customers({id})/NS.post`) acted on nothing. Now an OData key with one parameter (`customers({customer_id})`, `customers('{id}')`) gives the type before its `(` and the identity a whole-segment parameter would; a composite key or a call with arguments (`lines(documentId={d},sequence={s})`, `NS.getBalance(asOf={date})`) gives its name and no identity, since none of its parts identifies a record alone, and after a keyed record such a call acts on that record; an update or delete whose route names no identity no longer falls back to such a part as its target id either, so `PATCH` of `(A,10000)` stores nothing under `10000` and a `DELETE` of `(B,10000)` leaves A's line; and a named key beside a collection (`/carts/key={key}`) is an alternate key of that collection (`carts`, found by `key`). A format suffix (`{name}.json`) changes nothing, and other text around a parameter (`{id}:archive`, `v{version}`) compiles as before. Contracts without such segments compile unchanged. See [how a resource's identity is read](docs/import.md#how-a-resources-identity-is-read).
- REST mocks route OData-style keys and other parameters inside a segment. Sibling paths below one key, such as `/companies({company_id})/customers({customer_id})` and `/companies({company_id})/salesInvoices({sales_invoice_id})`, used to be refused by the router (matchit), and the whole mock then failed to mount, so every call got a 404. The REST adapter now has its own router, a tree of segments: a segment may hold any number of parameters with literal text around and between them (`entity(key1={k1},key2={k2})`, `files/{name}.{ext}`, `items/{id}:archive`). Precedence is matchit's documented one (static text, then templates with more literal text first, then a whole-segment parameter, then a catch-all, decided at the first segment where matching routes differ). Wherever matchit matched a request the router picks the same operation and values, or, in the rare sets where matchit did not backtrack out of a template, one that precedence ranks higher; some requests matchit answered with a 404 now match (with `/files/{id}/{rev}` and `/files/{name}.json/meta`, `GET /files/f.json/7` reaches the first). Matching a segment takes time linear in its length, whatever the request. See [path matching](docs/protocols.md#path-matching).
- One route never keeps a mock from mounting. An operation whose path matches exactly the requests of an earlier one of the same method (`/items/{id}` and `/items/{itemId}`), or is no valid pattern, is left out with a warning naming the operation and route; the other operations are served. `mockingbird validate` prints the same warning. `RouteTable::new` and `RouteTable::with_base_paths` no longer fail and list what they left out in `RouteTable::skipped`; `http_rest::try_router` is replaced by `http_rest::router_and_skipped`, and `RouteError` has `Conflict` and `Invalid` variants instead of `Insert` (no more `matchit` type in the API).
- The WSDL importer keeps the contract's documentation, so the LLM prompt shows it as it shows an OpenAPI contract's. The `wsdl:documentation` of `definitions` and of each served service becomes the bundle's API description (`<api_description>`), a portType operation's and then its binding operation's becomes the operation's summary, and the `xs:annotation/xs:documentation` of an element, attribute, complexType or simpleType, and an rpc part's `wsdl:documentation`, becomes the converted schema's `description`. Whitespace is collapsed and XHTML markup in it is reduced to its text; `xs:appinfo` is ignored. Several `documentation` elements on one component (one per `xml:lang`) are joined; a text repeated exactly in the API description or summary is shown once. The usual caps and credential redaction apply. Contract prose in every prompt, for every protocol, now goes through the same escaping and credential redaction: the operation's and the channel's (AsyncAPI operation or webhook) `Summary:` line is put on one line and cut at 500 characters (`prompt::MAX_SUMMARY`), and each `Hints:` line (OpenAPI and Swagger operation descriptions, tags, AsyncAPI, GraphQL and proto descriptions) is cut at 1000 (`prompt::MAX_HINT`) and keeps its line breaks, so plain text reads as before. Names (the title, operation and channel ids and targets, paths, topics, message names and action verbs) have `<` and `>` escaped, `&` kept. A WSDL without documentation compiles as before; one with it shows it after it is imported again.
- A page's cursor the session served reaches the prompt though its name holds a credential's word. A query parameter such as Zoom's `next_page_token`, hidden as a credential by its name, is shown with its description only when it carries a value an earlier answer of the same operation in the session served at the member it is the cursor of: free text the contract does not mark secret, no security scheme names, of a list answer declaring one text member beside the list, or in an object beside it, that is the parameter or ends with its words (a one-word parameter only by its very name). What was served is kept per session as hashes, never values, the newest 64. A value the client made up, a name a security scheme carries, `format: password` or `writeOnly`, and a cursor of an answer with no list stay hidden, so `access_token`, `refresh_token`, `token` and `client_secret` stay out of the prompt though members of the answer are named as them. The model now sees which page a request asks for.
- A create never replaces a stored record of its type. A create whose body asks for its record's id under the type's identity field, a member its request schema declares and not `readOnly` (a client-chosen `id`, as Chargebee's `POST /customers` takes), when the session holds a record under that id in the collection the create runs in (under the same parent path; a record placed nowhere known counts only for a top-level create of a type never created under a parent), is shown that record first among the related resources and in `<same_values>` under the identity member, read by its key on every store, and so is offered its declared `400`, `409`, `412` or `422`; the refusal note adds that a second record cannot take the id. Answered as a success anyway, it stores nothing: the held record is kept, its effects are dropped (told rejected in the request record), no wrapped record or mention is stored, and nothing is remembered for it. Its answer agrees with the store: the refusal the prompt offered on that record (the first status the offer names, a `409` before a `412` or a `422`), rendered from the contract as an LLM's refusal is; with a forced status, a scenario, or no refusal declared or offered, the held record under the status answered, as an idempotent create answers; never the model's replacement. An `id` the request schema does not declare is no request for one: an answer echoing a held id is given a fresh one, as any taken id is. A create asking for an id held in another collection (another repository's label of the same name) is answered as generated but not stored over that record. A create carrying a declared idempotency key, which may be a retry, and an HTTP `PUT` (an upsert) are as before. A create's effects also never copy its request onto another record of its own type: from an effect on such a record, every member whose value repeats what the request gives that member (numbers by value; an object holding, at any depth, a value the request holds at the same place) is taken out and told rejected (Mollie's second payment no longer copies its amount onto the first, even onto payment `1` with an amount of `1`). The record's own id is copied as much as any value (a `parent_id` never makes a record its own parent). The rest of the effect applies (a reply's count on its thread, the old default no longer the default), as do effects on the created record and on records of other types (a parent's counter). Known follow-ups: a copy under a renamed member, a copy of a subset of an array, and objects that share a common nested value only (stripped as copies) are not told apart yet.
- Noun-first GraphQL mutations get their kind and resource: a mutation whose name has no verb prefix and ends in `create`, `update` or `delete` after a word boundary (an uppercase letter or `_`) is that write when the rest of the name, once singular, names exactly an object type of the schema with an `id` (`issueCreate`, `issueUpdate`, `commentDelete`, `productVariantDelete`, Shopify's `productCreate`). That type is its resource. A name whose rest names no such type (`undoDelete`, `DryRunDelete`, `bulkDelete`, `itemsToDelete`, `onCreate`) keeps the kind it had, as do other verbs (`orderCancel`, `notificationMarkRead`, `issueArchive`), queries, and gRPC and SOAP operations. A mutation with a verb prefix keeps its kind; when its payload has no `id` (`IssuePayload`, `DeletePayload`) and the name is `create`, `update` or `delete` and a record type the same way (`deleteComment`), its resource is that type instead of the payload's.
- A GraphQL update or delete acts on the stored record its `id` argument names even when its payload does not select it. After a 2xx answer generated for `issueUpdate(id:, input:) { success }` (or `updateIssue`), the members of its input objects that the stored record has or its type declares are merged over it, after what the answer held, so a later read from state sees them; `commentDelete(id:) { success }` removes the record. The record is looked up under the operation's resource type when the name writes that record (`issueUpdate`, `deleteComment`; `updateTeamMember` returning a `Team` writes nothing onto the team); an update whose resource type has no `id` falls back to the one object member of its payload with an `id` when the name writes that member's type (a `TeamMemberPayload { team }` of `updateTeamMember` writes nothing onto the team), and a delete never does (`productVariantDelete` leaves the payload's `product`). A mutation with no `id` argument, other kinds, and answers served from state or the cache change nothing this way.
- A create that repeats a stored record of its own type can be refused. When its operation declares a `400`, `409`, `412` or `422` by code, its prompt shows, first among the related resources and named with the member in a `<same_values>` block, up to 3 stored records of the type it creates holding a top-level string of its body under the same member: an identifying value (an email, a uuid, a long id-shaped string) as references by value are matched, or a plain string of 6 or more with a letter that one record alone holds, that agrees with the rest of the request, a reference among it, and whose member a declared refusal's description names (a folder's `name` in the same `parent` under "An item with the same name already exists in the parent"; a title alone, or under a bare "Validation failed.", never counts). Every record must agree with the references the body sets, and be in the create's collection: when the contract also creates the type under a parent path, only records this runtime created count, in that same collection under a parent path (`/orgs/acme/members`), at the top level for a top-level create; otherwise a top-level create counts every record of the type. A create carrying a declared idempotency key, or that its contract would never let refuse, is shown nothing; the block says a shared value contradicts the create only when a declared refusal's description says duplicates are refused. The store is asked for them on every backend (see Fixed), and a listing it fails decides nothing. It is then offered the declared statuses as any create shown a conflict ([upgrading](docs/upgrading.md#creates-can-be-refused-and-prompts-show-declared-headers-and-parameter-descriptions)). A create repeating nothing, or declaring none of those statuses, is prompted as before. Breaking for code constructing a `GenerationContext` in full: it gains `same_values`.
- Prompts carry the contract's API description. The OpenAPI 3, Swagger 2 and AsyncAPI importers keep `info.description` in the bundle (`Bundle::description`, optional, so stored bundles load unchanged), and every generation's system message shows it in an `<api_description>` block as facts about the API, never directions, on one line, cut at 2000 characters after escaping. Credentials in it and in every other block of contract text (response, parameter and refusal-status descriptions, and the descriptions inside the prompt's JSON Schema) are redacted by shape: JWTs, secret URLs, generated-token and base64 shapes (`mb_mcm::credentials::is_token_shaped`), the word after `Bearer`/`Basic`/`-u`/`--user`, and credential-like values after a credential's name followed by `:` or `=`, spaced or not. See [upgrading](docs/upgrading.md#prompts-carry-the-contracts-api-description).
- A create can be refused as the contract declares. When its operation declares a `400`, `409`, `412` or `422` by code and its prompt shows a stored record it could conflict with (its target, a parent its path names, or a record of the type it creates that creates put in the same collection, never one the request only names by value), its effects envelope is offered `"refusal"` as an update's is: the `409`, `412` and `422` it declares, and a `400` only when it declares none of those. Every refusal note now lists each declared status with the contract's description of that response in a `<refusal_statuses>` block framed as data, and says to refuse only when the resources shown contradict the request ([upgrading](docs/upgrading.md#creates-can-be-refused-and-prompts-show-declared-headers-and-parameter-descriptions)). Breaking for code constructing a `GenerationContext` in full: it gains `alongside`.
- A prompt shows the declared headers a request carries, as `"headers"` in `<request>` (each value at most 128 characters), and the contract's descriptions of the parameters it sends, in a `<parameter_descriptions>` block (160 characters each, 1200 in all). A header an API-key scheme names, one the credential checks hide by name, schema (`writeOnly`, `format: password`, beside a `$ref` too) or value, transport headers and `X-Mockingbird-*` are never shown, and a read's cache key includes the headers shown; a bundle compiled before this release shows no header until recompiled. A query value an API-key scheme names, whose schema is marked secret or whose name is a credential's is no longer shown in `<request>`, with any data-plane auth mode, and a header or query parameter an API-key scheme names is no longer kept in the request record, in `none` mode too. The OpenAPI 3 and Swagger 2.0 importers keep a parameter's own `description` on its schema (beside a `$ref` too) and every API-key name the security schemes declare as `Bundle::api_key_names`. A request with none of these gets the prompt it did. A member whose schema has `writeOnly` or `format: password` beside a `$ref` is now kept out of write memory as well. Breaking for code constructing a `Bundle` in full: it gains `api_key_names: Option<Vec<ApiKeyName>>`.

- Records stay consistent after related writes. On an HTTP route, with an LLM and `consistency: on`, a 2xx create now also tells the held records its request refers to by value: a value of its body, or of its path beyond the parent, that holds a digit or a separator (or is a whole number of at least 100000) and is a held record's stored id or a path field known to hold it, by the same matching that shows a request's references to its generation. What the generated answer says names nothing. A reply naming the message it answers, or a refund at `/refunds` naming its payment, makes that record's next read generate once, as a create under a parent's path already did for the parent. Such a record is never rewritten wholesale: that read is offered the effects envelope, only the effects its answer lists on that record apply, validated as any effect, and it answers the stored copy as it then stands. A parent under the path keeps its catch-up. At most 4 records per create, found within 8 store reads; none an applied effect of the answer changed. The read catching up with a create, parent or referenced, is shown the records the waiting creates made, in a `<new_resources>` block after the rest (taken out of `<related_resources>`, which tells a list answer to keep them unchanged), so a count, a total or a status can move ([upgrading](docs/upgrading.md#related-writes-bring-their-records-up-to-date)).
- An update whose LLM answer settles on its stored target is told, in one sentence, that what the answer changes beyond what the request names is kept only when listed as effects.

- A prompt shows where a value the mock minted came from. On an HTTP route, with an LLM and `consistency: on`, a generated 2xx create or action whose answer holds a string under a member named as a credential (`access_token`, `public_token`, `link_token`, not `key` or `sid`), or shaped like one, that its request did not send, in its body, query, path or `Authorization: Bearer` header, is remembered by a hash of that value, with the answer and its request as context may show them: what their schemas declare, past the wider name and shape checks, so the value itself and a client's secret are left out, as is any string holding one of them. A later request carrying the value, or sending it as a bearer token, is shown that answer and request in an `<earlier_origins>` block, as what may have changed, so a Plaid `access_token` brings the `item_id` it was exchanged for. At most 8 answers per session are kept and 3 shown, each up to 4 KiB, under the reserved state type: not exported or counted, and cleared by a session reset ([upgrading](docs/upgrading.md#prompts-show-where-a-minted-value-came-from-and-a-write-can-be-refused)).
- A write on the target record the model was shown, not a create, can be refused as the contract declares. When the operation declares a `400`, `409`, `412` or `422` response, the effects envelope may carry `"refusal": <status>`, one of those, and the engine answers that declared error, faker-filled, with no effects and no second LLM call; a body the faker could not make valid is served as `fallback`, with its reason. A status the operation does not declare is ignored, and an operation declaring none of them is asked for exactly what it was. Not offered with a forced status or a scenario.
- `StateStore::touch_live` refreshes a live session and says whether it was live, never creating one. Its default, for test doubles, touches and answers `true`; the memory, SQL, Redis and caching stores implement it.
- `mb_state::UNLISTED_ID`: a session holding that internal document and no resource is left out of `StateStore::sessions` and `session_count` on every backend.
- Lists and lookups agree with the session, from the contract alone. With an LLM and `consistency: on`, on HTTP routes: a generated list answer keeps only the items whose member a query parameter names (by its name, in any case, or by stem: `To` for `to`, `generations` for `generation`) and holds another value, when the parameter and the member declare the same one type (text, integer or boolean, not a real number or a `const`), the value is one the member's `enum` and asserted `format` allow (`status=all` beside an `enum` without `all` filters nothing), the parameter's own `enum`, if it has one, has a member `enum` beside it, and the parameter is not a bare `id`. A comma-separated value is a set only when every part is in the `enum`. A text member with no `enum`, `format` or `pattern` keeps the items whose value contains the requested one, ignoring case, so `name=Ann` keeps `Anna`; a value holding a digit (an id, a phone number, a code) matches whole, ignoring case, so `owner_id=u1` does not keep `u10`. A value is trimmed first, one left empty filters nothing, and one that came with a leading space and a digit also matches with a `+`, as an unencoded `+` decodes to a space. A search's `q`, ranges and items missing the member are left alone. The list's main array is then cut to the page size the request asks for, by the signal the output budget reads. Each step is kept only when the answer still validates and keeps its `minItems`; a count that clearly belongs to the list goes down by what the filter took out, as for a deleted id, and a page size leaves it. Of the 77 list routes of `examples/apis`, 16 get a filter and 38 a page size, 40 in all. The page size a name gives, without a `maximum` tying it to an array, is now the whole normalized name only (`limit`, `per_page`, `page_size`, `max_results`, `size`, `first`, `top`), never a part of one, so `topic_id`, `desktop`, `first_seen` and `image_size` set neither the output budget's page nor a cap. A delete of a stored record also marks, by hash, the text of its identity and of the members a lookup of its type keys on, those a list read's required query parameter names (Auth0's `email`; never an optional filter such as `state`), under a bound of 1024 of their own, so a lookup naming that value (`/users-by-email?email=`) drops an item the session does not hold that carries it, where the model made up a new user with the deleted one's email; storing a record with that value again clears the mark. And a create or a read under a parent path (`/captures/{id}/refund`) is shown, as related resources and scrubbed as they are, the newest 4 records creates put under that same path, so a second refund sees the first; a generated read of one record by its path (`/captures/{id}`, a catch-up too) is shown the same of what creates put under it, so a capture's read sees its refunds. Nothing is added to an answer, there are as many LLM calls as before, and `consistency: off`, offline mocks and GraphQL are unchanged ([upgrading](docs/upgrading.md#lists-and-lookups-agree-with-the-session)). `mockingbird-engine` gains `budget::requested_page` and `consistency::list_member`, and `consistency::item_schema` is public.
- A prompt shows what a request refers to and who the caller is, from the contract and what the session holds, with no per-API rule. On an HTTP route, with an LLM and `consistency: on`: a body or query value that could be an id (6 to 128 bytes with no space and a digit or a separator, or a whole number of at least 100000) is looked up as the stored id of the types an effect can name, or a path field a write was seen to hold, and a hit joins the related resources, following none of its own references, so a write is offered effects on it, which go on the stored copy. An effect cannot write the redaction marker, here or anywhere: a member holding it stays as stored. `reactions.add` with `timestamp` and a reply with `thread_ts` reach their Slack message, where they found nothing. A word-only id such as `closed` is not matched, and a date can be. At most 8 values, 32 store reads and 6 records per generated call. A `GET` route with no path or query parameters answering a single object (`/users/@me`, `auth.test`) has what its read declares of its answer, scrubbed, at most 2 KiB and the newest 3 kept for the session, shown to later generations, its own route's too, in an `<earlier_answers>` block as what the API said and may have changed. A write on that route answering the read's schema replaces its answer, any other forgets it, and so does deleting the record it is the identity of. A write that stored no record of a list's type (`POST /users/{id}/roles` answering 204) is kept for its path and told to that path's list read in an `<earlier_writes>` block, as what may have changed, the newest 5: its route and the members of its body that its request schema or the list's items declare, past the name and shape checks, never its query. Deleting the path's parent forgets them, and deleting a child forgets the writes naming it. These three leave out what wider checks than a request record's find: credential names (`pass`, `pwd`, `passphrase`, `jwt`, `otp`, `hmac`, `signature`, `license_key`, `card_number`, `credit_card`, `ssn`, `salt`, `mfa`, `recovery_code`, `connection_string`, `dsn`, and as a last word `key` and `sid`, unless they are a type's identity and the type is not itself a credential), URLs with a password or a credential-named parameter, JWTs, `Bearer ` values, and a pair labelled as a credential, whole. All of this only adds to a prompt: there are as many LLM calls as before, and with nothing to show a prompt is the same to the byte. `consistency: off`, offline mocks, GraphQL, gRPC, SOAP and SSE are unchanged.
- Mocks remember a write's request when its answer did not show it. After a 2xx write on an HTTP route, with an LLM and `consistency: on`, a 204 update's members that the read's schema declares (not identity, path or `readOnly` members, and not into an object under a `oneOf` or `anyOf`) are merged into the stored copy when the result validates, and what could not be applied is kept, with the route template, the operation and a scrubbed body, for the resource it targets. GraphQL, gRPC, SOAP, streams and offline mocks are unchanged ([state](docs/concepts.md#sessions-and-state), [upgrading](docs/upgrading.md#write-memory)). Breaking for code constructing a `GenerationContext` in full: it gains `earlier_requests` and `earlier_own_body`. `mb_state::INTERNAL_TYPE`, `mb_engine::REDACTED`, `Engine::scrub` and a defaulted `RequestRecorder::redact` are new.
- `x-mockingbird-resource` on an OpenAPI 3 or Swagger 2.0 operation corrects what the compiler infers: `type`, `identity` and `action` (true or false), all optional, also over a read verb in the last segment. A value that is not valid gives an `invalid_resource_extension` warning and inference stands; contracts without it are not affected by it.
- A write's LLM answer can change related resources: a command with a stored target or related resources is asked for `{"effects": [{"type", "id", "set"}], "response": ...}`, deciding the changes first, with both members required in the schema sent, since a provider enforcing it writes only what it requires (a plain answer, or one with no `effects`, still counts, at no extra cost), and each effect, at most 10, is merged into the resource it names in that session when the resource exists, its `id`, `number` and identity field are left alone and the result matches its schema. A rejected effect costs itself; the answer is served. Counted by `mb_effects_total{mock,outcome}`; `consistency: off` applies none. The prompt of such a call now says the answer shows the state after it, instead of asking for the same field values, which kept old statuses. An applied effect also sends `<resource>.updated` to matching webhook targets, with the merged resource as `data.object`. Malformed and over-limit effects, any too large for `limits.max_response_bytes` and all those of an answer the provider cut at `max_tokens` (a `set` may stop mid-value; the answer is still served, and a reply holding `effects` with no `response`, cut or whole, is repaired) are dropped and counted as `rejected`; an effect on a type with no read is rejected, having no schema to check against. Breaking for code constructing a `GeneratedResponse` in full: it gains the public fields `effects`, `effect_outcomes`, `dropped_effects` and `new_record`, using the new types `ResourceEffect` and `EffectOutcome`. `mb_engine::without_effects_schema` joins `without_items_schema`.
- Mocks remember what their answers mention: an object nested in a 2xx answer (not GraphQL, which stores its own, or a delete) with an `id` or `number` is stored when its `$ref` or member name gives it a resource type and it validates as that type's read or list item, down to depth 6 and at most 100 per answer, never overwriting what the session holds. An order's `customer` then reads back from `GET /customers/{id}` with source `state`. A route whose last parameter names no field (`/repos/{owner}/{repo}`, `/users/{username}`) also finds a stored resource by its `name`, `login`, `slug` or `key`; a stored `full_name` must end with `{owner}/{repo}` on a route ending in two parameters ([state](docs/concepts.md)). A generated call on a route below one (`POST /repos/{owner}/{repo}/issues`) is shown that parent the same way, so its answer can change it. `consistency: off` turns seeding and the search by those fields off. A generated read by id is also stored under its type, so a later mention cannot change what repeating it returns: a repeat answers `state` instead of `cache`. That covers a plain read only: one with a query or `X-Mockingbird-Seed` is not stored, and a read naming a seed is not answered from a plain read's answer. Neither is a read on a route read by a field such as a number (`/issues/{issue_number}`), nor a read by name whose `id` is that name, set from the path, on a route with an earlier parameter (`/repos/{owner}/{repo}` or `/orgs/{org}/teams/{team_slug}` with a string `id`: stored there, it would answer for another owner's repository of that name; `/v1/customers/{customer}` has no such parameter and is stored), nor one on a route ending in an owner and a name whose `full_name` does not show that owner; the response cache repeats these, and all can change after a later answer mentions that entity. A search's shorter form of a resource (a `$ref` the type's read is composed of with `allOf`) is stored too, as a `FlightOffer` for an `Offer`: its read is generated knowing it and keeps what it holds, and that answer takes its place.
- A resource composed with `allOf` has an identity: its read by path knows the id, so a created or stored resource is served, and answered, as with a plain `properties` object. It had none, so `GET /offers/{offerId}` on such a contract was generated knowing nothing stored. Stored bundles need a recompile to pick this up ([upgrading](docs/upgrading.md#resources-composed-with-allof-have-an-identity)).

- Smart import of a URL that serves an OpenAPI 3.x or Swagger 2.0 contract (JSON or YAML, as anything but HTML, Markdown or PDF) takes its operations as written, like an embedded definition, without an LLM; a JSON contract was refused and a `text/plain` one was read by the LLM. Its `$ref`s to other documents are resolved against the URL of the document holding them and fetched through the same guards as the contract (address checks and `import.url_allowlist`, redirects, 10 MiB and 20 s per document), each once, at most 64 documents (`mb_import::smart::MAX_REF_DOCUMENTS`), 16 deep (`MAX_REF_DEPTH`), 20 MiB with the contract and 20 s in all; only refs of the contract's own scheme are followed, and `file:` and other schemes fail the import ([`$ref`s of a fetched contract](docs/import.md#refs-of-a-fetched-contract)). The draft's source kind is `text`.

Definitions are looked up by namespace and name. `?wsdl` points followed imports at `?xsd=<upload path>`, which serves them. Several `.wsdl` files were refused before.

- GraphQL accepts batched requests: a `POST` whose JSON body is an array of `{query, variables, operationName}` operations (at most 10, `mb_protocols::graphql::MAX_BATCH_OPERATIONS`) is answered `200` with an array of responses in the same order. Each operation runs in turn as if sent alone: checked against the root-field and size limits, admitted (tenant, quota and, in `api_key` mode, the key), given its own chaos decision and recorded as its own request; a refused one answers its own `{errors}` entry. The largest injected latency is waited once. A larger or empty batch is a `400` problem; batches used to fail with a serde error ([batched requests](docs/protocols.md#batched-graphql-requests)).

Offline answers default to seed `0`; `mocks.<name>.faker_seed` sets another, and `X-Mockingbird-Seed: <n>` overrides it for one request (honoured with header overrides, a `400` when it is not an integer, and part of the session's read-cache key). LLM fallbacks stay random unless a seed is set; event messages are not seeded. `mockingbird-engine` gains `Engine::with_faker_seed`, `Engine::faker_seed`, the `seed` module (`SEED_HEADER`, `DEFAULT_FAKER_SEED`, `SEEDED_NOW`, `request_seed`), `Faker::with_now` and `PersonaFormats::apply_with`; `mockingbird-store`'s `MockBehavior` gains `faker_seed`.
- REST mocks honour the contract's base paths: Swagger 2.0 `basePath` and the paths of OpenAPI `servers[].url` (variables replaced by their defaults). One that then validates is served as `patched` without a second call; it used to fall back to the faker. ### Changed

- Prompts carry more of the contract. A response's `description` is shown under its status in a `<response_description>` block framed as data, not instructions, on one line, escaped and cut to 160 characters like the schema's descriptions, unless it is only the status's reason phrase (`OK`, `Not Found`); OpenAPI 3 and Swagger 2.0 imports keep it as the new `OutputVariant::description`. A query parameter, or a member of a body that is not an update's, that the request leaves out and whose schema declares a `default` is shown in a `<request_defaults>` block, except a page size as the output budget reads one (a `limit` defaulting to 100 would read as asking for 100 items) and what the credential checks hide by name or shape; and a create's answer reflects a body default as it reflects the body, so a create leaving out `generation` with `default: legacy` answers `legacy`; a scenario's `set` still wins. With neither, nothing is added, though the next entry changes the system message of every call. Stored bundles need a recompile to show descriptions ([upgrading](docs/upgrading.md#prompts-carry-response-descriptions-and-request-defaults)). Breaking for code constructing an `OutputVariant` in full: add `description: None`.
- The system prompt allows an empty list: a list or search that nothing plausibly matches may answer `[]` where the schema allows it, and 3 to 5 items stay the default otherwise.
- The output budget leaves out the deepest required members first, then the heaviest, and keeps an array item's only object member whose schema requires an `id` or `uri` of its own while anything else can go instead: a playlist entry keeps its `track`, and the track's `album` goes instead, where the faker filled a random track. When nothing else fits the budget, that member goes too, as before.
- A create's, or an action's new record's, generated id is redrawn as a taken id is when the request carries it, in its path (other than a create's own path id) or as a string in its body (other than a member named as its identity), and the session holds a record of another type under it (looking in at most 32 types, with `consistency: on`): a new message no longer takes the id of the channel it names. Another type's id the request does not name is kept (user `42` held, a new account `42` stays `42`), and so is a value the request carries that is no held record's (`POST /b {"name": "my-bucket"}` answered `{"id": "my-bucket"}`).
- Prompts no longer tell an action that a status moves, since not every action does and not every resource has one, and an action answering something else is asked for its target's change only if it changes anything. Models told a `validate` succeeded set `status` to `validated`, a value the contract did not allow, every time; now about half keep the status ([results](docs/benchmarks/action-note-2026-10-31/README.md)).
- **Action routes come from the contract's structure, not the spelling of the path.** The rule that a tail ending in `s` is a collection is gone, so `/{id}/process` and `/{id}/address` are no longer collections. A `POST` under `<static>/{param}` whose successes declare no body acts on the parent and stores nothing, even with a `GET` beside it (Jira's `transitions`, Auth0's user `roles`), over a read verb, or under a longer static tail, and sends no webhook unless the contract gives it a payload. A declared `201` is a record of its own, also with no identity (when it stores nothing). An answer of the parent's own schema is an update whatever the status, and the runtime decides: with a stored parent, an LLM answer with another identity is a new record of the parent's type stored under its own id, which a stored record keeps if it holds that id (the answer takes a fresh id and a number past those stored, and is served unstored, with no webhook or effects, if no id can be drawn), with the parent untouched and a `created` webhook (`POST /comments/{id}/replies`), while the target's identity or none updates the parent (PayPal's `POST /orders/{id}/capture`). This depends on the model: a reply got a new id 8 of 8 times on Luna and the default model and at most 2 of 8 on Lightning. An answer another resource's `GET` serves by path is created under that route's type and identity (PayPal's `captures/{id}/refund` now creates `refunds`). A `200` nothing reads acts on the parent. A format suffix no longer hides a detail route. See [upgrading](docs/upgrading.md#action-routes-come-from-the-contracts-structure).
- **Action routes act on their parent resource.** A `POST <static>/{param}/<verb>` the contract shows acting on its parent (`POST /v1/payment_intents/{intent}/confirm`; see the entry above for how that is read) compiled as a create on a type named `confirm`, so it invented a new id and never touched the intent. It now takes its resource type from `<static>` and its identity from `{param}`. When it answers what `GET <static>/{param}` answers it is an update, whose LLM answer wins over the stored resource and is what later reads return (a faker answer leaves the stored values), unless the LLM's answer carries another identity, when it is a new record stored under that id with the resource untouched. Otherwise it is `Effect::Other`: the resource is prompt context, nothing is stored, and the answer keeps its own `id` unless a member is named for the parameter (`bookingId`, `intent`; a bare `{id}` names nothing there, so the answer of a `POST /orders/{id}/ship` that stays an action keeps its own `id`). Webhook event types follow (`confirm.created` becomes `payment_intent.updated`). Stored bundles need a recompile to pick this up ([upgrading](docs/upgrading.md#action-routes-act-on-their-parent-resource)). `mockingbird-mcm` gains `Operation::is_action` and `is_generic_id`.
- **`output_mode` now defaults to `json_schema`.** Answers are generated against the response schema, which raised first-try validity with `deepseek/deepseek-v4.1-flash-1017` from 66% to 99%, with median latency rising from 1.9 s to 2.2 s. Free-text strings in the sent schema carry a 2,000-character limit, because a model could otherwise loop in one until `max_tokens`. A schema the provider rejects is asked for in JSON mode, with a warning, instead of failing the call, and an empty answer is tried once more in JSON mode. An array answer is asked for as `{"items": [...]}` in this mode too, so a snapshot of one replays through its operation key, not its exact prompt; re-record if you need exact matches. The `openrouter` preset uses this mode too. Profiles already stored through the Admin API keep the mode they have. To keep the old behaviour elsewhere, set `output_mode: json_object`.
- Local patching keeps more of the LLM's answer. A value breaking a pattern or length keeps the characters that fit, and a replaced identifier also changes where the answer repeats it as a whole token, such as inside a URL or a secret. Errors inside `anyOf` and `oneOf` are now patched in the branch needing the fewest fixes instead of costing a repair call, unless that would change a `const` or `enum` member.
- The default LLM model is `deepseek/deepseek-v4.1-flash-1017`, on `MB_LLM_MODEL` and the `openrouter` preset, instead of `deepseek/deepseek-v4.1-flash`. A config that names a model keeps it; to keep the old one, set `MB_LLM_MODEL=deepseek/deepseek-v4.1-flash`, or pass `--model deepseek/deepseek-v4.1-flash` with `--provider openrouter`. This model is a dated snapshot: if OpenRouter retires it, calls fail with the provider's error and mocks fall back to the faker (`X-Mockingbird-Fallback-Reason` says why, `mockingbird llm test` exits 1), with no switch to another model unless the profile sets `fallback` ([benchmarks](docs/benchmarks.md)).
- Event channels and webhooks use the per-call provider policy too, instead of always the mock's configured profile. Broker and WebSocket replies and trigger messages (scheduled, cron, state change) ask the policy with their tenancy: a WebSocket client's from its upgrade, otherwise the `TenantResolver`'s for the channel's operation id and, for a broker reply, the consumed message's headers, falling back to tenant `default` for the policy when the resolver refuses. A broker reply's usage event is now attributed to that tenancy (it was resolved without the message's headers). A webhook payload uses the profile chosen for the call that sent it. A policy's refusal skips that one message with a warning, a `PUBLISH` record with its status, a publish error in the channel's activity and metrics, and a `not_generated` usage event; the consumer or trigger carries on. The self-hosted defaults (`SingleTenant`, `ConfiguredProfile`) choose the same tenant and profile as before and build no second engine. Manual publishes still use the configured profile ([event channels](docs/events.md)). No public API changes.

- A changed LLM profile rebuilds only the mocks that use it, on every node, instead of every mock: those naming it, those naming none while it is the default, those whose fallback chain reaches it, those whose calls the provider policy sent to it (their cached engine for it is dropped with the runtime), and those whose last build failed. A change of `llm.default_profile` rebuilds only the mocks naming no profile. Workspace changes and resyncs still rebuild every mock. `MockRegistry` gains `reload_profile` and `reload_default_profile_mocks`.
- The provider policy (`mb-ext` `ProviderPolicy`) is asked for every call with the call's tenancy, as its documentation said, instead of once per mock build as tenant `default`. Data-plane calls ask it after admission; a profile other than the configured one generates with that profile's provider chain, built on first use and kept for the mock (until the mock or a profile changes); a rejection is answered as the call's problem (`application/problem+json`, its status and `Retry-After`), like a quota's, instead of failing the mock's build. Imports and draft previews resolve their tenant through the `TenantResolver` (operation `import` or `draft`, the Admin API request's headers, the request's workspace) instead of always billing tenant `default`; the import worker bills the tenant its job was created for, and a resolver's or policy's refusal is the request's problem. The self-hosted defaults (`SingleTenant`, `ConfiguredProfile`) choose the same tenant and profile as before, so single-tenant servers see no change: no new configuration, and no second provider is ever built. `mb-ext` gains no API. New, additive: `mb_protocols::ProfileEngines`, `MockRuntime::{configured_profile, profile_engines, engine_for}`, `mb_admin::LlmAccessError` with the defaulted `LlmResolver::{import_llm_for, preview_engine_for}`, and `mockingbird::runtime::{import_provider_for, preview_engine_for}`.
- `mockingbird-cli`: `server::binds_for` (a `(bool, bool, bool)` tuple) and `Snapshot::open(dir, replay, record)` are deprecated in favour of `Binds::for_role` and `Snapshot::open_with`. `ServeError::Other`'s `Display` shows the error's own message instead of the whole chain (`{e:#}`); the causes are its `source()`.

The `smart` submodules that only this crate's tests use (`chunk`, `complete`, `embedded`, `har`, `infer`, `llm`, `paths`, `postman`, `text`) are hidden from the docs; they become private in 0.2.

- API keys are verified from a short-lived cache instead of a control-store read on every call: data-plane calls to `data_plane_auth: api_key` mocks and Admin API calls with a key read the store once per key every 5 seconds (10,000 checks on SQLite: 36 to 0.9 µs each), and concurrent calls write `last_used_at` once. A revocation through the Admin API applies at once on that node; other nodes of a cluster can accept the key for up to 5 seconds ([API keys](docs/console.md#api-keys)). `mb_auth::ApiKeys::with_cache`, `ApiKeys::invalidate_caches`, `DEFAULT_API_KEY_CACHE_TTL` and `StoreDataPlaneKeys::with_keys` expose it; `ApiKeys::new` and `StoreDataPlaneKeys::new` still read the store every time.
- Generated answers are checked against the `format`s the faker produces (`uuid`, `date-time`, `date`, `time`, `email`, `uri`, `ipv4`, `ipv6`, `hostname`): a value breaking one (an LLM's `"createdAt": "yesterday"`) is refilled locally and the answer is `repaired`, without a repair call. A value equal to a request path or query value is kept, so a path id echoed into a `format: uuid` field survives. Other formats, and request validation, keep `format` as an annotation. `SchemaValidator::for_output`, `is_valid_output` and `patch_keeping` are new.
- `mockingbird-llm`: `OpenAiCompatible::reasoning_off` is deprecated in favour of `with_reasoning_disabled`, which does the same.
- LLM answers are read from the first complete JSON value in the reply (after the whole text and a Markdown fence) instead of the text from the first `{` to the last `}`, so two objects back to back (`{..}{..}`) or trailing prose with braces no longer make the answer unparseable. A value nested in a broken or truncated answer is never taken for the answer (a truncated reply still goes to repair), and an empty `{}` or `[]` in prose loses to a later value.
- The `json_schema` profile key, `MB_LLM_JSON_SCHEMA` and `--json-schema` are deprecated aliases of `output_mode` (`true` is `json_schema`, `false` `json_object`); setting both keys (or both `configure_llm` arguments) is an error, as is an unknown `MB_LLM_OUTPUT_MODE`. The Admin API still reports `json_schema` beside `output_mode`, and a stored `output_mode` that contradicts the `json_schema` flag (written by an older node during a rolling upgrade) reads as the flag. `mockingbird-cli`'s `LlmEnv::from_env` is deprecated in favour of `try_from_env`, which rejects an invalid `MB_LLM_OUTPUT_MODE`.

- A scenario's `set` is checked when it is written: with an active contract, `PUT …/scenarios/{name}` answers `422 Invalid scenario` naming the pointer (`set/total fits no response the scenario can select (getOrder 200: …)`) when no response the scenario can select accepts a key present in `set`, and the config file is refused at load the same way. Such a `set` was dropped at request time with only a WARN. Absent keys and `required` are not checked, and `null` is always accepted. `mb_admin::invalid_scenario_set` holds the shared check.
- Audit webhook: a failing event is retried in the background (at most 64 at once) instead of holding up the queue, so one event's 7 s of backoff no longer delays every event behind it (the next event went out after 0.7 s with a 100 ms backoff base, now after about 2 ms). First attempts keep the queue's order, but a retried event can now arrive after later ones; order by the event `id`.
- Admin API reads fetch less from the store: listing mocks reads every active version number in one query instead of one full contract per mock (100 mocks with 256 KiB contracts: 10 to 1.0 ms on SQLite, 23 to 1.1 ms on Postgres); listing contract versions and `requests?fields=summary` no longer read sources and bodies (500 entries with 32 KiB bodies: 365 to 5 ms on SQLite, 481 to 13 ms on Postgres); drafts, channels, scenarios and uploads read the active bundle without its source, and a draft's parse and diff run off the async runtime; scenario validation checks operation names through hash sets (5,000 operations: 86 to 16 ms). `mockingbird-store` gains defaulted `ControlStore` methods for this (`active_versions`, `active_bundle`, `list_contract_version_infos`, `latest_contract_version`, `list_request_log_summaries`) and the `ActiveBundle`, `ContractVersionInfo` and `RequestLogSummary` types.

- `mockingbird` serve and proxy do less per change and per request, with the same results: queued control changes are applied once per mock (a burst of 100 changes to one mock: 26 to 2 ms until the next change is mounted); a reload of every mock builds 8 at a time in name order (40 mocks with 2 ms store reads: 316 to 39 ms); the proxy's claimed-host check is one set lookup (10,000 hosts: 1.5 ms to 86 ns); request-log records are not copied when nobody tails the log, and their redaction and truncation no longer allocate per key or hold the whole serialized body (a 10 MB response: 73 to 61 ms); HA state-change announcements are published from a queue of their own, so a slow bus no longer delays this node's change feed (500 changes with a 1 ms bus: 1.26 s to 1 ms); the request-log relay of another node lists the mocks at most once a second for entries of an unknown mock (200 lookups: 152 to 1.2 ms); and `serve --record` holds each answer once (10,000 answers to one prompt: 796 to 7.6 ms). The proxy now remembers at most 500 unmapped hosts: past them, new hosts are not logged and are counted as `host="other"` in `mb_proxy_unmapped_requests_total` (and `mockingbird report`) instead of adding a series each ([proxy](docs/proxy.md)).

Same answers.

### Fixed

- Noun-first operation names get their kind and resource: the existing verbs are read as a suffix too, after a camelCase boundary or `_` (`issueCreate`, `issueUpdate`, `commentDelete`, Shopify's `productCreate`), on GraphQL mutations, gRPC methods and SOAP operations alike. A prefix still wins (`deleteIssue` is unchanged), and no verb was added (`issueArchive` stays an action). A GraphQL mutation whose payload has no `id` (`IssuePayload`, `DeletePayload`) takes as its resource the object type its name names (`issue`, `comment`) when the schema has one with an `id`.
- A GraphQL update or delete acts on the stored record its `id` argument names even when its payload does not select it. After a 2xx `issueUpdate(id:, input:) { success }` (or `updateIssue`), the members of its input objects that the stored record has or its type declares are merged over it, after what the answer held, so a later read from state sees them; `commentDelete(id:) { success }` removes the record. The record is looked up under the operation's resource type, then the payload's object members' types. A mutation with no `id` argument, and any other kind, changes nothing this way.
- A create that repeats a stored record is found on every state store, not only the in-memory one. The match behind `<same_values>` (create refusals, above) looked member values up in the runtime's index, which holds them only when `StateStore::local_only` says no other process writes the store; `SqlStateStore` never said so, so on `sqlite::memory:` (the default install's store), a SQLite file (as the benchmark runs) and Postgres no record was ever shown and no refusal offered. The create now asks the store on every backend: one listing of the session's records of the type it creates, at most 500, newest first, made only when the request sets a value that could match (an identifying one, or a plain one under a member a declared refusal's description names), and matched by the same rules as before (at most 4 holders of an identifying value, a plain value only with one holder, an agreeing reference and a refusal naming its member; the idempotency-key skip and the caps). A listing holding 500 decides only a value it shows one record holding, and never a plain one; a listing the store failed, or the breaker held off, decides nothing. For a type the contract creates at the top level only, records the Admin API seeded or upserted, other nodes' records and records stored as mentions in other answers now count as what a create repeats, on every backend alike. For a type the contract also creates under a parent path, where a record is matters, and none of those count, as their placement is unknown: only records this runtime created count, in that very collection for a create under a parent path, at the top level for a top-level one, so a top-level create is no longer refused over a record another node created under `/groups/{group}/contacts`. The value index no longer keeps plain values (their 512-per-session cap is gone). `SqlStateStore::local_only` is now `true` for a private in-memory SQLite database (`sqlite::memory:`, `sqlite://:memory:`), which only that store's connections can open, so on the default install references by value match identifying member values as on the in-memory store; a SQLite file, a named in-memory database (`mode=memory`) and Postgres stay `false`.
- A record answered in an envelope of several members has an identity when the envelope's structure tells which member it is, even when every route of its type wraps it. An envelope whose one object member sits beside members that are single values (Zoho Books' `{code, message, invoice: {...}}`, Pipedrive's `{success, data: {...}}` for organizations and products, Plaid's `{item: {...}, request_id}`) goes by that object's key, under that member, when the contract corroborates it as the route's record: the type's writes send bodies setting mostly the object's members, two or more of its routes, one a `GET` by path, answer the same schema under it, and another type answers the same single values beside its object (a shared `{success, data}`, not one type's `{order_number, status, customer}`); or the member is named for the route's type and carries a key (on a query with no path parameter, only one named for the type, so `GET /pages` answering `{count, page: {id}}` stays as it was). A body setting a member of the envelope's own (`order_number` beside `{order_number, customer: {...}}` says the envelope is the record), or one that cannot be read as members, leaves the route without one. The key is the object's `id` or the member the route's last path parameter names (a parameter naming nothing gives none), or, on a route with no path parameter, the key the type's routes by path read the same schema by, else the object's `id`, else its one `<x>_id` or `<x>Id` member whose `<x>` is the route's type (`invoice_id` on `invoices`). Before, only an envelope member with the schema another route of the type answered unwrapped was a record, so these creates stored nothing and every later read, update and delete went to the model blind. An object nullable by `anyOf`, `oneOf`, `allOf` or a list of types counts as an object, so a related record, an error, a page or a job object beside the answer's own members is not taken for it. Routes that had an identity keep it: across the bench and example contracts, only Zoho Books (8 routes), Pipedrive's organizations (2) and Plaid (2) gain one, and nothing else in their bundles changes.
- A stored record whose read answers it in an envelope with other required members is served from state. Cal.com's `GET /v2/event-types/{eventTypeId}` answering `{status, data}` and Pipedrive's `GET /v1/deals/{id}` answering `{success, data}` held only `data`, failed their schema and were generated again, so reads drifted from what the session stored. The envelope now gets each other required member from what the session's answers of the same envelope said, else from what its schema fixes (a `const`, a one-value `enum`, a `default`), else from its example when that suits it and is not a boolean's. When none of these tells a member, nothing is guessed: the read is generated as before. What an envelope said is kept per session in the state store, under its reserved type, so every backend and node sees it, per envelope shape (record type, record member and the other required members): all of it for the operation that answered, so a read answers again what it answered (its strings, such as a `message` or `request_id`, across the operation's records too); and for other operations only a string or `enum` value the reading operation's own schema enumerates (`enum` or `const`) at that member, so a Cal.com create's `status: "success"` serves the first read from state, while a create's `code: 201`, `created: true` or Pipedrive's free boolean `success` stays with the create and that read is generated once per session. Nothing is kept of an answer holding no record (`{success: false, data: null}`), a faker stand-in, or an answer whose local patch replaced or filled the record's member or touched another envelope member (a patch inside the record leaves the rest remembered); `GeneratedResponse::patched` (`mb_engine::PatchedMembers`) is new and says which top-level members a local patch touched (breaking for code constructing a `GeneratedResponse` in full: add `patched: None`); only the required members, of at most 256 bytes each, never the record and nothing credential redaction would hide, at any depth; the newest 16 entries per session. An envelope requiring nothing beside its record costs no read. The record is served as stored, and the answer is still validated; a kept value that does not suit it is passed over for the schema's.
- A `<x>Id` or `<x>_id` member refers to a type of the contract of the same stem, whatever case either is named in: a booking's `eventTypeId` finds the `event-types` it refers to, which the prompt now shows. Only `eventTypes` and `eventType` were looked in.
- A request referring to a stored record by a value no member rule resolves is shown that record. On an HTTP route, with an LLM and `consistency: on`, the records this runtime stores are indexed, per session, by their identity and by the string members their read declares that look like ids (not references, enum, `const`, date or time members, and nothing a credential holds). A request's values, at any depth of its body, query or path, then match: a whole id-like value the one record it is the identity of; a delimited token of a longer string only an identity, exactly (Spotify's `spotify:track:<id>`); a short id under an identity member of an object named after its type (Jira's `transition: {id: "21"}`); and, failing an identity, a whole value the one record holding it in a member of the same name (by stem or whole words: `requester_email` names `email`, while a `timezone` is not matched under `zone`). Only a member value that identifies its record counts: a member of `format` `email`, `uuid`, `uri` or `hostname`, or a value holding an `@` or of eight or more characters with letters and digits, never a date or a time, so a shared `timezone: America/New_York` or `status: in_progress` names nothing. A member match leaves out records of the operation's own type, which are siblings, and is skipped for a value an id lookup resolved. A value two live records hold names neither, and short, word-only and small-number values name nothing. A delete the store's change feed reports drops its record from the index at once; holders are also read back, so a record deleted, changed, reset or expired in the store neither matches nor makes a value ambiguous, while a failed read forgets nothing. A record already shown costs no read. A match is scrubbed and shown as related context, within the existing bounds; it is not marked as referenced by a create, and no answer body is stored on it. A ticket created with its requester's `email` is shown that contact, so no `requester_id` is invented. Member values match only with the in-memory store on a single node (behind a local bus, as `mockingbird serve` runs by default): with a store other nodes write to (SQL, Redis, a bus to other nodes) their uniqueness cannot be known on one node, and only identities match. `StateStore::local_only` says which; it defaults to `false`, and the bus wrapper answers it from its bus and the store beneath. Records the Admin API seeds or upserts are not indexed.
- An update's answer keeps what its applied effects set on its own target. An answer that settles on the stored copy kept only what the request named, so GitLab's `state_event: close`, answered `"state": "closed"` with an effect saying so, stored `closed` and served `opened`. The members an applied, validated effect set on the update's target are now served as the store holds them, on an answer with the read's schema that still suits the type; a rejected effect shows nothing, and one applied in part shows only what applied. When the answer would not suit the type with them, it is served without them and a warning is logged with the operation and type. Breaking for code constructing an `EffectOutcome` in full: it gains `applied`, the members of `set` that went in.
- A direct update of a record that a create only referred to changes it. The record's memory then held only that reference, which made its own `PATCH` keep the stale copy over the answer and lose the nested members the request named (a HubSpot contact's `properties` after a deal's create associated it). Such an update now settles as though nothing were remembered, merging a `PATCH` at depth, and the memory stays for the record's next read, which still changes by effects alone. Whether a kept request only refers to its record is decided per request: no generation whose answer replaces the stored copy (a direct update, or a read with other requests to catch up on) is told one, so a later ordinary write no longer lets a catch-up see the referring create and rewrite the record. An action is told them as before.
- An update answering another schema than its record's read (an `Ack {ok}`) adds nothing of its own to the stored record: a member stays when the record's read declares it, allows more by `additionalProperties`, or the held record already had it.
- A record's key comes from the words of the path parameter that reads it, not from a list of endings. The longest group of a parameter's last words that names a member of the record, not an object or a list, is the member it reads by: `{issue_iid}` → `iid`, `{task_gid}` → `gid`, `{issueIdOrKey}` → `key`, `{MessageSid}` → `sid`. A create, with no path parameter, goes by the one member of its answer that its own type's reads by path go by; another type's reads teach it nothing. A delete on the same parameter goes by the same identity, and a deleted record stays gone though another shares its `iid`. So Asana's tasks and projects, keyed by `gid` in a `{data}` envelope, are stored and read back where every route had no identity, and GitLab's `GET /projects/{id}/issues/{issue_iid}` reads the issue by `iid`, not by its `id`. GitHub's, Jira's and Twilio's messages and calls are as they were. A `sid` or a `uuid` still names a created record when no read by path names a key. See [upgrading](docs/upgrading.md#keys-from-path-parameters-types-from-record-schemas).
- A create whose own type has no `GET` by path stores its record as the type that reads exactly its schema: the type whose `GET` by path serves it, else the one type whose lists list it. Freshdesk's notes and replies were stored as `notes` and `reply`, so `GET /tickets/{id}/conversations` never saw them; they are `conversations` now. Trello's card comment is one of the card's `actions`, and Asana's `POST /tasks/{task_gid}/subtasks` creates a `tasks` record, where it was taken for an update of the parent task.
- A read by another member than the key puts the path's value in that member, not in the key. A generated GitHub `GET /issues/7` by `issue_number`, or GitLab's by `issue_iid`, took `7` as its `id` and stored nothing; it now answers `number: 7` (or `iid: 7`) with its own `id`, is stored under that `id`, and the same read is served from state. A stored record keyed by the path's value is not taken for it when its member says otherwise. Jira's `issueIdOrKey`, whose words name the `id` too, is as it was. See [upgrading](docs/upgrading.md#keys-from-path-parameters-types-from-record-schemas).
- A path segment shaped like a version, followed by another static segment, is never a type. Mailchimp's `GET /3.0/search-members` was typed `3.0` and Spotify's `GET /v1/search` `v1`, because an RPC-style read took the segment before its verb; they are `search-members` and `search`.
- An update sent in its query string names its members as a JSON body does: when its answer settles on the stored record, the query's value of each member it names is applied after settling, as the body's is, and an effect leaves it alone. `PUT /cards/{id}?name=x&idList=y` (Trello) kept the stored name and list, as only the body counted. A body member of the same name wins. A form body already counted, decoded into the body.
- A generated error body whose schema declares an integer or number `status` member allowing the HTTP status carries that status. The faker drew a random one (a `404` problem said `"status": 46`) and a model could write another. The schema decides: a string `status`, or one whose bounds, `enum` or `const` leave the status out, is left as generated, and so is a body the change would make invalid and a success's.
- The local patcher moves a required member the model nested in the one child object whose schema declares other properties but not it, and no map or free-form members (the root's `type` and `uri` inside a playlist's `tracks`), back up when that leaves fewer errors and none new, so the answer is patched instead of repaired; repair messages name the root `/` instead of an empty pointer; and an answer integer repeating the request's integer path or query value that breaks only its bounds is clamped to the bound, not redrawn.
- A 204 update's remainder tells later reads only what the read's or the request's schema declares, past the wider name checks, as a list read is told of a write. It told every member it could not apply, so an undeclared `code` or `value` reached the next prompt. A remainder with nothing declared is not remembered and costs no catch-up.
- A `GET` storing nothing adds no session anyone sees. The answer of a route with no parameters is still kept in the shared store, so another node and a restart see it, but a session only a read wrote to is marked `mb_state::UNLISTED_ID` and is not listed or counted until a write or a resource.

- A record is found again when its path and its schema's id have different names. `/users/{id}` over a schema with `user_id` and no `id` had no identity, so a create stored nothing and a read saw nothing. A member named for the type (`user_id` for `users`, `category_id` for `categories`) is now its identity, where each route of the type ending in a parameter has an id-like one (`{id}`, `{userId}`, `{user_id}`, not `{handle}`). So `unknown_ids: 404` can now answer 404 on such a route. See [upgrading](docs/upgrading.md#a-member-named-for-its-type-is-its-identity).
- A lookup sees the records of its type. A read with no path parameter, of a type no other route has, every listed array of which holds what one type's `GET` by path answers, now has that type, so `GET /users-by-email` is shown the stored users and stores what it lists under them. It was a type of its own, which held nothing. `x-mockingbird-resource` still decides.
- A record in an envelope or an array has an identity. A route answering its record in a one-member envelope (Square's `{"payment": {...}}`), or in an envelope where exactly one member has the schema the type's other routes answer as its record (Zendesk's `{"ticket", "audit"}`), goes by the record's identity: the record is stored, a read answers it in its envelope from state, and Square's `POST /payments/{id}/complete` updates the payment. A read answering an array of items whose required member its last path parameter names (SendGrid's `GET /bounces/{email}`) goes by that member: a held record answers as a one-item array, and a deleted one, or an unknown one under `unknown_ids: 404`, as `[]` with no LLM call. A record an answer mentions is stored under the field its type goes by, not also under an `id` beside it, so a bounce deleted by address leaves no copy. Compiled bundles show where the record is under `identity.record`. See [upgrading](docs/upgrading.md#a-record-in-an-envelope-or-an-array-has-an-identity).
- A list is typed by its items wherever they are exactly a type's record. A list read under a path parameter or beside its own type's routes takes the type whose `GET` by path serves exactly what every array it lists holds, as a lookup already did: Notion's data source and database queries list `pages`, Jira's `GET /search/jql` lists `issue`, and Spotify's `top-tracks`, GitHub's `/installation/repositories` and `/search/repositories` list `tracks` and `repos`.
- A single answer with its own identity is stored as itself, not as the lists it holds: OpenWeatherMap's reading was stored as its `weather` conditions, so `{id: 803}` came back as the related record. It is stored only on a route with no path parameter: TMDB's `/movie/{movie_id}/credits` stores neither the credits nor their `cast`. The lists a record holds are stored only where another read serves exactly their schema, under that read's type: an order's `lines` were stored as `orders`, and a booking's passengers were taken for `bookings`.
- A read below a record that answers one of its members is answered from it: `GET /playlists/{id}/items` serves the stored playlist's `tracks` with no LLM call, unless the request has a query (`?offset=50`) or a write the playlist does not show yet is remembered for it or for that path.
- A deleted record stays deleted. With `unknown_ids: generate` the next read generated a replacement and stored it, and a later answer could store it again. A 2xx delete now keeps a marker for its concrete parent path, with an LLM and `consistency: on` and not on GraphQL: a read of that id under that parent answers as `unknown_ids: 404` does, with no LLM call, seeding skips it, and a generated list loses its item when the answer stays valid, with the count beside it when that is clearly the list's. A create or an update storing that id clears the marker, as does a session reset. At most 1024 are kept per session.
- An update keeps what its model answered at the paths the request named. The stored copy used to go over the whole answer, and a nested request that failed validation alone was then dropped, so `PATCH {properties: {lifecyclestage: "opportunity"}}` answered `opportunity` by the model served the stored `lead`. When the answer has the resource's read schema, a member of it now wins only if the request body names exactly the same path; the stored copy stands otherwise, and what it lacks comes from the answer at the top level. A request nested differently from its answer gets no benefit from this change. Identity, path, `readOnly` and owner members never take the answer's value, a named array takes the request's value, and a null counts only if the request names that path as null. A `PATCH` then merges at any depth, or takes a member whole when the merge does not validate; `PUT` still replaces each member it names. Other answers, faker answers and offline mocks behave as before. An effect on an update's own target applies without what the resource does not declare, a path or `readOnly` member, a member the request names, or what would show another owner.
- The output budget keeps what a request asked for. A word of the request names a member sharing its stem, so `type=track,artist` keeps `tracks` and `artists`; only `artists` was offered to the model before, whichever types were asked. A page's items are capped below the page size asked for only when nothing else fits, and the estimate counts that size. A page size is an integer query parameter whose `maximum` an array declares as its `maxItems`, or else, as a last resort, one whose name holds `limit`, `size`, `per_page`, `first` or `top`. Such an array is the last required member to go, so a named page keeps its items. Shaping no longer stops over budget when a member it left out held another it counted.
- A stored resource no longer answers for another owner on a route naming its target after another path parameter (`/repos/{owner}/{repo}`, `/orgs/{org}/teams/{slug}`, `/repos/{owner}/{repo}/issues/{n}`). A read needs the collection path it was listed or written under on that route template, or the owner shown by a path ending in the owner and name, a member tied to the parameter, or a link. A write acts unless the resource is known to be another's. A delete by number finds a listed resource when its answer does not declare the number, and a mention is keyed by the field the contract identifies its type by.
- An import job is billed to the tenant it was created for whichever node runs it: the tenant is stored with the job (migration `1100_import_job_tenant`, a nullable `import_jobs.tenant`) instead of kept in the creating node's memory, so a job resumed after a restart or claimed by another node no longer bills tenant `default`. Jobs queued before the migration still bill `default`. `mockingbird-store` gains the defaulted `ControlStore::create_import_job_for_tenant` and `import_job_tenant` (a store that does not override them bills `default`).
- A `rediss://` state, bus or leader URL no longer crashes the `mockingbird` binary. sqlx's `tls-rustls` feature enabled rustls's `ring` provider next to `aws-lc-rs`, so rustls could not choose a process default and `redis` panicked building its TLS config ("Could not automatically determine the process-level CryptoProvider"). sqlx now uses `tls-rustls-aws-lc-rs`, `ring` is no longer compiled into the CLI, and the binary installs the aws-lc-rs provider at startup.
- `mockingbird-protocols`: the `Debug` output of `BrokerConfig` and of a webhook `ResolvedTarget` (and so of `WebhookDispatcher`) shows the URL without userinfo (`amqp://user:password@…`), and for webhooks without the query and fragment, which can carry a token; it printed the URL as configured.
- `mockingbird run --offline`, `--record`, `--replay` and `-c` reusing a server that already answers print a warning naming the flags that do not apply to it; a leftover dev server silently turned `run --replay snap -- npm test` into live LLM calls.
- `mockingbird snapshot export` writes each mock's `path_rewrite` and `header_overrides`, and `snapshot import` creates the mock with them, so an imported mock routes like the original; older snapshots import as before. `docs/ci.md` lists what a mock file carries.
- `mockingbird server stop` (and `mockingbird run`) ask the background server to stop through a stop file it watches (`MB_STOP_FILE`, set by `server start`), so on Windows it shuts down gracefully instead of being killed with `taskkill /F`; `/F` is used only after 10 s, and `forced` says when it was.
- The MCP server no longer advertises the `logging` capability: it sends no log notifications (`logging/setLevel` is still accepted).
- The MCP `admin_api` tool returns non-JSON answers (`{content_type, text}`, or `{content_type, bytes, base64}` for binary bodies up to 1 MiB) instead of failing, so a non-JSON contract's `…/source` can be read; an event stream is refused at once instead of hanging the call.
- A `--watch` reload that changes a read-at-startup section (`server`, `storage`, `protocols`, `auth`, `audit`, `outbound`, `bus`, `limits`, `pii`, `import`) logs `config reload: the <section>: section changed; restart the server to apply it`, as it already did for `proxy:`; the edit was ignored without a word.
- `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` alone enables OTLP trace export, and `OTEL_EXPORTER_OTLP_PROTOCOL=grpc` (or the traces variant) logs a warning that spans go over HTTP/protobuf instead of being overridden silently.
- `agent install claude-code --scope user` explains why it cannot pass keys through (a printed `claude mcp add` line would write their values into `~/.claude.json`) and suggests `--scope project` or `mockingbird keys setup`; it said Claude Code cannot read variables.
- MQTT shared subscriptions (with a shared, non-`local` bus) use each mock's consumer group, `$share/<client_id_prefix>-<mock>/<topic>`, instead of `$share/<client_id_prefix>/<topic>` for every mock: two mocks consuming one topic split its messages between them (each got about half); each now gets every message, and the instances of one mock still share them. Messages are told apart per mock with MQTT 5 subscription identifiers when the broker supports them.
- Console logins started on one node failed on another with `unknown login state` (half the callbacks with `mode: split` and two control replicas), and every login in progress failed after a restart: started logins (PKCE verifier, nonce, return path) lived in process memory. They are now kept in the control store (migration `0800_oidc_pending_logins`, SQLite and Postgres), keyed by the sha256 of the `state`, single use, expiring after 600 s and bounded to 10 000. `OidcClient::with_store`, `start_login`, `login_pending` and `cancel_login` are new; the in-memory `begin_login`, `is_pending` and `abandon_login` are deprecated. `mockingbird-store` gains defaulted `ControlStore` methods for this (`put_oidc_pending_login`, `get_oidc_pending_login`, `take_oidc_pending_login`, `delete_expired_oidc_pending_logins`) and the `OidcPendingLogin` type.
- GraphQL: queries using a custom executable directive the schema declares, such as Shopify Storefront's `@inContext(country: …)`, failed validation with `Unknown directive`; the directive definitions were dropped when the schema was built (and, for an introspection upload, when it was rendered to SDL). Such directives are now accepted and ignored, as are the variables only they use; undeclared directives still fail validation.
- GraphQL: a stored schema defining a field, argument, input field, enum value, union member or implemented interface twice in one type (possible in bundles imported before duplicates were refused at import) no longer panics when the mock is served; the mock fails to load with an `invalid GraphQL schema: … is defined more than once` error naming the type and member.
- A `$ref` to a missing component schema (`#/components/schemas/X`, `#/definitions/X`) no longer fails the whole contract (Square's spec): the schema is stubbed as an open schema, with a `dangling_ref` warning. Refs to files that were not uploaded are still refused, with an error that says to upload them or bundle the spec.
- Archive uploads drop `__MACOSX/` entries and hidden files (a zip made in Finder no longer breaks a `.proto` upload), and a single contract beside a README, LICENSE or other documentation compiles; several contracts are refused with an error naming them.
- An upload with several `.wsdl` files, or a WSDL that needs definitions it pulls in with `wsdl:import`, is refused with an error naming `wsdl:import` (which is not followed) instead of "expected one" or "unknown portType" alone.
- `DELETE /api/v1/workspaces/{ws}?force=true` refuses with `409 Managed by config file`, naming them, when the workspace holds mocks or LLM profiles declared in the config file: it deleted them, and the next reload recreated them.
- `docs/configuration.md` says `storage.session_ttl` runs from a session's last use (any request that reads or writes its state), as it always has; it said "last write".
- `docs/admin-api.md` lists the AsyncAPI upload media types and the workspace, API key, audit, `/me`, request-log entry and stream, and webhook delivery endpoints.
- `vault:<mount>/<path>#<field>` secret references work wherever `env:` and `file:` do, as documented: an LLM profile's `api_key` and `${…}` header references in the config file, a broker's `sasl.password`, and an Admin API profile's `secret_ref` and headers (still gated by `server.api_secret_refs`) were refused with "must be a secret reference (env:NAME or file:/path)". A malformed `vault:` reference (such as `vault:token#key`, which the Vault resolver cannot read) is now refused when written, including in webhook `secret`s, which accepted any `vault:` text and failed only at delivery.
- `mb-ext`: `DefaultSecrets` resolving a well-formed `vault:` reference without a usable Vault returns `ExtError::Other` naming the reason (`VAULT_ADDR is not set`, or `Vault is disabled: …` with the configuration error) on every resolve, instead of `ExtError::BadSecretRef` ("invalid secret reference"), which pointed at a correct reference. Malformed references are still `BadSecretRef`.

- HTTP/REST query strings and form or multipart bodies decode in linear time: they were O(k^2) in the number of keys (50k keys took about 11 s) and are decoded before auth, so an unauthenticated request could burn CPU. A request with more than 1,000 query pairs, or more than 1,000 form or multipart fields, is now refused with a 400 `application/problem+json` ("Too many parameters"), and the request log keeps at most 1,000 recorded query or form fields.
- The MCP `stop_server` tool stops a server the same MCP server started at once with SIGTERM: it no longer waits 10 s and reports `forced: true` because the exited server lingered as an unreaped (zombie) child, and `server_status` no longer reports such a server as running.
- Deleting a mock (or a workspace) forgets its webhook deliveries: the in-memory delivery log kept up to 200 records for every mock ever deleted until the process restarted, and a new mock of the same name listed the old one's deliveries.
- The Vault client honours `outbound.proxy`, `outbound.no_proxy` and `outbound.ca_file` like the server's other outbound clients; it followed only the `HTTP(S)_PROXY` environment and `VAULT_CACERT`. `mb-ext` gains `VaultHttp`, `VaultSecrets::from_vars_with_http` and `DefaultSecrets::with_http` (additive); embedders that pass their own extensions use them to do the same.
- In a cluster, a session reset, a seed or a mock reset clears the response cache on every node, not only on the node that made it: other nodes kept answering the reset session's repeated reads from the cache (`X-Mockingbird-Source: cache`) until its next write or idleness. The node announces the reset on the bus as a state event of no resource type, which older nodes ignore.

### Changed

- Less work per call in the protocol adapters, with the same answers: narrowed GraphQL selections and event key, header and address-parameter schemas reuse a compiled validator (bounded cache) instead of compiling one per call; a GraphQL request is parsed once instead of two or three times; subscription frames read only their `type` and `id`; operations are found by id through an index, and the per-create path-field and listed-member walks are computed once per mock; gRPC calls no longer copy their operation and scenario; offline bidi streams no longer copy earlier messages; consumed events copy their payload and headers only for the request log.
- Faster contract and smart imports, with identical results: saving or assembling a draft checks its schemas in one compile instead of one per schema location (a 400-component draft went from 1.8 s to 15 ms), the `schema_too_large` check measures schema sizes without cloning or serializing the reachable definitions (1.8 s to 83 ms for 1,000 operations that each reach 1,000 definitions), `compile` parses a JSON or YAML document once instead of twice, recognising a HAR or Postman upload no longer builds the whole JSON tree (20 MiB in 39 ms instead of 125 ms), and the extra roots of `outbound.ca_file` are parsed once per bundle instead of on every fetch hop.

## [0.1.0] - 2026-10-28

The first release. Since 0.1.0-rc.1, in short:

- **Run apps unchanged.** Mocks take the real host names they stand in for (`hosts:`), and `mockingbird proxy` intercepts HTTPS to them with a local CA, so an app reaches mocks of `api.stripe.com` or `api.github.com` without source edits. `mockingbird run -- <command>` does the whole setup for one command, with preloads that make Node, Python, Java, Go, curl and Deno trust the CA and use the proxy, and `mockingbird proxy browser` for Chromium-based browsers ([proxy](docs/proxy.md)).
- **Deterministic CI.** `serve --record` / `--replay` answers a CI run from recorded LLM answers without a key; `mockingbird report` and `mockingbird verify` turn the request log into a summary, JUnit and a pass/fail gate; a GitHub Action and a GitLab CI template wrap it ([CI](docs/ci.md)).
- **Mocks as infrastructure.** A Terraform / OpenTofu provider and Pulumi ([IaC](docs/iac.md)); mocks declared in Helm values, Kustomize overlays, Argo CD and Flux previews per pull request, Argo Workflows, Tekton and Testcontainers modules for Node, Python, Java and Go ([GitOps](docs/deploy/gitops.md)).
- **21 ready-made API mocks.** `mockingbird examples init stripe` (or GitHub, Shopify, Twilio, Slack, Plaid, TMDB and more) writes a contract, persona, scenarios and webhooks for the real host, plus three sample apps tested against them ([examples catalog](docs/examples.md)).
- **Faster and leaner on real LLMs.** An output budget shapes huge response schemas (GitHub `search/commits` p50 29.8 s → 9.4 s), OpenRouter reasoning is off by default, GraphQL mutations and multi-root queries generate only their selection, and persona-declared id formats are patched locally ([performance](docs/performance.md#latency-against-a-real-llm)).
- **Consistent, stateful answers.** Reads of what a session created come from its state, repeated reads from a per-session cache, and list items seed later reads by id; `unknown_ids: 404`, `default_scenario` and per-operation scenario instructions.
- **Real-world contracts.** Stripe's and GitHub's full contracts load and serve: form-encoded and multipart bodies, covariant GraphQL interfaces, `$ref`s in vendor extensions, prompts fitted to a 64 KiB schema budget, GraphQL answers generated from the selection set, and local patching instead of repair calls. Fallbacks dropped from 25–33% in the field trials to none on the Stripe and TMDB trials; a second round of trials ran plaid/quickstart, healthchecks, the GitHub CLI, Next.js Commerce and Stripe's Java sample unchanged under `mockingbird run` ([trials](docs/trials/README.md)).
- **Diagnosable.** `X-Mockingbird-Fallback-Reason`, `X-Mockingbird-Validation` and the request log say why an answer fell back or a request was rejected.
- **Smart import drafts you can finish.** Several URLs and documents per draft, merge or replace, embedded OpenAPI blocks taken as written, confidence and warnings per operation, and MCP tools to read, edit and approve drafts.
- **Agents set it up alone.** The MCP server finds keys from the login shell, `agent install` passes key names through to each agent, and `keys setup` stores a key without it passing through the agent.
- **Webhooks.** Signed Stripe-style or HMAC events after writes, with retries and a delivery log.

- LLM profiles take `extra_body`, JSON merged into every provider request (OpenRouter `provider` routing, `reasoning` settings); `--extra-body` on `llm configure` and `init`.
- `mockingbird mcp` imports the variables it lacks from the login shell at startup (`MB_NO_SHELL_ENV=1` skips it), so keys exported in `~/.zshenv` reach a server started by a desktop agent; `doctor` reports `shell_env.imported`.
- `mockingbird init` (MCP `init_config`) takes `--port`, `--admin-port` and `--grpc-port`.
- A request that fails validation reports why: the `X-Mockingbird-Validation` response header, the declared error shape's message-like field (`message`, `detail`, … or nested, like Stripe's `error.message`), and `request.validation` in the request log.
- Reads of a resource the session holds are answered from session state without the LLM (`X-Mockingbird-Source: state`) when the stored value matches the response schema.
- Per-session response cache: a session repeating a read gets the same answer (`cache`, 500 answers per session), cleared by any write of the resource type and by a session reset. `consistency: off` on a mock disables it and list seeding.
- List→detail seeding: the items of a list answer are stored in the session, so a later read by id returns the same item.
- `unknown_ids: 404` on a mock answers reads of ids the session does not hold with the operation's 404 (problem+json when none is declared).
- `default_scenario` on a mock applies a scenario when a request names none; a scenario's `operations` entries may be `{id, instructions}` to give one operation its own instructions (config, Admin API and console client).
- Faker: strings honour `pattern` (via `rand_regex`), formats `ipv4`, `ipv6`, `hostname` and `uri-reference`, and path, query and GraphQL argument values are echoed into same-named fields.
- Migration `0610_mock_behavior` adds `mocks.behavior`.
- Smart import takes operations from OpenAPI 3.x blocks embedded in documentation (fenced code blocks, JSON scripts, ReadMe page data) as written; a page fully covered by its blocks needs no LLM.
- Imports take `urls` (up to 20) and `documents` (up to 100) for one draft from several sources, and `mode: merge | replace`; by default an import merges into the mock's newest draft or active version (adds operations, replaces those with the same method and path, removes nothing). CLI: several URLs, docs folders, `--mode`.
- Schema-size warnings (`schema_too_large`) on uploads, the version list, activation, approval, drafts and `mockingbird validate`, for response schemas over the 64 KiB prompt budget; `mb_import::compile_with_warnings`.
- Migration `0650_import_drafts` adds `contract_versions.warnings` and `import_jobs.mode`.
- Mocks take `hosts:` (config, Admin API, console client). Dispatch filters by `Host`, then takes the longest prefix, so mocks on different hosts may share a route prefix (GitHub REST at `/` and GraphQL at `/graphql` on `api.github.com`). A GraphQL mock also answers at its own mount point (`POST /graphql` for a mock at `/graphql`). Migration `0600_mock_hosts` adds `mocks.hosts`.
- `mockingbird proxy` (and `serve --proxy` / `proxy.enabled`): an HTTP proxy that intercepts HTTPS to mapped hosts with a local CA (`~/.mockingbird/ca`, `MB_CA_DIR`, `proxy.ca_dir`; never installed system-wide); `proxy.unmapped: pass | block` (default `pass`); placeholder PNGs for `proxy.images`; `mockingbird ca path` and `mockingbird proxy env`; `GET /proxy/hosts` on the ops port. See [docs/proxy.md](docs/proxy.md).
- `mockingbird run [-c FILE] [--offline] [--record DIR | --replay DIR] [--wait] [--keep] [--state-dir DIR] -- <command…>`: starts the server with its proxy unless one already answers, waits for `/readyz`, runs the command with the proxy environment, stops what it started and exits with the command's code (`128+n` on a signal, `127` when the command cannot start).
- `proxy env` covers more runtimes: a Node.js preload (`NODE_OPTIONS=--require <ca_dir>/node-proxy.cjs`) that sends every `http`/`https` agent and undici's `fetch` through the proxy and trusts the CA, `JAVA_TOOL_OPTIONS` (proxy properties and a JKS truststore), `CURL_CA_BUNDLE` and `DENO_CERT`; existing `NODE_OPTIONS` / `JAVA_TOOL_OPTIONS` are kept.
- Browsers: a PAC file at `/proxy.pac`, and `mockingbird proxy browser` (Chrome, Chromium, Edge or Playwright's Chromium in a profile of its own that trusts the local CA by SPKI pin; `--print` prints the command). `proxy.images` entries may name a path prefix, with ipx `s_WxH` / `w_N` sizing; CONNECT tunnels to mapped hosts also carry plain HTTP.
- `mocks.<name>.path_rewrite: {strip_prefix, add_prefix}` mounts a contract under another base path (config, Admin API and console client).
- The examples catalog: `mockingbird examples list|show|init <name> [--dir] [--force] [--full]` with 21 API mocks embedded in the binary (Stripe, PayPal, Square, Plaid, GitHub REST and GraphQL, Shopify Admin GraphQL, Twilio, Slack, SendGrid, Discord, HubSpot, Notion, Jira, Zendesk, Auth0 Management, Spotify, TMDB, OpenWeatherMap, Kafka events and an OTLP collector), each mapping the real host with a persona, scenarios and webhooks; `--full` downloads the pinned upstream spec and checks its SHA-256. Sample apps in `examples/apps` (FastAPI + Stripe, go-github, Node + Shopify + Stripe) run their tests offline through the proxy. See [docs/examples.md](docs/examples.md).
- MCP draft tools: `get_draft` (operations with confidence and warnings, one operation's definition on request), `edit_draft` (JSON merge patch on one operation or the whole draft; a patch that breaks it changes nothing) and `approve_draft` (activates by default). `import_contract` takes `urls` and `mode`.
- Request log: Admin API `GET …/mocks/{mock}/requests/{id}` and `?fields=summary` (entries without bodies, with `request_bytes` / `response_bytes`); MCP `get_request`.
- MCP `proxy_env` (the proxy variables and CA path, with `export` lines) and `start_server {proxy: true}`; `mockingbird server start --proxy`.
- `mockingbird agent install` passes the default profile's key variables (names only) through to the agent's MCP config in each agent's syntax; `--config`, `--pass-env`.
- `mockingbird keys setup` and MCP `open_key_setup`: a one-shot local page that stores an LLM key in `~/.mockingbird/secrets/<name>` (`0600`) and points the profile at it, returning only the name and profile (the URL when the user takes longer than 45 s). `doctor` reports the store under `key_store`.
- `mb-ext`: `check_secret_file` and `in_key_store` (additive).
- Webhooks: mocks POST an event after each successful write to the URLs in `mocks.<name>.webhooks` (or the Admin API), signed Stripe-style (`Stripe-Signature`) or with `X-Mockingbird-Signature`, retried 3 times (1 s, 2 s, 4 s); the payload is the contract's OpenAPI `webhooks`/`callbacks` body when defined, else a Stripe-shaped `<resource>.<created|updated|deleted>` event. Deliveries: `GET …/mocks/{mock}/webhooks/deliveries`, `mockingbird webhooks deliveries`, MCP `list_webhook_deliveries`; `mockingbird webhooks sign` prints a signature for tests. `server.api_webhook_secret_refs` limits secret references set through the API. Migration `0700_mock_webhooks` adds `mocks.webhooks`. See [docs/webhooks.md](docs/webhooks.md).
- GraphQL answers store every object with an `id` under its type (`Cart` → `cart`): a mutation's are merged into the session, a query's added when new, so `cartCreate` → `cart(id:)` → `cartLinesAdd` reads and updates one cart. Mutations are generated knowing what their `<x>Id` arguments and `gid://…/<Type>/…` ids name (in nested inputs too).
- Base64 fields (`format: byte`, `contentEncoding: base64`, `content` beside `encoding: "base64"`) are asked for as plain text and encoded locally; values that do not decode are re-encoded from their text.
- Request-validation rejections have their own source, `rejected` (header, request log, metrics and `report`), instead of `fallback`.
- `mockingbird verify --no-unmatched`: fails when a request matched no operation of its mock's contract; `report` lists those routes.
- `mocks.<name>.graphql_path`: one GraphQL mock's endpoint below its route prefix (Shopify's `/graphql.json`), instead of the server-wide `protocols.graphql.path`.

### Changed

- Relative `sqlite:` paths in `storage.url` / `storage.state_url`, and relative `server.tls`, `outbound.ca_file` and `brokers.<name>.ca_file` paths, are resolved against the config file's directory, like `contract:` paths (were the working directory). Flags, environment variables and runs without a config file keep the working directory. See [Upgrading](docs/upgrading.md#relative-paths-in-the-config-file-follow-the-file).
- The binary's package is `mockingbird-cli` (the command is still `mockingbird`): `cargo install mockingbird-cli` and `cargo binstall mockingbird-cli` once 0.1.0 is on crates.io, and `-p mockingbird-cli` in cargo commands. The `publish-cli` release job publishes it with the internal crates as `mockingbird-<name>` (`mockingbird-engine`, `mockingbird-protocols`, …; libraries still `mb_*`), which pin each other to the workspace version and carry no API stability guarantee; `mb-ext` keeps its name and its own semver.
- GraphQL mutations generate only their selection, like queries (GitHub `createIssue`: 38.8k → 745 prompt tokens, no fallback).
- `POST`s whose last path segment is a read verb (`/accounts/get`, `/transactions/sync`, `users.list`, `_search`) are imported as reads: cached, seeded, and generated knowing the lists other reads stored; a webhook target fires for such a read only when it names its operation.
- `mockingbird verify` prints a short text summary by default (`--format text`): the totals and one line per failed check, naming the most frequent reasons; `--format json` keeps the whole report.
- Validation errors (fallback reasons, logs, repair prompts, request-validation 400s) read `<pointer>: <keyword>: <message>`, follow a failed `anyOf`/`oneOf` into its closest branch and mask long quoted values.
- The GitHub GraphQL example's `--full` downloads GitHub's own `schema.docs.graphql` (github/docs, CC-BY-4.0) instead of octokit/graphql-schema, so current `gh` queries validate.
- Requests to OpenRouter send `reasoning: {enabled: false}` unless the profile's `extra_body` sets `reasoning`; a model that rejects it is asked again without it.
- A single object answered for a top-level array schema is taken as the list's one item instead of costing a repair; a faker list standing in for a failed LLM call no longer seeds session state.
- A fallback answer to a read is cached under consistency: the identical repeat is answered at once and still reported as `fallback`.
- GraphQL queries with several root fields read state, the response cache and stored resources per field, seed and cache per field, and are recorded as one request (operations comma-separated, `request.args` keyed by response key); each field is still metered.
- MCP `list_requests` returns summaries (method, path, status, source, fallback reason, sizes) unless `include_bodies: true`; `validate_contract` returns counts by protocol and the first 20 operations and channels (`operations_truncated`, `channels_truncated`).
- Background-server logs carry no ANSI codes (colour only on a terminal; `server_logs` strips any left), and the MCP server tools find the server's state next to the config `start_server` used (or the `config` argument), not in the MCP process's folder.
- The mock-api and testing skills recommend proxy mode over editing an app's base URL.
- Every config reload logs at info, `serve -c` without `--watch` says it reads the file once, and a changed `proxy:` section logs that it needs a restart.
- A `file:` secret reference into `~/.mockingbird/secrets` is refused when the file is readable by group or others; other `file:` paths (container mounts) are unchanged.
- `mockingbird mcp`'s login-shell import also fills a variable that is set but empty (an agent's `${NAME:-}` passthrough) when the shell has a value.
- `server start` drops `HTTP(S)_PROXY` variables that point at the server's own proxy from the server's environment.
- Faker integers without tight bounds (and count-like fields) are drawn from 0..=100 (id-like fields such as `id`, `owner_id`, `userId` from 1..=1 000 000), ignoring bounds wider than ±2^31; nullable arrays are never `null`; strings without a `maxLength` are at most 64 characters.
- An LLM string over 2 000 characters where the schema sets no `maxLength` is cut to 200 (`repaired`); the prompt asks for free text under 200 characters.
- `pattern`, `maxLength`, `minLength`, `enum`, `format` and `const` errors in an LLM answer are patched locally without a repair call.
- Generated lists get unique item ids, and a create never reuses an id the session already holds.
- LLM profiles default to a 60 s timeout and 16 384 output tokens (were 3 s and 2048): a large response from a remote model takes 30 s or more.
- The OpenRouter preset uses `deepseek/deepseek-v4.1-flash`.
- `mockingbird llm test` with no flags tests the default profile of `./mockingbird.yaml`.
- MCP `start_server` refuses a config whose default profile's key the server cannot see, unless `offline: true`.
- Documentation import extracts at temperature 0 in JSON-object mode.
- The MCP "is a server running?" hint appears only when the Admin API is unreachable.
- GraphQL root fields are generated from the query's selection set: the prompt, validation and fallback use only the selected fields (fragments merged, each field's arguments noted); creates and updates are still generated whole, since they become stored state. GitHub's `viewer { login … }` went from ~347k to ~1k prompt tokens.
- The prompt (and the JSON Schema response format) carries the response schema as compact JSON fitted to 64 KiB: past that, descriptions are cut to 160 characters and the definitions furthest from the root become short stubs. Validation still uses the full schema. Stripe's `payment_intent` went from ~357k to ~23k prompt tokens.
- The prompt asks for arrays of 3 to 5 items unless the request names a count.
- The Admin API request log (and MCP `list_requests`) includes `fallback_reason`.
- `POST …/contracts/{version}/approve` also activates the version unless the body is `{"activate": false}`; `mockingbird import --approve` activates unless `--no-activate`. The console still approves and activates in two steps.
- Drafts keep the documentation's operation ids (converted when invalid, the original in `x-original-operation-id`), get `required` and nullable properties from the examples and the text, drop `default` values the documentation does not state, and leave out operations below 0.4 confidence with a `low_confidence` warning.
- `/readyz` reports `config_reload: <error>` after a failed config reload until the next good one, and words a failed mock rebuild as `stale, serving the previous version` or `failed`.
- Config reloads log `config reloaded: N added, N removed, N changed`.
- The root fields of a GraphQL query are generated in one LLM call, as one object keyed by response key, so they agree with each other (GitHub's `user(login:)` and `organization(login:)` no longer both answer). A nullable field may be left out of that answer; one that stays invalid after the repair is answered field by field as before. Mutations, subscriptions and queries with root-level fragments or directives are unchanged.
- An LLM answer whose only errors are nulls the schema does not allow is patched instead of sent back for a repair call: an optional property is dropped, a required one gets a faker value. The response's source is `repaired`. Real APIs return null where their docs never say so (TMDB's `belongs_to_collection`), and models copy them; this saved a 20–40 s repair call on 4 of 8 TMDB detail pages.
- An answer wrapped like a GraphQL response (`{"data": {"user": {...}}}`) is unwrapped like an array envelope.
- The default LLM is OpenRouter: `MB_LLM_BASE_URL` defaults to `https://openrouter.ai/api/v1` and `MB_LLM_MODEL` to `deepseek/deepseek-v4.1-flash` (DeepSeek V4.1 Flash), so `MB_LLM_API_KEY` is an OpenRouter key. Set both variables to keep using DeepSeek directly (`https://api.deepseek.com`, `deepseek-chat`). The example configs and tests use an `openrouter` default profile.

### Fixed

- A create or update copies only the request members its response schema declares (all of them when it declares none): undeclared fields such as Twilio's `To`/`Body` in request casing or a credential sent in the body no longer appear in answers.
- An answer wrapped as `{"data": …, "errors": null}` is unwrapped like `{"data": …}`, and `minimum`/`maximum`/`multipleOf` violations are patched locally instead of costing a repair call.
- The GitHub GraphQL example mounts at `/graphql`, so it shares `api.github.com` with the GitHub REST example in one config.
- `serve --watch` sees updates to a config or contract mounted from a Kubernetes ConfigMap or Secret, which arrive as a swap of the volume's `..data` link rather than a change to the file.
- Provider replies with the answer only in `reasoning`, errors inside a 200, or output cut at `max_tokens` are handled (with one retry for transient failures) instead of falling back without a reason.
- A JSON array the model wrapped in a one-key object (JSON-object mode) is unwrapped when the inner value matches the schema.
- Real-world contracts load: a `$ref` inside a vendor extension (Stripe's `x-expansionResources`, GitHub's `x-github-breaking-changes`) no longer fails compilation, and an unresolvable `$ref` names its referrer and the JSON pointer where it sits.
- GraphQL schemas with covariant interface fields serve (GitHub's `User.email: String!` implementing `ProfileOwner.email: String`): implementations are checked with the spec's rules instead of async-graphql's inverted check.
- OpenAPI 3 `application/x-www-form-urlencoded` and `multipart/form-data` request bodies are compiled, decoded and validated; the engine no longer sees `"body": null` for them, nor for any non-empty body the contract does not describe. Bracket notation (`a[b][c]=1`, `a[0]=x`, `a[]=y`) nests in form bodies and query strings, so stripe-node requests validate against Stripe's schema. The request log shows the body as decoded. Swagger 2 `type: file` parameters are binary strings.
- GraphQL aliases of one field with different arguments (`small: repositories(first: 1)`, `large: repositories(first: 5)`) get separate generated values; aliases with identical arguments share one.
- Chaos errors on an operation that declares only a `default` error response (Stripe) answer HTTP 503 in that shape, with its message-like field set, instead of problem+json.
