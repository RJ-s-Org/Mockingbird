# Changelog

All notable changes to this project are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).
The `mb-ext` crate follows semantic versioning on its own from 1.0.

## [Unreleased]

### Added

- `mockingbird snapshot export --include scenarios,chaos,limits` adds each mock's scenarios (`scenarios/<mock>/<scenario>.json`, with its default scenario), chaos and limits to a snapshot, and `snapshot import` restores whichever a snapshot holds on the mocks it creates. Opt-in only: a plain export writes exactly the files it wrote before, the format version stays 1 and older snapshots import unchanged; an older build importing an opt-in snapshot restores chaos and limits but not scenarios ([snapshot directory](docs/ci.md)). `mockingbird-cli` (additive) gains `snapshot::SnapshotPart`, `SnapshotExportArgs`, `export_with` and `client::WorkflowCommand::SnapshotExport`.
- WSDL imports follow `wsdl:import` within the upload: an archive (or `mb_import::compile_files`) with several `.wsdl` files is rooted at the one that holds `wsdl:service`, and the messages, portTypes, bindings and types of the WSDLs and XSDs it imports are used, resolved relative to the importing file, each document once (cycles are fine), at most 16 imports deep. Definitions are looked up by namespace and name. `?wsdl` points followed imports at `?xsd=<upload path>`, which serves them. A location that is not in the upload is still not fetched: an error names it when its definitions are needed, else `wsdl_import_ignored` warns ([WSDL known limits](docs/protocols.md#known-limits)). Several `.wsdl` files were refused before.
- REST responses that declare only a non-JSON media type are served in it instead of as an empty body or JSON: a declared example as written (any media type), a faked text body for `text/*`, XML rendered from the generated JSON by the SOAP XML mapper, and `application/octet-stream` only from a declared example (the import warns `response_body_omitted` without one). Text and example answers never call the LLM ([response media types](docs/protocols.md#response-media-types)). The OpenAPI and Swagger importers now keep the schema of text and XML responses and put a declared example in its `examples`; re-import a contract to pick this up. `mockingbird-engine` gains `NON_JSON_MEDIA_REASON`.
- The CLI finishes the import workflow without the console: `mockingbird drafts approve <mock> [<version>]` (the newest draft by default; `--no-activate`), `mockingbird contracts list <mock>` and `contracts activate <mock> <version>`, `mockingbird mocks update <name>` (`--prefix`, `--persona`, `--profile` and a JSON `--patch FILE|-`), and `mockingbird api <METHOD> <PATH>`, which sends any Admin API request with a JSON body from `--data` (inline, `@FILE` or `@-`) and prints the answer, problem details on stderr for a non-2xx one. They match the MCP tools `approve_draft`, `list_contract_versions`, `activate_contract_version`, `update_mock` and `admin_api`. `import --approve` on a draft with warnings now names the `drafts approve` command to run after review ([CLI client](docs/cli.md)). `mockingbird-cli` (additive) gains `client::WorkflowCommand` and `run_workflow`, and `config::command`, `parse`, `parse_from` and `Invocation`, which parse them beside the existing `Cli` (whose enums are unchanged).
- GraphQL accepts batched requests: a `POST` whose JSON body is an array of `{query, variables, operationName}` operations (at most 10, `mb_protocols::graphql::MAX_BATCH_OPERATIONS`) is answered `200` with an array of responses in the same order. Each operation runs in turn as if sent alone: checked against the root-field and size limits, admitted (tenant, quota and, in `api_key` mode, the key), given its own chaos decision and recorded as its own request; a refused one answers its own `{errors}` entry. The largest injected latency is waited once. A larger or empty batch is a `400` problem; batches used to fail with a serde error ([batched requests](docs/protocols.md#batched-graphql-requests)).
- The faker is seeded: the same seed, contract and request (path parameters, query and body) give the same faker body, with dates drawn back from a fixed day instead of the clock, so `--offline` runs repeat as the testing skill promises. Offline answers default to seed `0`; `mocks.<name>.faker_seed` sets another, and `X-Mockingbird-Seed: <n>` overrides it for one request (honoured with header overrides, a `400` when it is not an integer, and part of the session's read-cache key). LLM fallbacks stay random unless a seed is set; event messages are not seeded. `mockingbird-engine` gains `Engine::with_faker_seed`, `Engine::faker_seed`, the `seed` module (`SEED_HEADER`, `DEFAULT_FAKER_SEED`, `SEEDED_NOW`, `request_seed`), `Faker::with_now` and `PersonaFormats::apply_with`; `mockingbird-store`'s `MockBehavior` gains `faker_seed`.
- REST mocks honour the contract's base paths: Swagger 2.0 `basePath` and the paths of OpenAPI `servers[].url` (variables replaced by their defaults). Each operation is served under every base path as well as at its own path, so `GET /v1/orders` and `GET /orders` both work and existing mocks keep their routes; a contract path wins over a prefixed one ([base paths](docs/protocols.md#base-paths)). `mb_import::base_paths`, `RouteTable::with_base_paths` and `MockRuntime::base_paths` expose it.
- Console sessions end after `auth.session_idle_timeout` without use (default `1h`, `0` disables), on top of the absolute `auth.session_ttl`; the `last_seen` time that was written but never read decides it. Existing deployments get the 1-hour default; set `0` to keep sessions alive until their TTL as before. `GET /api/v1/console-sessions` lists live sessions (everyone's for a sysadmin, otherwise the caller's), `DELETE /api/v1/console-sessions/{id}` ends one and `DELETE /api/v1/console-sessions?subject=<sub>` every session of a principal (audited as `console_session.revoke` and `console_session.revoke_all`); the console's user menu gains **Sign out everywhere** ([sessions](docs/console.md#auth-modes)). `mockingbird-auth` gains `SessionManager::with_idle_timeout`, `list`, `get`, `revoke`, `revoke_all`, `session_id` and `SessionInfo`; `mockingbird-store` gains defaulted `ControlStore::list_admin_sessions`, `delete_admin_sessions_of` and `delete_idle_admin_sessions`.
- Console session roles are re-derived after login instead of being a snapshot of it: from the stored provider claims when the role mapping changes, and, when the provider issued a refresh token (request `offline_access` if yours needs it), from the provider every 5 minutes; a refused refresh ends the session ([roles after login](docs/console.md#auth-modes)). The refresh token is stored sealed under a key derived from the session cookie. Migration `0900_admin_session_grants` adds nullable `admin_sessions` columns. `mockingbird-auth` gains `OidcClient::finish_login`, `refresh_grant` and `mapping`, `FinishedLogin`, `LoginGrant`, `SessionManager::create_from_login`, `with_role_refresh` and `with_role_refresh_interval`, `DEFAULT_ROLE_REFRESH_INTERVAL`, and refresh-token support in `testing::MockOidcProvider`; `mockingbird-store` gains `AdminSessionGrant` and defaulted `ControlStore::get_admin_session_with_grant`, `put_admin_session_grant` and `claim_admin_session_refresh`.
- Contract imports report what they relax or skip as warnings (returned by `mockingbird validate`, uploads and the version list; they never block activation): `status_range_expanded`, `dangling_ref`, `cookie_param_ignored`, `response_header_unresolved`, `xsd_wildcard_ignored` and `wsdl_import_ignored` ([import warnings](docs/protocols.md#import-warnings)). `mb_import::compile_files_with_warnings` is the multi-file counterpart of `compile_with_warnings`.
- OpenAPI response ranges (`2XX` to `5XX`) are no longer dropped: each stands for the common codes of its class that the operation does not declare itself (`4XX` for 400, 401, 403, 404, …), so scenarios can force them. Explicit codes win, and an explicit 2xx keeps `2XX` from adding `200`.
- OpenAPI, Swagger 2.0 and AsyncAPI contracts split into several files import as one contract: in an archive upload, a directory given to the CLI (`mockingbird import api/`, `mockingbird validate api/`) or `mb_import::compile_files`, `$ref`s naming other uploaded files (`./schemas/pet.yaml`, `../common.yaml#/Error`) are resolved relative to the file holding them and bundled into the stored contract: schemas become named definitions (recursive ones included), other objects are copied in place. Paths that climb out of the upload are refused, URLs are never fetched, and bundling is capped at 32 MiB and 64 nested refs ([multi-file contracts](docs/cli.md#archive-uploads)). A lone file with such a ref fails with an error saying what to do instead of "unresolvable $ref".
- OpenAPI 3.0 `x-webhooks` (GitHub's spec) are read as webhook payloads, like 3.1 `webhooks`.
- Smart import converts Swagger 2.0 blocks embedded in documentation pages to OpenAPI 3.0 and takes their operations as written, as it does for OpenAPI 3 blocks; the `embedded_swagger2` warning is gone.
- `DELETE /api/v1/workspaces/{ws}/mocks/{mock}/contracts/{version}` deletes a contract version that is not active (rejected imported drafts were kept forever, up to 20 MiB each), with the finished import jobs that produced it; the active version and mocks from the config file are a `409`. It needs the edit permission and records `contract.delete` in the audit log. The console's contract list has a **Discard** button for it. `mockingbird-store` gains a defaulted `ControlStore::delete_contract_version`.
- Console logins log, at info, the `<prefix>:` groups of the identity provider that grant nothing (an unknown role, a missing segment or an invalid workspace name), which were dropped silently; bearer tokens log them at debug. `RoleMapping::ignored_groups` returns them.
- SOAP: `GET ?wsdl` points the `schemaLocation` of every XSD uploaded with the WSDL at `GET <address path>?xsd=<upload path>`, which serves that XSD with its own references rewritten the same way, so WSDL tools can resolve a multi-file contract from the mock. The importer embeds the uploaded schemas in the stored WSDL; contracts imported earlier gain this when imported again.
- gRPC: gzip-compressed requests are accepted, and responses are gzipped for clients that send `grpc-accept-encoding: gzip`; they were refused with `UNIMPLEMENTED` ("Content is compressed with `gzip` which isn't supported").
- WebSocket event channels receive binary frames like text frames: a JSON frame is validated, recorded and replied to, anything else is recorded as a `400`. They were dropped without a trace.
- Console logout ends the identity provider's session too when its discovery document advertises an `end_session_endpoint`: `POST /auth/logout` then answers `200` with `{"end_session_url": …}` (with `client_id` and `post_logout_redirect_uri=<external_url>/`) and the console goes there. Without the endpoint it answers `204` as before ([signing out](docs/console.md#auth-modes)). `OidcClient::end_session_url` and `with_post_logout_redirect` expose it.
- Streamed LLM calls are charged the tokens the provider reports instead of a `ceil(bytes / 4)` estimate: OpenAI-compatible streams ask for `stream_options: {"include_usage": true}` (dropped for good when an endpoint rejects it, like the reasoning switch), and the stream is read to its end with the last item, for at most 1 s, to get the final usage chunk. The token budget, the `mb.llm` span and the per-item usage (summed over the items) then carry the reported numbers; without a report they are estimated as before, and replayed snapshot streams cost nothing. `mockingbird-llm` gains a defaulted `Provider::stream_metered`, `MeteredStream`, `StreamUsage` and `ScriptedProvider::with_stream_usage`.
- `mb-evals run` reports what it did not evaluate: `report.json` and `report.md` list `skipped_contracts` (corpus files that could not be read or do not compile), `skipped_calls` (calls the engine rejected) and `skipped_streaming_operations`, and `--max-skipped <n>` fails a run that skips more calls and contracts than that. Before, skips were only logged, so a shrinking corpus still passed.
- A server built without the console (no `npm run build` before `cargo build`) logs a warning at startup naming the build command, instead of silently serving the "Console not built" page.
- LLM profiles take `output_mode: none | json_object | json_schema` (`MB_LLM_OUTPUT_MODE`, `--output-mode`, the Admin API's `output_mode` and the console's **Output mode**). `none` sends no `response_format`, for models that answer badly or not at all in JSON mode; the default stays `json_object`. In `json_object` mode an operation returning an array is asked for as `{"items": [...]}` and unwrapped, since JSON mode forces an object at the top level and models invented envelopes of their own. Migration `1000_profile_output_mode` adds a nullable `llm_profiles.output_mode` ([configuration](docs/configuration.md#llm)). `mockingbird-llm` gains `OutputMode`, `OpenAiConfig::output_mode` (replacing `json_schema`) and `ScriptedProvider::with_capabilities`; `mockingbird-store` gains `OutputMode` and `LlmProfile::output_mode` (replacing `json_schema`).
- `X-Mockingbird-Source: patched` (and `source="patched"` in metrics, the request log and usage events) for an LLM answer fixed locally without a second call; `repaired` now means only an answer fixed by a repair call, so first-try quality is no longer under-reported. `mockingbird-engine` gains `Source::Patched`, `mb-ext` `UsageEvent::SOURCE_PATCHED`.

- The faker generates for `additionalProperties` and `patternProperties` schemas (a map gets an entry, keyed to match its pattern), `minProperties` and `maxProperties`, `prefixItems` (positionally, with `items: false` closing the list) and `contains`/`minContains`. Avro maps and tuple schemas were answered with an empty object or ignored positions, and an offline answer to them failed validation. `not` and `if`/`then`/`else` are still left to the faker's retries.
- Metrics `mb_faker_invalid_total` (a faker answer that matched no schema-valid draw) and `mb_scenario_set_ignored_total{reason}` (a scenario `set` dropped at request time: `invalid` or `not_an_object`).
- `mb-ext` (additive): `Rejection` implements `Display` (`429 Quota exceeded: …`) and `std::error::Error`, and gains `Rejection::from_status(http::StatusCode, …)`; `Extensions` implements `Debug` (it names no extension); `UsageEvent::SOURCE_*` name the documented `source` values. The crate docs have a worked example, and fallible functions and trait methods have `# Errors` sections.
- `mockingbird-llm`, `mockingbird-store`: every public type implements `Debug`, and none prints a secret: `HttpOptions` shows a proxy URL without its user and password (as do `OpenAiConfig`'s `base_url` and the client's "invalid proxy" error), `OpenAiCompatible` shows its redacted config, and `PgStore`/`SqliteControlStore` show pool sizes, never the connection URL. `mb_llm::Role` and the store's `ResourceSource`, `ContractStatus`, `ImportJobStatus` and `RequestKind` implement `Display` (their wire names) and, in the store, `FromStr`; those store enums and `DataPlaneAuthMode` are also `Copy`, `Eq` and `Hash`. By-value builders are `#[must_use]`.
- `mockingbird-protocols`: every public type implements `Debug` (`MockRuntime`, `Brokers`, `GrpcServer` and the broker clients among them; none shows a credential, a secret or the contract); `RequestKind`, `BrokerKind` and `DeliveryStatus` implement `Display` and `FromStr` (an unknown name is a `ParseNameError`); its small enums derive `Hash`; `DispatchSettings::retry_delay` replaces the free function `webhooks::deliver::retry_delay`, now deprecated. The crate docs gain an example, `# Errors` and `# Panics` sections, and docs.rs builds them with every feature.
- `mockingbird-import` (additive): typed errors with the same messages, `TriggerError` from `check_triggers` and `AllowlistError` from `AllowEntry::parse_entry` and `FetchPolicy::parse_allowlist`. Every public type implements `Debug`: `ExtractLlm` shows its settings and the provider's capabilities, never the provider, and `ImportInput` shows the length of uploaded bytes and a URL without its user, password or query values. `ImportKind` implements `Display` and `FromStr`, `Phase` implements `Display`, `SourceFormat`, `Phase` and `AllowEntry` are `Hash`, and `ParamLocation` is `Copy`, `Eq` and `Hash`. The crate docs have an example and a features section, fallible functions have `# Errors` sections, and docs.rs builds the `smart` module.

The hand-written impls print no secrets: `LeaderBackend` shows its Postgres or Redis URL without user info, query or fragment, `Engine` never shows its provider, and `Faker` shows its hint names but not the request values. ### Changed

- Event channels and webhooks use the per-call provider policy too, instead of always the mock's configured profile. Broker and WebSocket replies and trigger messages (scheduled, cron, state change) ask the policy with their tenancy: a WebSocket client's from its upgrade, otherwise the `TenantResolver`'s for the channel's operation id and, for a broker reply, the consumed message's headers, falling back to tenant `default` for the policy when the resolver refuses. A broker reply's usage event is now attributed to that tenancy (it was resolved without the message's headers). A webhook payload uses the profile chosen for the call that sent it. A policy's refusal skips that one message with a warning, a `PUBLISH` record with its status, a publish error in the channel's activity and metrics, and a `not_generated` usage event; the consumer or trigger carries on. The self-hosted defaults (`SingleTenant`, `ConfiguredProfile`) choose the same tenant and profile as before and build no second engine. Manual publishes still use the configured profile ([event channels](docs/events.md)). No public API changes.

- A changed LLM profile rebuilds only the mocks that use it, on every node, instead of every mock: those naming it, those naming none while it is the default, those whose fallback chain reaches it, those whose calls the provider policy sent to it (their cached engine for it is dropped with the runtime), and those whose last build failed. A change of `llm.default_profile` rebuilds only the mocks naming no profile. Workspace changes and resyncs still rebuild every mock. `MockRegistry` gains `reload_profile` and `reload_default_profile_mocks`.
- The provider policy (`mb-ext` `ProviderPolicy`) is asked for every call with the call's tenancy, as its documentation said, instead of once per mock build as tenant `default`. Data-plane calls ask it after admission; a profile other than the configured one generates with that profile's provider chain, built on first use and kept for the mock (until the mock or a profile changes); a rejection is answered as the call's problem (`application/problem+json`, its status and `Retry-After`), like a quota's, instead of failing the mock's build. Imports and draft previews resolve their tenant through the `TenantResolver` (operation `import` or `draft`, the Admin API request's headers, the request's workspace) instead of always billing tenant `default`; the import worker bills the tenant its job was created for, and a resolver's or policy's refusal is the request's problem. The self-hosted defaults (`SingleTenant`, `ConfiguredProfile`) choose the same tenant and profile as before, so single-tenant servers see no change: no new configuration, and no second provider is ever built. `mb-ext` gains no API. New, additive: `mb_protocols::ProfileEngines`, `MockRuntime::{configured_profile, profile_engines, engine_for}`, `mb_admin::LlmAccessError` with the defaulted `LlmResolver::{import_llm_for, preview_engine_for}`, and `mockingbird::runtime::{import_provider_for, preview_engine_for}`.
- `mockingbird-cli`: `server::binds_for` (a `(bool, bool, bool)` tuple) and `Snapshot::open(dir, replay, record)` are deprecated in favour of `Binds::for_role` and `Snapshot::open_with`. `ServeError::Other`'s `Display` shows the error's own message instead of the whole chain (`{e:#}`); the causes are its `source()`.
- `mockingbird-import`: `validate_triggers` and `FetchPolicy::from_allowlist`, which return `String` errors, are deprecated in favour of `check_triggers` and `FetchPolicy::parse_allowlist`, which return typed errors with the same messages. The `smart` submodules that only this crate's tests use (`chunk`, `complete`, `embedded`, `har`, `infer`, `llm`, `paths`, `postman`, `text`) are hidden from the docs; they become private in 0.2.

- API keys are verified from a short-lived cache instead of a control-store read on every call: data-plane calls to `data_plane_auth: api_key` mocks and Admin API calls with a key read the store once per key every 5 seconds (10,000 checks on SQLite: 36 to 0.9 µs each), and concurrent calls write `last_used_at` once. A revocation through the Admin API applies at once on that node; other nodes of a cluster can accept the key for up to 5 seconds ([API keys](docs/console.md#api-keys)). `mb_auth::ApiKeys::with_cache`, `ApiKeys::invalidate_caches`, `DEFAULT_API_KEY_CACHE_TTL` and `StoreDataPlaneKeys::with_keys` expose it; `ApiKeys::new` and `StoreDataPlaneKeys::new` still read the store every time.
- Generated answers are checked against the `format`s the faker produces (`uuid`, `date-time`, `date`, `time`, `email`, `uri`, `ipv4`, `ipv6`, `hostname`): a value breaking one (an LLM's `"createdAt": "yesterday"`) is refilled locally and the answer is `repaired`, without a repair call. A value equal to a request path or query value is kept, so a path id echoed into a `format: uuid` field survives. Other formats, and request validation, keep `format` as an annotation. `SchemaValidator::for_output`, `is_valid_output` and `patch_keeping` are new.
- `mockingbird-llm`: `OpenAiCompatible::reasoning_off` is deprecated in favour of `with_reasoning_disabled`, which does the same.
- LLM answers are read from the first complete JSON value in the reply (after the whole text and a Markdown fence) instead of the text from the first `{` to the last `}`, so two objects back to back (`{..}{..}`) or trailing prose with braces no longer make the answer unparseable. A value nested in a broken or truncated answer is never taken for the answer (a truncated reply still goes to repair), and an empty `{}` or `[]` in prose loses to a later value.
- The `json_schema` profile key, `MB_LLM_JSON_SCHEMA` and `--json-schema` are deprecated aliases of `output_mode` (`true` is `json_schema`, `false` `json_object`); setting both keys (or both `configure_llm` arguments) is an error, as is an unknown `MB_LLM_OUTPUT_MODE`. The Admin API still reports `json_schema` beside `output_mode`, and a stored `output_mode` that contradicts the `json_schema` flag (written by an older node during a rolling upgrade) reads as the flag. `mockingbird-cli`'s `LlmEnv::from_env` is deprecated in favour of `try_from_env`, which rejects an invalid `MB_LLM_OUTPUT_MODE`.
- A faker answer that matches no schema-valid draw (a schema the faker cannot satisfy, such as one relying on `not`) says so: its `X-Mockingbird-Fallback-Reason` ends with `faker output does not validate against the schema` (`mb_engine::FAKER_INVALID_REASON`). It was served as if valid.
- An offline answer without a body (a `204`) is labelled `X-Mockingbird-Source: fallback` with the offline reason; it was labelled `llm`.
- A scenario's `set` is checked when it is written: with an active contract, `PUT …/scenarios/{name}` answers `422 Invalid scenario` naming the pointer (`set/total fits no response the scenario can select (getOrder 200: …)`) when no response the scenario can select accepts a key present in `set`, and the config file is refused at load the same way. Such a `set` was dropped at request time with only a WARN. Absent keys and `required` are not checked, and `null` is always accepted. `mb_admin::invalid_scenario_set` holds the shared check.
- Audit webhook: a failing event is retried in the background (at most 64 at once) instead of holding up the queue, so one event's 7 s of backoff no longer delays every event behind it (the next event went out after 0.7 s with a 100 ms backoff base, now after about 2 ms). First attempts keep the queue's order, but a retried event can now arrive after later ones; order by the event `id`.
- Admin API reads fetch less from the store: listing mocks reads every active version number in one query instead of one full contract per mock (100 mocks with 256 KiB contracts: 10 to 1.0 ms on SQLite, 23 to 1.1 ms on Postgres); listing contract versions and `requests?fields=summary` no longer read sources and bodies (500 entries with 32 KiB bodies: 365 to 5 ms on SQLite, 481 to 13 ms on Postgres); drafts, channels, scenarios and uploads read the active bundle without its source, and a draft's parse and diff run off the async runtime; scenario validation checks operation names through hash sets (5,000 operations: 86 to 16 ms). `mockingbird-store` gains defaulted `ControlStore` methods for this (`active_versions`, `active_bundle`, `list_contract_version_infos`, `latest_contract_version`, `list_request_log_summaries`) and the `ActiveBundle`, `ContractVersionInfo` and `RequestLogSummary` types.
- The gRPC service conflict check (contract uploads and activation, and config reload against mocks managed through the API) reads the other mocks' active bundles 64 per query instead of one query per mock, and config reload no longer reads their sources (500 mocks on SQLite: 30 to 15 ms). `mockingbird-store` gains a defaulted `ControlStore::active_bundles`.
- `mockingbird` serve and proxy do less per change and per request, with the same results: queued control changes are applied once per mock (a burst of 100 changes to one mock: 26 to 2 ms until the next change is mounted); a reload of every mock builds 8 at a time in name order (40 mocks with 2 ms store reads: 316 to 39 ms); the proxy's claimed-host check is one set lookup (10,000 hosts: 1.5 ms to 86 ns); request-log records are not copied when nobody tails the log, and their redaction and truncation no longer allocate per key or hold the whole serialized body (a 10 MB response: 73 to 61 ms); HA state-change announcements are published from a queue of their own, so a slow bus no longer delays this node's change feed (500 changes with a 1 ms bus: 1.26 s to 1 ms); the request-log relay of another node lists the mocks at most once a second for entries of an unknown mock (200 lookups: 152 to 1.2 ms); and `serve --record` holds each answer once (10,000 answers to one prompt: 796 to 7.6 ms). The proxy now remembers at most 500 unmapped hosts: past them, new hosts are not logged and are counted as `host="other"` in `mb_proxy_unmapped_requests_total` (and `mockingbird report`) instead of adding a series each ([proxy](docs/proxy.md)).
- SQLite request-log pruning deletes by an id range on the `(mock_id, id)` index instead of `NOT IN` the kept rows, so its cost no longer grows with the retention (100 appends with one prune at a retention of 100,000: 46 to 12.5 ms).
- The response engine does less per answer, with the same answers: faker answers reuse each schema's definitions, cost table and compiled patterns (an offline answer 108 to 60 µs), persona templates are matched without compiling a regex per object (a 1,000-item list 26 to 0.4 ms), local patches fake from the validator's schema instead of copying its definitions per error (a 12-error patch 1.1 to 0.28 ms), validity checks stop at the first error, and the budget-shape caches are bounded across contract uploads. `SchemaValidator` gains `is_valid` and `declared_property_names`.
- `vault:` secrets: concurrent cache misses on one reference share a single Vault read (16 concurrent resolves of two references made 16 requests, now 2), and expired values are evicted when a new one is cached instead of staying in memory. Failed reads are still not cached.
- Session state hot paths: the in-memory store keeps each session's resources per type in recency order, so a list reads only the items it returns and reads share the session lock (a 20-item list in a 10,000-resource session, 77 µs to 3.2 µs, flat in the session size); the Redis store lists in one Lua round trip that pages the order set newest first and stops at the limit, instead of fetching every member of every type; and the response cache evicts its least recently used answer from a recency index instead of a scan (a put at capacity 5,000, 30 µs to 0.5 µs).
- Hot-path trims: `PrometheusUsage` shares each label value across its series and reuses status and source label text (about 240 instead of 390 to 500 ns per call without a recorder, 0.88 instead of 1.18 µs with a registry); the console serves embedded files without copying them per request; JSON found in a reasoning-only LLM reply is validated without being built (2.4x faster on 10 KB of reasoning); event channel lookups by id (manual publish, request-reply) use an index instead of a scan (300 channels: 1.6 µs to 0.2 µs).
- Reads by a path field that is not the stored id (GitHub's `GET …/issues/{issue_number}`) find a resource the mock wrote or seeded without scanning the session's resources of that type (500 stored issues, in-memory store: 316 to 1.4 µs per read); resources written elsewhere (the Admin API, another node) are still found by the scan. GraphQL root fields reuse the narrowed schema of a selection they saw before (bounded cache) and hash it for the response cache key without printing it (GitHub `viewer`, 12 fields: 48 to 7 µs per root field). Same answers.

### Deprecated

- `mb_mcm::OperationKind::label` (use `as_str` or `Display`, same text), and `LocalBus::new`, `MemoryBusHub::new` and `GenerationLimiter::new`, which return an `Arc<Self>` (use `new_shared`; in 0.2.0 `new` will return `Self`).

### Fixed

- A `rediss://` state, bus or leader URL no longer crashes the `mockingbird` binary. sqlx's `tls-rustls` feature enabled rustls's `ring` provider next to `aws-lc-rs`, so rustls could not choose a process default and `redis` panicked building its TLS config ("Could not automatically determine the process-level CryptoProvider"). sqlx now uses `tls-rustls-aws-lc-rs`, `ring` is no longer compiled into the CLI, and the binary installs the aws-lc-rs provider at startup.
- `mockingbird-protocols`: the `Debug` output of `BrokerConfig` and of a webhook `ResolvedTarget` (and so of `WebhookDispatcher`) shows the URL without userinfo (`amqp://user:password@…`), and for webhooks without the query and fragment, which can carry a token; it printed the URL as configured.
- `mockingbird run --offline`, `--record`, `--replay` and `-c` reusing a server that already answers print a warning naming the flags that do not apply to it; a leftover dev server silently turned `run --replay snap -- npm test` into live LLM calls.
- `mockingbird snapshot export` writes each mock's `path_rewrite` and `header_overrides`, and `snapshot import` creates the mock with them, so an imported mock routes like the original; older snapshots import as before. `docs/ci.md` lists what a mock file carries.
- `mockingbird server stop` (and `mockingbird run`) ask the background server to stop through a stop file it watches (`MB_STOP_FILE`, set by `server start`), so on Windows it shuts down gracefully instead of being killed with `taskkill /F`; `/F` is used only after 10 s, and `forced` says when it was.
- The MCP server no longer advertises the `logging` capability: it sends no log notifications (`logging/setLevel` is still accepted).
- The MCP `admin_api` tool returns non-JSON answers (`{content_type, text}`, or `{content_type, bytes, base64}` for binary bodies up to 1 MiB) instead of failing, so a non-JSON contract's `…/source` can be read; an event stream is refused at once instead of hanging the call.
- A `--watch` reload that changes a read-at-startup section (`server`, `storage`, `protocols`, `auth`, `audit`, `outbound`, `bus`, `limits`, `pii`, `import`) logs `config reload: the <section>: section changed; restart the server to apply it`, as it already did for `proxy:`; the edit was ignored without a word.
- `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` alone enables OTLP trace export, and `OTEL_EXPORTER_OTLP_PROTOCOL=grpc` (or the traces variant) logs a warning that spans go over HTTP/protobuf instead of being overridden silently.
- `agent install claude-code --scope user` explains why it cannot pass keys through (a printed `claude mcp add` line would write their values into `~/.claude.json`) and suggests `--scope project` or `mockingbird keys setup`; it said Claude Code cannot read variables.
- MQTT shared subscriptions (with a shared, non-`local` bus) use each mock's consumer group, `$share/<client_id_prefix>-<mock>/<topic>`, instead of `$share/<client_id_prefix>/<topic>` for every mock: two mocks consuming one topic split its messages between them (each got about half); each now gets every message, and the instances of one mock still share them. Messages are told apart per mock with MQTT 5 subscription identifiers when the broker supports them.
- Console logins started on one node failed on another with `unknown login state` (half the callbacks with `mode: split` and two control replicas), and every login in progress failed after a restart: started logins (PKCE verifier, nonce, return path) lived in process memory. They are now kept in the control store (migration `0800_oidc_pending_logins`, SQLite and Postgres), keyed by the sha256 of the `state`, single use, expiring after 600 s and bounded to 10 000. `OidcClient::with_store`, `start_login`, `login_pending` and `cancel_login` are new; the in-memory `begin_login`, `is_pending` and `abandon_login` are deprecated. `mockingbird-store` gains defaulted `ControlStore` methods for this (`put_oidc_pending_login`, `get_oidc_pending_login`, `take_oidc_pending_login`, `delete_expired_oidc_pending_logins`) and the `OidcPendingLogin` type.
- GraphQL: queries using a custom executable directive the schema declares, such as Shopify Storefront's `@inContext(country: …)`, failed validation with `Unknown directive`; the directive definitions were dropped when the schema was built (and, for an introspection upload, when it was rendered to SDL). Such directives are now accepted and ignored, as are the variables only they use; undeclared directives still fail validation.
- GraphQL: a stored schema defining a field, argument, input field, enum value, union member or implemented interface twice in one type (possible in bundles imported before duplicates were refused at import) no longer panics when the mock is served; the mock fails to load with an `invalid GraphQL schema: … is defined more than once` error naming the type and member.
- A `$ref` to a missing component schema (`#/components/schemas/X`, `#/definitions/X`) no longer fails the whole contract (Square's spec): the schema is stubbed as an open schema, with a `dangling_ref` warning. Refs to files that were not uploaded are still refused, with an error that says to upload them or bundle the spec.
- Archive uploads drop `__MACOSX/` entries and hidden files (a zip made in Finder no longer breaks a `.proto` upload), and a single contract beside a README, LICENSE or other documentation compiles; several contracts are refused with an error naming them.
- An upload with several `.wsdl` files, or a WSDL that needs definitions it pulls in with `wsdl:import`, is refused with an error naming `wsdl:import` (which is not followed) instead of "expected one" or "unknown portType" alone.
- `DELETE /api/v1/workspaces/{ws}?force=true` refuses with `409 Managed by config file`, naming them, when the workspace holds mocks or LLM profiles declared in the config file: it deleted them, and the next reload recreated them.
- `docs/configuration.md` says `storage.session_ttl` runs from a session's last use (any request that reads or writes its state), as it always has; it said "last write".
- `docs/admin-api.md` lists the AsyncAPI upload media types and the workspace, API key, audit, `/me`, request-log entry and stream, and webhook delivery endpoints.
- `vault:<mount>/<path>#<field>` secret references work wherever `env:` and `file:` do, as documented: an LLM profile's `api_key` and `${…}` header references in the config file, a broker's `sasl.password`, and an Admin API profile's `secret_ref` and headers (still gated by `server.api_secret_refs`) were refused with "must be a secret reference (env:NAME or file:/path)". A malformed `vault:` reference (such as `vault:token#key`, which the Vault resolver cannot read) is now refused when written, including in webhook `secret`s, which accepted any `vault:` text and failed only at delivery.
- `mb-ext`: `DefaultSecrets` resolving a well-formed `vault:` reference without a usable Vault returns `ExtError::Other` naming the reason (`VAULT_ADDR is not set`, or `Vault is disabled: …` with the configuration error) on every resolve, instead of `ExtError::BadSecretRef` ("invalid secret reference"), which pointed at a correct reference. Malformed references are still `BadSecretRef`.

- HTTP/REST query strings and form or multipart bodies decode in linear time: they were O(k^2) in the number of keys (50k keys took about 11 s) and are decoded before auth, so an unauthenticated request could burn CPU. A request with more than 1,000 query pairs, or more than 1,000 form or multipart fields, is now refused with a 400 `application/problem+json` ("Too many parameters"), and the request log keeps at most 1,000 recorded query or form fields.
- The MCP `stop_server` tool stops a server the same MCP server started at once with SIGTERM: it no longer waits 10 s and reports `forced: true` because the exited server lingered as an unreaped (zombie) child, and `server_status` no longer reports such a server as running.
- Deleting a mock (or a workspace) forgets its webhook deliveries: the in-memory delivery log kept up to 200 records for every mock ever deleted until the process restarted, and a new mock of the same name listed the old one's deliveries.
- The Vault client honours `outbound.proxy`, `outbound.no_proxy` and `outbound.ca_file` like the server's other outbound clients; it followed only the `HTTP(S)_PROXY` environment and `VAULT_CACERT`. `mb-ext` gains `VaultHttp`, `VaultSecrets::from_vars_with_http` and `DefaultSecrets::with_http` (additive); embedders that pass their own extensions use them to do the same.
- In a cluster, a session reset, a seed or a mock reset clears the response cache on every node, not only on the node that made it: other nodes kept answering the reset session's repeated reads from the cache (`X-Mockingbird-Source: cache`) until its next write or idleness. The node announces the reset on the bus as a state event of no resource type, which older nodes ignore.

### Changed

- Less work per call in the protocol adapters, with the same answers: narrowed GraphQL selections and event key, header and address-parameter schemas reuse a compiled validator (bounded cache) instead of compiling one per call; a GraphQL request is parsed once instead of two or three times; subscription frames read only their `type` and `id`; operations are found by id through an index, and the per-create path-field and listed-member walks are computed once per mock; gRPC calls no longer copy their operation and scenario; offline bidi streams no longer copy earlier messages; consumed events copy their payload and headers only for the request log.
- Faster contract and smart imports, with identical results: saving or assembling a draft checks its schemas in one compile instead of one per schema location (a 400-component draft went from 1.8 s to 15 ms), the `schema_too_large` check measures schema sizes without cloning or serializing the reachable definitions (1.8 s to 83 ms for 1,000 operations that each reach 1,000 definitions), `compile` parses a JSON or YAML document once instead of twice, recognising a HAR or Postman upload no longer builds the whole JSON tree (20 MiB in 39 ms instead of 125 ms), and the extra roots of `outbound.ca_file` are parsed once per bundle instead of on every fetch hop.

## [0.1.0] - 2026-10-28

The first release. Since 0.1.0-rc.1, in short:

- **Run apps unchanged.** Mocks take the real host names they stand in for (`hosts:`), and `mockingbird proxy` intercepts HTTPS to them with a local CA, so an app reaches mocks of `api.stripe.com` or `api.github.com` without source edits. `mockingbird run -- <command>` does the whole setup for one command, with preloads that make Node, Python, Java, Go, curl and Deno trust the CA and use the proxy, and `mockingbird proxy browser` for Chromium-based browsers ([proxy](docs/proxy.md)).
- **Deterministic CI.** `serve --record` / `--replay` answers a CI run from recorded LLM answers without a key; `mockingbird report` and `mockingbird verify` turn the request log into a summary, JUnit and a pass/fail gate; a GitHub Action and a GitLab CI template wrap it ([CI](docs/ci.md)).
- **Mocks as infrastructure.** A Terraform / OpenTofu provider and Pulumi ([IaC](docs/iac.md)); mocks declared in Helm values, Kustomize overlays, Argo CD and Flux previews per pull request, Argo Workflows, Tekton and Testcontainers modules for Node, Python, Java and Go ([GitOps](docs/deploy/gitops.md)).
- **21 ready-made API mocks.** `mockingbird examples init stripe` (or GitHub, Shopify, Twilio, Slack, Plaid, TMDB and more) writes a contract, persona, scenarios and webhooks for the real host, plus three sample apps tested against them ([examples catalog](docs/examples.md)).
- **Faster and leaner on real LLMs.** An output budget shapes huge response schemas (GitHub `search/commits` p50 29.8 s → 9.4 s), OpenRouter reasoning is off by default, GraphQL mutations and multi-root queries generate only their selection, and persona-declared id formats are patched locally ([performance](docs/performance.md#latency-against-a-real-llm)).
- **Consistent, stateful answers.** Reads of what a session created come from its state, repeated reads from a per-session cache, and list items seed later reads by id; `unknown_ids: 404`, `default_scenario` and per-operation scenario instructions.
- **Real-world contracts.** Stripe's and GitHub's full contracts load and serve: form-encoded and multipart bodies, covariant GraphQL interfaces, `$ref`s in vendor extensions, prompts fitted to a 64 KiB schema budget, GraphQL answers generated from the selection set, and local patching instead of repair calls. Fallbacks dropped from 25–33% in the field trials to none on the Stripe and TMDB trials; a second round of trials ran plaid/quickstart, healthchecks, the GitHub CLI, Next.js Commerce and Stripe's Java sample unchanged under `mockingbird run` ([trials](docs/trials/README.md)).
- **Diagnosable.** `X-Mockingbird-Fallback-Reason`, `X-Mockingbird-Validation` and the request log say why an answer fell back or a request was rejected.
- **Smart import drafts you can finish.** Several URLs and documents per draft, merge or replace, embedded OpenAPI blocks taken as written, confidence and warnings per operation, and MCP tools to read, edit and approve drafts.
- **Agents set it up alone.** The MCP server finds keys from the login shell, `agent install` passes key names through to each agent, and `keys setup` stores a key without it passing through the agent.
- **Webhooks.** Signed Stripe-style or HMAC events after writes, with retries and a delivery log.

- Webhooks: mocks POST an event after each successful write to the URLs in `mocks.<name>.webhooks` (or the Admin API), signed Stripe-style (`Stripe-Signature`) or with `X-Mockingbird-Signature`, retried 3 times (1 s, 2 s, 4 s); the payload is the contract's OpenAPI `webhooks`/`callbacks` body when defined, else a Stripe-shaped `<resource>.<created|updated|deleted>` event. Migration `0700_mock_webhooks` adds `mocks.webhooks`. See [docs/webhooks.md](docs/webhooks.md).
- GraphQL answers store every object with an `id` under its type (`Cart` → `cart`): a mutation's are merged into the session, a query's added when new, so `cartCreate` → `cart(id:)` → `cartLinesAdd` reads and updates one cart. Mutations are generated knowing what their `<x>Id` arguments and `gid://…/<Type>/…` ids name (in nested inputs too).
- Base64 fields (`format: byte`, `contentEncoding: base64`, `content` beside `encoding: "base64"`) are asked for as plain text and encoded locally; values that do not decode are re-encoded from their text.
- Request-validation rejections have their own source, `rejected` (header, request log, metrics and `report`), instead of `fallback`.
- `mockingbird verify --no-unmatched`: fails when a request matched no operation of its mock's contract; `report` lists those routes.
- `mocks.<name>.graphql_path`: one GraphQL mock's endpoint below its route prefix (Shopify's `/graphql.json`), instead of the server-wide `protocols.graphql.path`.

### Changed

- Relative `sqlite:` paths in `storage.url` / `storage.state_url`, and relative `server.tls`, `outbound.ca_file` and `brokers.<name>.ca_file` paths, are resolved against the config file's directory, like `contract:` paths (were the working directory). Flags, environment variables and runs without a config file keep the working directory. See [Upgrading](docs/upgrading.md#relative-paths-in-the-config-file-follow-the-file).
- The binary's package is `mockingbird-cli` (the command is still `mockingbird`): `cargo install mockingbird-cli` and `cargo binstall mockingbird-cli` once 0.1.0 is on crates.io, and `-p mockingbird-cli` in cargo commands. The `publish-cli` release job publishes it with the internal crates as `mockingbird-<name>` (`mockingbird-engine`, `mockingbird-protocols`, …; libraries still `mb_*`), which pin each other to the workspace version and carry no API stability guarantee; `mb-ext` keeps its name and its own semver.
- GraphQL mutations generate only their selection, like queries (GitHub `createIssue`: 38.8k → 745 prompt tokens, no fallback).
- `POST`s whose last path segment is a read verb (`/accounts/get`, `/transactions/sync`, `users.list`, `_search`) are imported as reads: cached, seeded, and generated knowing the lists other reads stored; a webhook target fires for such a read only when it names its operation.
- `mockingbird verify` prints a short text summary by default (`--format text`): the totals and one line per failed check, naming the most frequent reasons; `--format json` keeps the whole report.
- Validation errors (fallback reasons, logs, repair prompts, request-validation 400s) read `<pointer>: <keyword>: <message>`, follow a failed `anyOf`/`oneOf` into its closest branch and mask long quoted values.
- The GitHub GraphQL example's `--full` downloads GitHub's own `schema.docs.graphql` (github/docs, CC-BY-4.0) instead of octokit/graphql-schema, so current `gh` queries validate.
- Requests to OpenRouter send `reasoning: {enabled: false}` unless the profile's `extra_body` sets `reasoning`; a model that rejects it is asked again without it.
- A single object answered for a top-level array schema is taken as the list's one item instead of costing a repair; a faker list standing in for a failed LLM call no longer seeds session state.
- A fallback answer to a read is cached under consistency: the identical repeat is answered at once and still reported as `fallback`.
- GraphQL queries with several root fields read state, the response cache and stored resources per field, seed and cache per field, and are recorded as one request (operations comma-separated, `request.args` keyed by response key); each field is still metered.
- MCP `list_requests` returns summaries (method, path, status, source, fallback reason, sizes) unless `include_bodies: true`; `validate_contract` returns counts by protocol and the first 20 operations and channels (`operations_truncated`, `channels_truncated`).
- Background-server logs carry no ANSI codes (colour only on a terminal; `server_logs` strips any left), and the MCP server tools find the server's state next to the config `start_server` used (or the `config` argument), not in the MCP process's folder.
- The mock-api and testing skills recommend proxy mode over editing an app's base URL.
- Every config reload logs at info, `serve -c` without `--watch` says it reads the file once, and a changed `proxy:` section logs that it needs a restart.
- A `file:` secret reference into `~/.mockingbird/secrets` is refused when the file is readable by group or others; other `file:` paths (container mounts) are unchanged.
- `mockingbird mcp`'s login-shell import also fills a variable that is set but empty (an agent's `${NAME:-}` passthrough) when the shell has a value.
- `server start` drops `HTTP(S)_PROXY` variables that point at the server's own proxy from the server's environment.
- Faker integers without tight bounds (and count-like fields) are drawn from 0..=100 (id-like fields such as `id`, `owner_id`, `userId` from 1..=1 000 000), ignoring bounds wider than ±2^31; nullable arrays are never `null`; strings without a `maxLength` are at most 64 characters.
- An LLM string over 2 000 characters where the schema sets no `maxLength` is cut to 200 (`repaired`); the prompt asks for free text under 200 characters.
- `pattern`, `maxLength`, `minLength`, `enum`, `format` and `const` errors in an LLM answer are patched locally without a repair call.
- Generated lists get unique item ids, and a create never reuses an id the session already holds.
- LLM profiles default to a 60 s timeout and 16 384 output tokens (were 3 s and 2048): a large response from a remote model takes 30 s or more.
- The OpenRouter preset uses `deepseek/deepseek-v4.1-flash`.
- `mockingbird llm test` with no flags tests the default profile of `./mockingbird.yaml`.
- MCP `start_server` refuses a config whose default profile's key the server cannot see, unless `offline: true`.
- Documentation import extracts at temperature 0 in JSON-object mode.
- The MCP "is a server running?" hint appears only when the Admin API is unreachable.
- GraphQL root fields are generated from the query's selection set: the prompt, validation and fallback use only the selected fields (fragments merged, each field's arguments noted); creates and updates are still generated whole, since they become stored state. GitHub's `viewer { login … }` went from ~347k to ~1k prompt tokens.
- The prompt (and the JSON Schema response format) carries the response schema as compact JSON fitted to 64 KiB: past that, descriptions are cut to 160 characters and the definitions furthest from the root become short stubs. Validation still uses the full schema. Stripe's `payment_intent` went from ~357k to ~23k prompt tokens.
- The prompt asks for arrays of 3 to 5 items unless the request names a count.
- The Admin API request log (and MCP `list_requests`) includes `fallback_reason`.
- `POST …/contracts/{version}/approve` also activates the version unless the body is `{"activate": false}`; `mockingbird import --approve` activates unless `--no-activate`. The console still approves and activates in two steps.
- Drafts keep the documentation's operation ids (converted when invalid, the original in `x-original-operation-id`), get `required` and nullable properties from the examples and the text, drop `default` values the documentation does not state, and leave out operations below 0.4 confidence with a `low_confidence` warning.
- `/readyz` reports `config_reload: <error>` after a failed config reload until the next good one, and words a failed mock rebuild as `stale, serving the previous version` or `failed`.
- Config reloads log `config reloaded: N added, N removed, N changed`.
- The root fields of a GraphQL query are generated in one LLM call, as one object keyed by response key, so they agree with each other (GitHub's `user(login:)` and `organization(login:)` no longer both answer). A nullable field may be left out of that answer; one that stays invalid after the repair is answered field by field as before. Mutations, subscriptions and queries with root-level fragments or directives are unchanged.
- An LLM answer whose only errors are nulls the schema does not allow is patched instead of sent back for a repair call: an optional property is dropped, a required one gets a faker value. The response's source is `repaired`. Real APIs return null where their docs never say so (TMDB's `belongs_to_collection`), and models copy them; this saved a 20–40 s repair call on 4 of 8 TMDB detail pages.
- An answer wrapped like a GraphQL response (`{"data": {"user": {...}}}`) is unwrapped like an array envelope.
- The default LLM is OpenRouter: `MB_LLM_BASE_URL` defaults to `https://openrouter.ai/api/v1` and `MB_LLM_MODEL` to `deepseek/deepseek-v4.1-flash` (DeepSeek V4.1 Flash), so `MB_LLM_API_KEY` is an OpenRouter key. Set both variables to keep using DeepSeek directly (`https://api.deepseek.com`, `deepseek-chat`). The example configs and tests use an `openrouter` default profile.

### Fixed

- A create or update copies only the request members its response schema declares (all of them when it declares none): undeclared fields such as Twilio's `To`/`Body` in request casing or a credential sent in the body no longer appear in answers.
- An answer wrapped as `{"data": …, "errors": null}` is unwrapped like `{"data": …}`, and `minimum`/`maximum`/`multipleOf` violations are patched locally instead of costing a repair call.
- The GitHub GraphQL example mounts at `/graphql`, so it shares `api.github.com` with the GitHub REST example in one config.
- `serve --watch` sees updates to a config or contract mounted from a Kubernetes ConfigMap or Secret, which arrive as a swap of the volume's `..data` link rather than a change to the file.
- Provider replies with the answer only in `reasoning`, errors inside a 200, or output cut at `max_tokens` are handled (with one retry for transient failures) instead of falling back without a reason.
- A JSON array the model wrapped in a one-key object (JSON-object mode) is unwrapped when the inner value matches the schema.
- Real-world contracts load: a `$ref` inside a vendor extension (Stripe's `x-expansionResources`, GitHub's `x-github-breaking-changes`) no longer fails compilation, and an unresolvable `$ref` names its referrer and the JSON pointer where it sits.
- GraphQL schemas with covariant interface fields serve (GitHub's `User.email: String!` implementing `ProfileOwner.email: String`): implementations are checked with the spec's rules instead of async-graphql's inverted check.
- OpenAPI 3 `application/x-www-form-urlencoded` and `multipart/form-data` request bodies are compiled, decoded and validated; the engine no longer sees `"body": null` for them, nor for any non-empty body the contract does not describe. Bracket notation (`a[b][c]=1`, `a[0]=x`, `a[]=y`) nests in form bodies and query strings, so stripe-node requests validate against Stripe's schema. The request log shows the body as decoded. Swagger 2 `type: file` parameters are binary strings.
- GraphQL aliases of one field with different arguments (`small: repositories(first: 1)`, `large: repositories(first: 5)`) get separate generated values; aliases with identical arguments share one.
- Chaos errors on an operation that declares only a `default` error response (Stripe) answer HTTP 503 in that shape, with its message-like field set, instead of problem+json.
